# 黑金时代 CI/CD 建设心路历程

> 记录日期：2026-10-31  
> 项目：黑金时代 / 宜游轩 ERP  
> 主题：从本地开发、GitHub、Codeup 到阿里云 ECS 的 CI/CD 链路建设

## 一、最初的问题：代码到底应该放在哪里

一开始同时使用 WorkBuddy、Codex 和本地 Git，最容易混淆的是「谁占用了哪个分支」以及「本地分支、GitHub 分支、Codeup 分支是不是同一个东西」。

后来把职责拆开，问题就清楚了：

| 位置 | 分支 | 职责 |
| --- | --- | --- |
| Mac 本地 | `dev` | 日常开发、功能集成、本地测试 |
| Mac 本地 | `feature/*`、`fix/*` | 单功能或 Bug 修复，必要时配合 Worktree 并行开发 |
| Mac 本地 | `main` | 跟踪正式稳定版本，不作为日常开发中转 |
| GitHub | `test` | CI 自动化验证 |
| GitHub | `main` | 正式稳定版本，作为代码源 |
| Codeup | `main` | GitHub `main` 的镜像，连接阿里云 Flow 和生产部署 |

这里最重要的认识是：分支不是“被某个工具占用的文件”，而是提交历史的指针。WorkBuddy、Codex 可以通过不同 Worktree 同时工作，但每个工作目录必须有清晰的分支归属。

## 二、确定开发与发布流程

最终采用的主流程是：

```text
本地 dev
  └─ 创建 feature/* 或 fix/*
       └─ 完成功能、提交、本地测试
            └─ 合并回本地 dev
                 └─ 集成测试通过
                      └─ 推送 GitHub
                           └─ GitHub CI 验证
                                └─ GitHub main 更新
                                     └─ Codeup main 镜像同步
                                          └─ 云效 Flow 构建与部署
                                               └─ 阿里云 ECS 生产环境
```

这里没有让本地 `dev` 长期推送到 Codeup，也没有把 Codeup 作为日常开发仓库。Codeup 的职责是承接 GitHub 正式代码并执行阿里云侧的 CD。

## 三、CI 检查：先确认现状，再补齐缺口

CI 改造前先检查了现有的后端工作流、覆盖率门禁、Lint 门禁、PII 检查、前端测试脚本和构建脚本。

确定的原则：

1. 保留已有后端检查，不使用生产数据库和生产密钥。
2. 前端至少执行 TypeScript 检查、UI 守卫、自动化测试和构建验证。
3. Playwright E2E 与普通单元测试分开，关键业务路径逐步补齐。
4. `test` 用于自动化验证，`main` 只接收已经验证的成果。
5. 不通过测试时，不通过删除测试或 `skip` 来“修复” CI。

## 四、CD 的第一次落地：为什么构建很慢、为什么会失败

### 1. 国内 ECS 不适合直接依赖外部源

生产服务器位于阿里云国内区域，直接访问 Docker Hub、PyPI、npm 源不稳定，表现为拉取慢、连接失败或超时。

因此构建链路做了三项调整：

- Alpine 软件包改用阿里云镜像源。
- Python 依赖改用阿里云 PyPI 镜像。
- npm 依赖改用 npmmirror。

最终由 CI 构建镜像，ECS 只接收镜像包并执行 `docker load`，避免生产服务器现场编译。

### 2. 部署包不能把整个项目都上传

最初考虑把仓库内容整体打包，这会把日志、数据库、缓存、开发依赖和其他不需要部署的文件一起带上去，既慢又有泄漏风险。

最终的源码部署包只保留：

```text
deploy/docker-compose.yml
deploy/scripts/*.sh
frontend/nginx.conf
```

应用源码和前端静态资源已经进入 Docker 镜像，不需要再次作为源码上传。`.env`、SQLite 数据库、日志、`node_modules`、本地虚拟环境均不进入部署包。

### 3. 第一次部署失败：只解开了一层压缩包

部署产物结构是：

```text
heijin-deploy.tgz
├── heijin-images-1.0.0-amd64.tar.gz
└── heijin-source.tar.gz
```

第一次部署脚本只解开了外层 `heijin-deploy.tgz`，随后直接寻找镜像包，服务器因此报错：找不到 `heijin-images-1.0.0-amd64.tar.gz`。

根因不是镜像构建失败，而是部署脚本缺少第二层解包。修复后，脚本按顺序执行：

```bash
tar -xzf /tmp/heijin-deploy.tgz -C /tmp/heijin-cd
tar -xzf /tmp/heijin-cd/heijin-deploy.tgz -C /tmp/heijin-cd
gunzip -c /tmp/heijin-cd/heijin-images-1.0.0-amd64.tar.gz | docker load
```

### 4. 为什么源码包必须保留全部部署脚本

服务器上的 root crontab 使用：

```text
20 3 * * * /bin/bash /opt/heijin/deploy/scripts/backup_daily.sh
```

所以不能只上传 `deploy.sh`。虽然当前 CD 只直接执行 `deploy.sh`，但生产环境的备份任务还依赖 `backup_daily.sh`，最终改为保留整个 `deploy/scripts` 目录。

这是一次很有价值的检查：部署包的“最小化”不能只看当前发布命令，还要检查服务器已有的定时任务和运维依赖。

## 五、最终构建内容

流水线只构建两个应用镜像：

| 镜像 | 来源 | 用途 |
| --- | --- | --- |
| `heijin-backend:1.0.0` | `backend/Dockerfile` | FastAPI 后端、迁移和健康检查 |
| `heijin-frontend:1.0.0` | `frontend/Dockerfile` | React/Vite 构建产物、Nginx 静态服务和反向代理 |

构建基础镜像：

- 后端运行时：`alpine:3.20`
- 前端构建阶段：`node:22-alpine`
- 前端运行时：`alpine:3.20` + nginx

两个镜像被导出为一个 amd64 镜像包，生产 ECS 只做导入和启动，不在服务器上重新构建。

## 六、GitHub 与 Codeup 的分支同步

曾经出现过以下状态：

- GitHub `main`：`f2c633f`
- Codeup `main`：`3fdad377`
- 两者内容基本一致，但 Codeup 多了一个已验证的 CD 修复提交。

这不是代码冲突，而是两个远端的提交指针不一致。处理方式不是强制覆盖，而是把 Codeup 的额外提交以普通快进方式同步回 GitHub：

```text
GitHub main  f2c633f  ──▶  Codeup CD 修复 3fdad377
```

同步完成后，三处指针已经一致：

```text
本地 dev       3fdad377
GitHub main    3fdad377
Codeup main    3fdad377
```

本地 `dev` 的文件内容原本已经和 Codeup `main` 一致，只是历史指针分叉；确认工作区干净后，将本地 `dev` 对齐到 `3fdad377`，没有丢失业务文件。

## 七、最终验收结果

云效 Flow 第 8 次运行已成功：

- 构建镜像与部署包：约 3 分 28 秒
- 生产 ECS 部署：约 43 秒
- 后端容器：健康
- 前端容器：正常运行
- 公网前端：HTTP 200
- `/api/v1/health`：`status: ok`
- 数据库：正式 ECS SQLite 持久化库
- 安全响应头：CSP、`X-Frame-Options`、`X-Content-Type-Options` 已生效
- 每日备份脚本：仍在服务器并保留定时任务

## 八、现在的操作规范

### 日常开发

```text
从 dev 创建 feature/* 或 fix/*
→ 完成功能和测试
→ 合并回 dev
→ 本地集成测试
```

### 发布

```text
确认 dev 干净且测试通过
→ 推送 GitHub
→ 等待 GitHub CI
→ 更新 GitHub main
→ Codeup 自动镜像 main
→ 云效 Flow 构建镜像、上传部署包、部署 ECS
```

### 不允许的做法

- 不直接强推 GitHub `main` 或 Codeup `main`。
- 不把生产 `.env`、数据库和日志打进部署包。
- 不在生产 ECS 上依赖 Docker Hub、PyPI 或 npm 现场构建。
- 不因测试失败而删除测试或使用无理由的 `skip`。
- 不把 Codeup `main` 当作日常开发分支。

## 九、这次建设真正解决的事情

这次并不只是“把代码部署上去”，而是把几个容易混淆的边界拆清楚了：

1. **开发边界**：本地 `dev` 负责开发和集成。
2. **验证边界**：GitHub CI 负责自动化检查。
3. **镜像边界**：Codeup `main` 作为阿里云部署入口。
4. **运行边界**：ECS 只负责运行已经构建好的镜像。
5. **数据边界**：正式 SQLite 数据卷独立于代码和部署包。
6. **运维边界**：备份脚本和定时任务必须纳入部署依赖检查。

最终得到的不是一条“能跑一次”的链路，而是一条可以重复验证、重复部署、出现问题能定位到具体阶段的链路。
