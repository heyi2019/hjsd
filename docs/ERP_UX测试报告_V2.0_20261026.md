## 4. 取证更正：两项高优指控不成立

自动巡检的读数不能直接当结论。本轮用定向复测与 CDP 溯源复核 F2、F3，两者均不成立。

### 4.1 F2「输入控件无焦点反馈」→ 误报，撤销

巡检在 Tab 后立即读 `getComputedStyle`，读到 `box-shadow` 全透明。但：

| 检测条件 | `box-shadow` 计算值 |
| --- | --- |
| Tab 后立即读 | `oklab(0 0 0 / 0) 0 0 0 0` ×3（透明） |
| **Tab 后等 600ms** | **`color(srgb 0.039 / 0.388 / 0.847 / 0.24) 0 0 0 3px, …`** ← 蓝色焦点光环 |

**根因**：`antd-adapter.css:145` 写了 `transition: … box-shadow 220ms var(--ease-spring)`。巡检在**过渡首帧**取样，读到的是动画起点而非终态。`--focus-glow` Token 有值且可被解析，`.ant-input-affix-wrapper-focused` 类在 antd v5 下正常挂载，CDP 显示的规则链中聚焦态排在最末（应生效且确实生效）。

干扰项排除：`:where()` 将特异性压为 0、静止态与聚焦态均带 `!important`、内联 `!important` 同样被覆盖——三者均呈现层叠冲突的表象；改为延时取样后症状全部消失，据此统一定性为**取样时机**问题，而非样式优先级问题。

### 4.2 F3「触控目标 <24px」→ 误报，撤销

巡检以**内层 `<input>`** 的计算宽高判定（140×22）。但用户点击的是外层容器：

- 几何：wrapper `180×36`，inner input `140×22`；
- 实点测试：点击 wrapper **上留白**、**下留白**、input **正中**，三种情形焦点均落入 input；

→ **有效可点击区域为 36px 高**，远超 WCAG 2.5.8 的 24×24。内层 22px 是 `antd-adapter.css:135-138` 的刻意设计（外层负责高度与居中，内层交回 flex 自适应）。

### 4.3 教训归纳

巡检脚本有三类误报来源，本轮取证全部踩到过：

| 类型 | 例子 | 规避方式 |
| --- | --- | --- |
| 取样时机 | 带 transition 的属性读到首帧 | 属性受影响时延时复测 |
| 测内不测外 | antd 焦点态/触控区在外层容器 | 上溯有效交互容器 |
| 选择器与实际 DOM 不符 | `moreBtn` 只在 `.nav-item` 内找，实际是普通 `button` | 实点验证 |

## 5. 已修复：F1 接口失败被静默降级为「0」

### 5.1 现象与危害

全站 API 注入 500 后，工作台「进行中业务/已完成业务」由真实 **35/65** 变为 **0/0**，页面骨架照常渲染。经营系统里「0」有确定业务含义（真的没有业务），接口故障与「今日无业务」在界面上不可区分，用户会据此做出错误判断。

### 5.2 根因

`DashboardPage.tsx` 并非缺失错误处理——它已捕获异常并渲染 `ErrorBanner`。问题在于**错误态没有传导到派生指标**：`orders` 停留在初始 `[]`，`StatRow` 仍取 `.length` 得 0。即错误图景只做了一半。

### 5.3 修复

`StatRow` 契约原生规定 `amount` 为 `null` 时显示 `-`（`StatCard.tsx:26,39`）。据此把失败态接进去，两行：

```tsx
{ label: "进行中业务", kind: "count", amount: summaryError ? null : String(orders.filter(o => o.status === "ACTIVE").length) },
{ label: "已完成业务", kind: "count", amount: summaryError ? null : String(orders.filter(o => o.status !== "ACTIVE").length) },
```

**零波及面**：仅错误分支行为变化，正常路径渲染结果完全不变；未改组件、未改共用样式，其余 7 处 `StatRow` 调用方不受影响。

### 5.4 验证

| 项目 | 结果 |
| --- | --- |
| 浏览器实测（500 注入） | `进行中业务｜-｜已完成业务｜-`（修复前 `0/0`） |
| 浏览器实测（正常态） | `35 / 65`，与修复前一致，**零回归** |
| 全站巡检复跑 | CLS 0、对比度 0、溢出 0，与修复前逐项一致 |
| 单测 | `DashboardPage` 3 文件 **21 用例通过** |
| 类型检查 | `tsc -p tsconfig.app.json` 零错误 |
| 静态守卫 | `ui_guards` 零新增（4 项既存违规均在未改动的文件） |
| **变异验证** | 撤回 `summaryError ? null :` 后新增用例转红、其余 5 个仍绿 → 守卫有效，非假绿 |

新增契约测试 `DashboardPage.deep.test.tsx`：失败态断言显示 `-` 且**反证不得出现 `0`**。

**F5 已修复并验证**（`shared/api/client.ts`）：将 5xx 拦截前置到 v1 统一结构解析之前——后端业务异常（AppError）全部落在 4xx、其中文语义须原样透出，而 5xx 仅源于未捕获异常或网关故障、原文对用户无意义且可能携带英文/堆栈，故统一降级为中文兜底（BACKEND_ERROR / BACKEND_UNAVAILABLE）。修复前：`status>=500` 分支被 `if (data?.message) return` 提前返回架空；现 5xx 一律走中文。新增 2 条契约测试（结构化 5xx→中文、4xx 中文原样透出）并做变异验证（撤拦截后新用例转红、其余 12 条仍绿）。调用面 20+ 处，仅影响原「上屏英文原文」的 5xx 路径，属纯改善、零波及业务文案。

**F6 已定位根因（无需应用层改动）**（`rc-resize-observer`）：真机组件栈显示告警来自 `SingleObserver`(rc-resize-observer) → `ResizeObserver` → `Dropdown` → `TabNavListWrapper2` → `OrdersPage:300`，即在业务中心挂载 `<Tabs>`/`<Dropdown>` 时触发。经查 `rc-resize-observer@1.4.3` 的 `SingleObserver/index.js:3` 导入的是 `rc-util/es/Dom/findDOMNode`（带 `?.` 安全降级的封装，非裸 `ReactDOM.findDOMNode`）：React 18 下该封装仍会调用并产出 deprecation warning（业务中心 2 页各 1 处，无害）；React 19 移除 `ReactDOM.findDOMNode` 后，封装静默返回 `undefined` 而不崩溃（ResizeObserver 取不到节点仅不触发 resize 回调，不影响渲染）。**应用层 `OrdersPage` 仅正常使用 antd 组件，无改点；彻底消除需升级 antd 大版本（有回归风险，未要求）。结论：F6 为依赖层已知行为，当前 React 18 环境无需改动，React 19 前向兼容已确认。**
