# ERP 领域化治理实施方案 v1.0

## 1. 文档目的与适用范围

本方案将宜游轩 ERP 的现有功能按稳定的业务边界重新归类，用于后续需求评审、代码演进、权限设计、数据口径和测试组织。它是**渐进式治理方案**：先统一业务语言和调用边界，再逐步收口实现；本轮不以改表名、改编号或一次性重写页面为目标。

本文是规划与执行依据。产品功能范围仍以 [ERP PRD v1.3（当前实现版）](ERP_PRD_v1.3_当前实现版.md) 为准；字段、枚举、状态机、权限与接口分别以相应事实源为准。

## 0. 执行检查点（2026-11-06）

阶段 0 已完成首版落地：领域归属台账、八条关键链路基线、核心指标口径表、阶段 0 裁决记录和首批边界审计清单已经建立并登记。阶段 1 已完成首个高风险边界收口：订单事件派生资金流水改由资金结算域服务创建，仍保持事件、流水、资产状态和订单状态在同一事务内提交。

当前仍待执行的阶段 1 项目：账号资产命令/回执统一、利润分配归属裁决、跨域资金查询门面和幂等键全面清查。具体状态以 [领域边界审计清单](ERP_领域边界审计清单_v1.0.md) 为准。

### 1.1 目标

- 将当前 12 个功能域收敛为 6 个核心业务域、2 个支撑域和一组跨域平台能力。
- 将“回收 HS、提号 TH、代挂 DG”明确为交易履约域下的业务类型，而非各自独立的顶层领域。
- 固化订单、库存、资金、利润之间的单向职责边界，避免重复记账和跨模块直接改数。
- 维持现有 6 个一级导航，避免因内部架构调整增加一线人员的使用成本。

### 1.2 非目标

- 不在本方案中改变既有业务编号、数据库物理表名或历史单据内容。
- 不合并已经不同的业务规则、表单字段或状态机；共用的是流程框架，不是强行统一业务差异。
- 不以领域拆分为理由绕开现有规则快照、审计、权限与金额精度约束。

## 2. 现状与目标口径

### 2.1 现状功能域

当前 PRD 按功能统计包含 12 个域：工作台、订单与业务事件、账号库存、回收 HS、提号 TH、代挂 DG、客户与合作方、资金中心、返点、经营报表、设置与治理、数据导入。

该统计口径适合衡量需求数量，但不适合作为长期架构边界：HS、TH、DG 都包含建单、事件、交付、核算等相似生命周期；资金、返点和利润又存在同一笔业务多处处理的风险。

### 2.2 目标领域模型

| 分类 | 领域 | 主要职责 | 不负责的事项 |
|---|---|---|---|
| 核心业务 | 客户与合作方 | 客户、合作方、联系人、资料与业务关系 | 订单履约、资金入账 |
| 核心业务 | 交易履约 | 订单、业务事件、HS/TH/DG 业务类型、交付、分期/回款流程 | 直接修改资金池余额或经营汇总 |
| 核心业务 | 账号资产 | 账号入库、库存状态、运营资料、出库与账号交付记录 | 订单定价与资金记账 |
| 核心业务 | 资金结算 | 资金池、流水、押金、返点、核算凭据及结算确认 | 自行改变订单业务状态 |
| 核心业务 | 经营分析 | 工作台指标、利润、经营报表、数据中心 | 直接修改业务交易数据 |
| 核心业务 | 规则与配置 | 业务类型、字段、字典、费率、状态规则、团队与权限配置 | 追溯性改写已生效快照 |
| 支撑业务 | 数据接入 | 导入、校验、映射、对账、导出、异常数据处置 | 绕过正常业务规则批量写入 |
| 支撑业务 | 平台治理 | 身份认证、审计、附件、通知、搜索、运行治理 | 决定任何业务账务或状态流转 |

### 2.3 导航映射

领域边界是内部职责，不要求与导航一一对应。用户侧继续保留以下入口：

| 一级导航 | 对应领域 | 用户任务 |
|---|---|---|
| 工作台 | 经营分析 | 查看概况、待处理事项和高频入口 |
| 业务中心 | 交易履约、账号资产 | 建单、跟进事件、库存和交付 |
| 客户中心 | 客户与合作方 | 建档、查询与维护客户关系 |
| 资金中心 | 资金结算 | 查看和处理资金池、流水、押金、返点 |
| 经营中心 | 经营分析 | 查看订单利润、经营报表和数据分析 |
| 设置 | 规则与配置、数据接入、平台治理 | 管理规则、人员、导入及系统能力 |

## 3. 核心边界与强制规则

### 3.1 交易、资产、资金三域的单向协作

```text
客户与合作方 ──提供主体资料──► 交易履约 ──确认业务事实──► 资金结算
                                      │                           │
                                      ├──形成入/出库指令──► 账号资产 │
                                      │                           │
                                      └────提供只读事实──────────► 经营分析
账号资产 ──确认库存与交付事实────────────────────────────────────► 经营分析
资金结算 ──确认流水与结算结果────────────────────────────────────► 经营分析
规则与配置 ──发布未来生效规则──► 上述所有业务域
```

执行规则如下：

1. 交易履约负责记录“发生了什么”，例如订单创建、业务事件确认、交付完成和回款条件达成。
2. 账号资产负责记录“账号资产处于什么状态”，例如入库、运营、锁定、交付和出库；其状态不得由报表或资金模块反向修改。
3. 资金结算负责记录“钱是否已经确认”，包括流水、押金、返点和结算结果。任何影响余额、可用资金或利润的写入，必须通过资金结算域的统一服务完成。
4. 经营分析只读消费已确认的业务、资产和资金事实；发现问题应跳转至来源业务处理，不能在报表内直接改数。
5. 规则与配置只能对未来新建业务生效。订单、返点、分期等已创建对象继续保留创建时的规则快照。

### 3.2 跨域禁止事项

- 禁止业务页面直接新增、删除或修改资金流水。
- 禁止资金结算以修改订单状态替代结算确认。
- 禁止报表页面直接修正利润、余额、库存成本或订单金额。
- 禁止导入任务跳过权限、金额校验、状态机、审计与对账。
- 禁止通过修改当前规则版本影响历史业务的计算结果。

### 3.3 跨域协作契约

跨域写操作必须具备以下信息：来源业务对象、动作类型、操作人、发生时间、幂等标识、关联单据、审计说明。发生失败时，应返回可定位的错误，不允许出现“业务已完成、资金未入账”却没有补偿路径的静默不一致。

涉及资金的协作必须遵守“两段确认”：先形成可追溯的业务事实，再由资金结算确认流水；未确认的事项不得计入正式利润和可用余额。

## 4. 业务类型治理：HS、TH、DG

### 4.1 统一与保留

HS、TH、DG 统一使用交易履约域的通用能力：建单、编号、参与方关联、业务事件、附件、规则快照、审计、权限、交付记录和结算触发。

下列内容仍由各业务类型独立维护：

- 必填字段、表单板块、字段校验和展示文案；
- 专属状态与状态迁移条件；
- 费用项、交付资料、分期与返点适用条件；
- 专属报表维度和操作权限。

### 4.2 交付物

为每种业务类型建立一张“类型契约卡”，至少包含：适用对象、订单生命周期、库存影响、交付条件、资金触发点、规则快照、权限、异常场景和测试编号。类型契约卡应作为新增业务类型的准入条件。

## 5. 实施路线图

### 阶段 0：立项与基线盘点（第 1 周）

| 工作项 | 执行动作 | 产出 | 完成标准 |
|---|---|---|---|
| 领域归属台账 | 将现有功能编号、页面、接口、数据表、权限点和测试用例标记为一个主归属域 | 《领域归属台账》 | 每个条目只有一个主责域；跨域项标注协作域 |
| 关键链路盘点 | 盘点建单、入库、交付、回款、押金、返点、利润、导入八条链路 | 《关键链路清单》 | 每条链路有输入、输出、主责域和失败处理 |
| 数据口径核对 | 确认订单金额、库存成本、押金、返点、流水、利润的唯一事实来源 | 《核心指标口径表》 | 不存在两个模块都可修改同一指标的情况 |
| 架构裁决 | 评审本方案的目标模型和例外需求 | 裁决记录 | 产品、业务、财务、技术负责人签字确认 |

**阶段退出条件**：领域归属台账完成率 100%，所有影响资金和利润的写入链路均有负责人和来源凭据。

### 阶段 1：建立边界与防线（第 2–3 周）

| 工作项 | 执行动作 | 验收标准 |
|---|---|---|
| 统一领域入口 | 为每个目标领域建立明确的应用服务入口与权限校验职责 | 跨域写操作不再绕过主责服务 |
| 资金写入收口 | 清查并替换订单、库存、导入等路径中分散的流水写入 | 余额、流水、返点、押金均可追溯来源业务对象 |
| 状态机收口 | 将订单、账号、分期状态迁移与领域动作对应 | 无直接赋值跨越状态迁移的路径 |
| 审计增强 | 所有跨域动作补齐关联单据、来源动作和操作人 | 可从任意流水追溯至来源业务单据 |
| 幂等与补偿 | 为创建流水、库存指令、导入批次增加幂等标识与失败处置 | 重试不产生重复资金或重复库存 |

**阶段退出条件**：关键写链路均通过服务层、权限和审计；针对重复提交与中途失败具备自动或人工补偿方案。

### 阶段 2：交易履约域收敛（第 4–6 周）

| 工作项 | 执行动作 | 验收标准 |
|---|---|---|
| 通用订单骨架 | 抽出订单、参与方、事件、附件、交付、规则快照等公共能力 | HS、TH、DG 的共用行为口径一致 |
| 类型差异配置化 | 将各类型字段、板块、校验、费用项和状态差异放到类型契约 | 新增/调整类型规则不复制整套流程 |
| 交付与库存协作 | 定义订单交付与账号出入库的指令、回执和失败处理 | 交付失败不会留下错误库存状态 |
| 分期与回款协作 | 明确分期计划、回款确认、逾期处理对订单和资金的影响 | 分期金额、回款流水与订单应收可对账 |

**阶段退出条件**：三种业务类型完成类型契约卡；共用流程有共享测试，类型差异有独立测试。

### 阶段 3：规则、数据与分析治理（第 7–8 周）

| 工作项 | 执行动作 | 验收标准 |
|---|---|---|
| 规则发布流程 | 将费率、字段、业务类型、状态规则的发布、生效、停用流程统一管理 | 规则变更可审计，可明确影响范围 |
| 数据接入流水线 | 导入采用“预检 → 映射 → 试运行 → 对账 → 确认入库 → 归档”步骤 | 任意导入批次可查看差异与回滚/冲销方案 |
| 经营指标取数 | 将报表指标明确关联到订单、库存或流水的来源口径 | 利润和余额报表可下钻到原始凭据 |
| 历史数据修复 | 对历史不一致数据使用专用修复单与审计说明 | 禁止无痕直接改生产数据 |

**阶段退出条件**：正式导入均带批次、预检和对账；经营报表的关键指标均能追溯来源。

### 阶段 4：界面与组织固化（第 9 周）

| 工作项 | 执行动作 | 验收标准 |
|---|---|---|
| 导航梳理 | 按第 2.3 节校准入口、名称和跳转关系 | 用户无需理解内部领域即可完成工作 |
| 权限复核 | 按领域主责和动作重审权限矩阵与数据范围 | 无越权写入；必要只读可正常使用 |
| 看板和异常待办 | 在工作台展示跨域待处理事项，如待结算、待交付、导入异常 | 待办可跳转至主责域处理 |
| 运行手册 | 更新业务操作、异常处理、发布及回滚手册 | 新成员可按手册处理常见异常 |

**阶段退出条件**：完成角色验收、回归测试、数据对账和灰度观察后再正式切换。

## 6. 任务分工与节奏

| 角色 | 主责 | 每周固定动作 |
|---|---|---|
| 产品负责人 | 领域边界、需求归属、类型契约裁决 | 审核新增需求是否跨域、是否需要新规则 |
| 业务负责人 | 流程事实、异常口径、结算触发确认 | 审核关键链路和历史数据差异 |
| 财务负责人 | 资金流水、余额、押金、返点、利润口径 | 抽查资金链路与报表对账 |
| 技术负责人 | 服务边界、跨域协议、演进顺序、质量门禁 | 评审跨域写入和例外方案 |
| 开发人员 | 按领域实施、补齐审计、测试与迁移脚本 | 每项变更附主责域和回归证据 |
| 测试人员 | 领域测试、跨域流程测试、回归和对账 | 维护关键链路的失败场景覆盖 |
| 运营人员 | 灰度验证、实际使用反馈、异常登记 | 汇总入口、表单和数据口径问题 |

建议每周进行一次 45 分钟领域治理例会：只处理跨域归属、口径冲突、数据差异和高风险变更；普通页面样式问题仍走常规迭代，避免会议失焦。

## 7. 迁移、发布与回滚

### 7.1 迁移原则

1. 先加边界和适配层，再迁移调用方；旧路径确认无调用后再删除。
2. 优先保持接口兼容。确需调整时，先增加兼容版本和双写/双读校验窗口，再下线旧行为。
3. 数据库变更采用增量、可验证、可回滚的方式；禁止以领域重构为由重建生产库。
4. 需要修复历史数据时，必须先备份、后预演、再按批次执行并产出对账报告。

### 7.2 发布检查清单

- [ ] 变更已标明主责域、协作域、影响的业务类型和权限。
- [ ] 金额、状态机、规则快照和审计约束均已覆盖。
- [ ] 关键链路至少覆盖成功、重复提交、权限不足、关联对象不存在和中途失败五类场景。
- [ ] 上线前完成订单、库存、流水、押金、返点和利润的抽样对账。
- [ ] 已定义开关或明确的镜像/版本回退方案。
- [ ] 发布后观察期内，持续监控异常流水、状态不一致和导入失败。

### 7.3 回滚策略

代码问题优先回退应用版本；数据问题不得简单覆盖恢复。对于已产生的真实流水、库存和订单，应采用可追溯的冲销、补偿或修复批次处理，并保留审批与审计记录。

## 8. 测试与验收矩阵

| 层级 | 必测内容 | 通过标准 |
|---|---|---|
| 领域单元测试 | 金额计算、状态迁移、规则选择、权限判断、幂等 | 规则覆盖正常与边界输入 |
| 领域集成测试 | 订单/库存/资金服务之间的协议与事务 | 不产生重复写入或悬空关联 |
| 跨域流程测试 | 建单→入库→交付→结算→报表；导入→对账→确认 | 数据可串联、金额可对账、审计完整 |
| 权限测试 | 业务、财务、审核、查看等角色的读写边界 | 无越权，必要权限不误拦截 |
| 数据回归 | 历史订单、库存、资金和报表抽样比对 | 差异均有可解释原因和处置记录 |
| 用户验收 | 六个一级导航下的高频业务任务 | 一线人员可独立完成任务 |

领域化改动合并前，至少应完成项目既有后端测试、前端检查与构建，并按改动范围补充跨域回归证据。具体命令和测试资产维护方式见 [测试体系文档](testing/测试架构与执行规范.md)。

## 9. 风险与控制措施

| 风险 | 表现 | 控制措施 |
|---|---|---|
| 把目录重命名当成领域治理 | 文件移动后依赖关系和重复写入依旧存在 | 以服务职责、写入权限和数据来源为验收对象 |
| 过度抽象三种业务类型 | HS、TH、DG 的特殊规则被抹平 | 共用骨架，差异由类型契约和独立测试保护 |
| 资金改造引入账实差异 | 流水、余额、利润短期不一致 | 双向对账、幂等标识、灰度开关和可追溯补偿 |
| 规则发布误伤历史业务 | 调整费率后旧单利润变化 | 强制规则快照；历史修复走专用审批流程 |
| 导入绕过业务防线 | 批量产生错误数据且难追责 | 预检、试运行、对账、批次审计和回滚预案 |
| 导航随架构频繁变化 | 一线用户找不到入口 | 内部领域调整不等于用户导航调整 |

## 10. 首批两周行动清单

### 第 1 周

1. 建立领域归属台账，先覆盖所有资金、库存、订单和报表相关功能。
2. 绘制八条关键链路，标注每一步的主责域、输入、输出和异常处理。
3. 召开一次架构裁决会，确认目标领域模型与 HS/TH/DG 定位。
4. 明确核心指标唯一来源，并记录已有不一致项。

### 第 2 周

1. 找出所有直接写资金流水、余额、押金、返点的入口，形成整改清单。
2. 为建单→库存→交付→结算链路补齐关联单据、审计与幂等要求。
3. 编写 HS、TH、DG 三张类型契约卡并与业务负责人确认。
4. 选择一条风险最低的资金写入链路试点收口，完成回归和对账后再推广。

## 11. 成功判定

本方案不以“完成目录调整”作为成功标准，而以下列结果作为完成判定：

- 每个功能、接口、数据对象和权限点都能说清主责域。
- 任意一笔资金流水可追溯到来源业务事实、操作人和规则依据。
- 任意一笔利润可下钻到订单、库存成本、资金流水与返点依据。
- HS、TH、DG 共用流程一致，但各自差异没有被弱化。
- 历史业务不会因修改未来规则而被改变。
- 用户仍可从现有 6 个一级导航顺畅完成日常任务。
