## 1. 文档目的

本 PRD 只描述当前代码已经形成的产品能力、数据对象、用户流程和下一步缺口。只有当前代码、接口契约和当前验收结果能证明的能力才写入“已实现”；没有被当前实现证明的内容列入缺口或后续计划。

系统定位为工作室经营台账：统一记录业务订单、账号库存、资金明细、分期回款、返点、客户与合作方，并提供经营报表、权限控制、审计和标准导入能力。系统不接支付通道，不自动打款，所有资金事实由用户录入或由已登记业务事件生成。

## 2. 用户与权限

系统支持登录、退出登录、修改密码、首次登录强制改密和基于角色的后端鉴权。前端按钮显隐只用于体验，不能替代后端权限校验。

| 角色 | 主要能力 |
|---|---|
| 系统管理员 `admin` | 全部主数据、业务、资金、报表、导入、用户和团队管理 |
| 业务经办人 `operator` | 客户、合作方只读/建档/更新；创建和更新订单；发布业务事件；查看资金与报表 |
| 财务 `finance` | 资金池、押金、划转及资金相关事件；查看客户、合作方、报表 |
| 业务审核人 `auditor` | 查看资金；处理订单异常；审批经营规则；查看合作方和报表 |
| 经营查看人 `viewer` | 只读查看资金和经营报表 |

权限点覆盖客户、合作方、订单、业务事件、资金、押金、划转、规则、活字段、审计、报表、导入、用户和业务类型等领域。用户还可配置数据范围、所属资金池和团队。

### 3.2 全局交互约束

- 页面统一展示加载态、错误提示和重试入口。
- 金额前端以字符串接收和展示，前端不进行浮点计算；金额输入支持两位小数。订单详情中的操作明细、资金明细行、生命周期和运营动作等派生数据由后端 `OrderDetailView` 统一计算，前端只做格式化和渲染。
- 列表支持响应式布局；客户、订单和库存在窄屏下提供移动卡片或自适应表格。
- 受权限控制的动作使用统一按钮组件；无权限时不显示或不可操作。
- 业务对象的状态、编号和关键字段由后端返回，前端不自行推导可写状态。

## 4. 核心业务功能

### 4.0 业务、类型与增值服务边界

产品分类拆成三个层级，必须分别记录“业务”“类型”和“增值服务”，不能把三者混称为同一个业务类型：

| 层级 | 取值 | 含义 | 当前实现 |
|---|---|---|---|
| 业务 | 自营 `SELF` / 分销 `DISTRIBUTION` | 经营模式，描述账号和资金由谁承担、库存如何归属 | 订单列表和库存台账可按业务筛选 |
| 类型 | 回收 `HS` / 提号 `TH` / 代挂 `DG` | 同一级别的主业务类型，分别描述账号来源和当前核心交易 | 工作台和建单弹窗分别提供三类入口 |
| 增值服务 | 分期出售（`STOCK_SALE` / `PICKUP_SALE` 是当前有效合约类型；`CONSIGNMENT_SALE` 仅保留历史读取） | 在主业务之外提供的分期收款服务；回收、提号售出可选分期出售，代挂售出仅全款 | 分期合约按订单类型独立编码，不把分期收款混入三类主业务类型 |

具体归属关系如下：

| 产品分类 | 订单/合约编码 | 业务模式 | 说明 |
|---|---|---|---|
| 自营·回收 | 订单 `HS` | `SELF` | 工作室买入账号，进入 `RECOVERY` 自营库存 |
| 分销·提号 | 订单 `TH` | `DISTRIBUTION` | 从同行/供货方取得账号，形成 `PICKUP` 提号实体；不计入自营库存资产 |
| 分销·代挂 | 订单 `DG` | `DISTRIBUTION` | 受托销售账号，形成 `CONSIGNMENT` 实体；只记录卖出金额、订单利润、寄售方和平台，不配置抽成比例、金额来源或自动结算公式 |
| 自营·分期出售 | 合约 `STOCK_SALE`，不新增业务订单 | `SELF` | 已买入的 HS 自营库存分期卖给客户；分期收齐后交付 |

最终归属口径固定为：

| 产品 | 归属 |
|---|---|
| 回收 | 自营·类型 |
| 提号 | 分销·类型 |
| 代挂 | 分销·类型 |
| 分期出售 | 增值服务（回收·自营可选，提号·分销可选；代挂·分销仅全款） |

系统必须按以上归属处理展示、筛选、库存、资金和报表口径：

- `SELF` 只能承载自营回收，以及从自营回收库存发起的分期出售；
- `DISTRIBUTION` 承载分销提号与分销代挂；
- 回收（`HS`）、提号（`TH`）和代挂（`DG`）是同一级别的主业务类型；寄售不属于其中任何一种业务类型；
- 寄售是订单运营动作，必须归属于当前订单，不得因为寄售动作自动创建新的 `DG` 订单或改变原订单类型；
- `STOCK_SALE` 是自营回收库存的增值服务合约，不能被记录成独立订单类型；
- `PICKUP_SALE` 只允许由 TH 提号订单发起；`CONSIGNMENT_SALE` 仅保留历史读取，不允许由 DG 代挂订单新建；
- 错误组合必须由后端拒绝，前端只负责按字典提供可选项和提示。

`capital_type`（`STOCK`、`ZERO`）是业务定义层的核算维度标签，不等同于业务、类型或增值服务：它决定资金和成本如何路由，**不落在订单上、不支持按单覆盖**（2026-11-17 起订单层字段删除），也不能改变产品分类。库存字段使用 `business_mode` 保存业务，使用 `inventory_type` 保存来源（`RECOVERY`、`PICKUP`、`CONSIGNMENT`）。

### 4.1 工作台

工作台提供三类主业务的快速建单入口；增值服务从既有账号的售出入口发起，不新建独立主业务订单：

| 分类 | 编码 | 页面名称 | 当前建单入口 |
|---|---|---|---|
| 自营·类型 | `HS` | 回收 | 自营回收 |
| 分销·类型 | `TH` | 提号 | 分销提号 |
| 分销·类型 | `DG` | 代挂 | 分销代挂 |

增值服务的业务名称统一为「分期出售」，不按货源拆成「提号分期」「代挂分期」。合约类型仍按订单类型编码：`HS + STOCK_SALE`（回收售出分期）与 `TH + PICKUP_SALE`（提号售出分期）；代挂售出（`DG`）仅全款，不进入分期出售。工作台还提供“售出库存账号”入口和进行中/已完成业务数量摘要。摘要只来自订单列表，不重复实现经营报表。

三类建单当前实现共用以下结构：

- HS、TH、DG 共用“游戏账号信息”卡片，账号、密码、游戏类型、渠道/区服、账号备注和条件图片字段均按同一字段组件渲染；营地账号保留录入与数据能力，但不进入主展示字段；“二次图片（选填）”仅在选择有二次时出现，“钱包实名图片（选填）”仅在选择已注销时出现。
- HS、TH 共用“资金明细”卡片：主金额、资金账户和右上角“+ 增加支出”入口在同一卡片内；支出项只填写金额和备注。DG 建单不登记买入金额、不展示买入资金卡，售出时统一登记售出资金明细。
- 建单负责人、交付负责人和分润人员共用人员选择控件，选项只展示姓名，支持多选；提号供货方昵称为选填，供货方来源字段已移除。
- 客户备注、供货方备注和账号备注均为选填备注字段；提号建单提交时使用实际账号备注 `game_account_note` 与供货方备注同步写入订单上下文，不读取已下线的旧字段。
- 建单不在前端预先创建客户或供货方：HS/DG 提交客户草稿，TH 提交供货方草稿；订单接口在同一事务内先按既有档案口径复用，未命中才建档并绑定订单。订单创建任一步失败时，新增档案与订单一并回滚。

订单类型接口统一返回 `business_mode`、`business_type`、`value_added_service` 分类字段；前端筛选、订单详情和报表使用这些后端字段，不再从 `capital_type` 或库存字段推断业务归属。

### 4.2 订单与业务事件

订单创建支持业务类型、交易日期、账号快照或库存账号、负责人、资金类型、备注、活字段、客户角色和合作方角色。售出统一使用 `SELL`，通过 `SALE_MODE=FULL` 或 `SALE_MODE=INSTALLMENT` 区分全款和分期；分期合约在售出动作中建立。代挂不使用独立抽成结算字段。

订单状态为 `ACTIVE`、`COMPLETED`、`CANCELLED`。订单号按业务类型独立递增，创建后不可由前端修改。订单详情包含：

- 业务事件时间线：`BUY`、`SELL`、`DELIVER`、`CANCEL`、`OPERATE`、`REBATE`；每条事件记录操作人和发生日期；收入和支出另记 `cashflow`；利润分配只通过“分润配置”保存，不作为资金事件登记。操作明细按账号生命周期展示为“账号入库 / 账号运营 / 账号出库”：回收、提号、代挂建单分别显示“回收入库”“提号入库”“代挂入库”，售出显示“账号售出”；DG 的入库展示取建单事实，不额外创建 `BUY` 事件或资金明细；
- 动作性质统一为买号、售出、运营：回收/提号/代挂建单均保留业务负责人，运营通过 `OPERATION_TYPE` 区分作图、描述、寄售、下架；公司只作为利润归属。售出统一绑定实际操作人，全款和分期都记录同一个 `SELL`；
- 关联订单、资金明细、返点、分期合约/期次、附件和审计摘要；
- 订单编辑、取消和事件登记；
- 订单台账与库存中心列表“编辑”直接展开当前订单详情，不弹新窗口；订单类型、订单编号、账号关联、订单状态和历史审计记录不可编辑，其余文本字段、时间字段和操作人字段均可在展开详情内编辑并保存；
- 参与方编辑按订单类型提供客户和可用渠道方的多选下拉；允许直接新建客户/渠道方后加入当前订单，保存时通过详情编辑接口写入订单参与关系，取消编辑不删除既有参与关系；
- 订单台账的“操作”列和订单详情在订单已售出后提供“分润配置”，并提供登记退款、取消交易；系统管理员可执行“删除”，删除前必须填写原因并二次确认。库存编号与订单编号强绑定：删除时，订单及关联事件、资金明细、分润、分期、返点、押金、订单关系和绑定库存一并物理删除；若历史数据仍有多张订单挂在同一库存，则一并清理该库存下的其余订单，禁止留下孤立库存编号。库存中心不提供分润入口；库存中心的“删除”同步物理清理绑定订单及其全部业务从属数据，禁止留下孤立订单编号；两类删除均保留审计日志及客户、合作方等主数据；不提供独立的实际分润支出登记；行级操作会重新读取订单最新状态，避免使用列表快照执行资金动作；
- 订单台账与库存中心的运营动作均通过“运营”入口展开；订单台账固定展示描述、作图、寄售（上架）和下架四项，不可执行项置灰，库存中心按当前账号可执行项展示。订单台账的“取消”仍是订单级冲销/取消动作，代挂在库账号的系统下架只从“运营 → 下架”进入，不与“取消”混用；
- 订单台账与库存中心均以订单作为列表行和展开主键；库存中心等价于订单台账按库存状态筛选“在库”的视图，库存账号只作为订单关联的库存实体，用于详情资料、库存动作和账号编辑；两边使用同一订单详情展开组件与订单上下文；
- 资金池路由：显式指定资金池优先，否则使用业务默认路由。

寄售与代挂必须严格区分。回收（`HS`）、提号（`TH`）和代挂（`DG`）均为同一级别的主业务类型；寄售属于订单运营动作，不是业务类型，也不是代挂的别名。用户在任一订单上点击“寄售”时，只能向该订单登记一条 `OPERATE` 事件，`operation_type=CONSIGNMENT`，不得创建新的业务订单、消耗 `DG` 订单号、创建重复库存账号或改变原订单的业务类型、订单状态和资金状态。HS000 执行寄售后，寄售记录必须仍归属于 HS000，订单列表中不得因此出现新的 DG 订单。

寄售事件可以记录寄售平台、挂牌价格、实际上架时间、运营备注、操作人和审计信息。挂牌价格是平台运营资料，不是售出金额，不自动生成收入、支出、利润或其他资金明细。下架同样归属于原订单，使用 `OPERATE` 事件和 `operation_type=UNLIST` 记录，并保留寄售与下架历史：平台下架只取消对应平台上架记录、账号仍留在 ERP 库存；系统下架只允许 DG 代挂订单，登记系统下架后再取消/冲销原订单并让账号退出库存。只有用户明确发起“新建代挂业务”时，系统才创建 `DG` 订单。

业务事件可以关联零条、一条或多条资金明细；交付事件不产生现金流。业务事件按类型驱动订单、库存和分期状态；已登记事实只能通过冲销或补充事件修正。

#### 4.2.1 订单状态机

订单状态由后端状态机统一控制，前端只能展示状态并发起业务动作，不能直接改写状态。订单创建后进入 `ACTIVE`；订单状态只允许按下表流转：

| 当前状态 | 触发动作/事件 | 适用条件 | 下一状态 | 说明 |
|---|---|---|---|---|
| `ACTIVE` | `BUY` | 业务事实登记，尚未形成终态 | `ACTIVE` | 记录买入；其他收入 / 支出通过 `cashflow` 关联订单 |
| `ACTIVE` | `SELL` | 非分期订单完成售出 | `COMPLETED` | 生成售出事实并完成订单 |
| `ACTIVE` | `DELIVER` | 分期合约已满足交付前提 | `COMPLETED` | 交付事件不产生现金流，只确认业务完成 |
| `ACTIVE` | `CANCEL` | 取消未完成交易，或按原事件完成冲销 | `CANCELLED` | 必须填写原因；有资金事实时保留反向事件和退款金额 |
| `COMPLETED` | `CANCEL` | 已完成售出需要完整冲销 | `CANCELLED` | 必须关联被冲销事件，不能直接改状态 |
| `COMPLETED` | `CASHFLOW_CREATE[CASHFLOW_REASON=REFUND]` | 交付后发生全部或部分退款 | `COMPLETED` | 退款记录支出资金事实，不把已完成订单改成取消 |
| `COMPLETED` | `BUY` | 仅 HS/TH 且无分期合约，重新买入同一业务资源 | `ACTIVE` | 重新开启业务周期并保留原历史 |
| `CANCELLED` | 任意业务动作 | — | 拒绝 | 取消是终态，不再接受新业务事件 |

四类业务的主路径如下：

- HS：`ACTIVE → BUY → SELL[SALE_MODE=FULL] → DELIVER[DELIVERY_DIRECTION=SELL] → COMPLETED`；分期为 `ACTIVE → BUY → SELL[SALE_MODE=INSTALLMENT] → INSTALLMENT → CASHFLOW[CASHFLOW_REASON=INSTALLMENT_PAYMENT] → DELIVER[DELIVERY_DIRECTION=SELL] → COMPLETED`。
- TH：全款路径为 `ACTIVE → BUY → SELL[SALE_MODE=FULL] → DELIVER[DELIVERY_DIRECTION=SELL] → COMPLETED`；分期路径为 `ACTIVE → BUY → SELL[SALE_MODE=INSTALLMENT] → INSTALLMENT → CASHFLOW[CASHFLOW_REASON=INSTALLMENT_PAYMENT] → DELIVER[DELIVERY_DIRECTION=SELL] → COMPLETED`。
- DG：`ACTIVE → SELL[SALE_MODE=FULL] → DELIVER[DELIVERY_DIRECTION=SELL] → COMPLETED`；代挂不登记 `BUY`，不创建分期合约。
- 取消路径：`ACTIVE` 或 `COMPLETED → CANCELLED`；交付前取消按 `CANCEL_MODE` 和原资金池冲销，交付后使用 `CASHFLOW_REASON=REFUND`，两者均保留原始业务事实和审计链。

订单状态机与账号、分期合约同步约束：`CANCELLED` 订单不得再产生新事件；HS/DG 等库存型分期取消后账号回到库存，TH 取消后账号结束；状态变化必须与事件、资金明细、账号和分期状态在同一事务内完成。

#### 4.2.2 动作性质与人员

动作性质用于区分订单中由谁完成哪类业务工作，并作为利润分配项。每项动作性质均关联人员：

| 动作性质 | 业务含义 | 人员绑定 |
|---|---|---|
| 买号 `BUY` | 回收、提号、代挂均属于买号动作 | 绑定对应业务的操作人；当前回收、提号取已登记的买号事件操作人，代卷取建单操作人 |
| 售出 `SELL` | 账号售出统一使用标准售出动作；代挂和分期出售不另设售出名称 | 绑定执行售出的操作人；全款售出取售出事件操作人，分期出售取创建分期合约的操作人 |
| 运营 `OPERATE` | 订单的运营工作；通过 `OPERATION_TYPE` 区分运营类型 | 不建立独立运营动作台账；在每张订单的利润分配中选择运营人员和比例 |

公司是利润归属方，不是动作性质，也不绑定个人。分期是 `SELL` 的售出方式属性，不是独立动作性质。订单事件、资金明细、交付和冲销用于记录具体业务或资金事实，不因此新增利润分配动作性质。

利润分配按订单配置买号、售出、运营和公司归属四项，固定每项一行。买号、售出、运营行可多选人员，比例或金额只填写该动作合计，保存时按所选人数平分；公司行不绑定个人。买号收益绑定买号操作人，售出收益绑定售卖人，运营人员按订单选择。分配基数按订单收入与关联支出资金明细计算；返点收益单独核算，不参与分配。库存售出订单可追溯同一账号的买号事件；分期出售根据分期合约登记人绑定售卖人。当前不保留按人逐行分配入口或历史兼容分支。

退款规则要求交付前使用取消或冲销，交付后登记 `CASHFLOW_DIRECTION=OUT`、`CASHFLOW_REASON=REFUND`；原因和责任方必填，退款不得超过已收减已退，原收入与收款事实保留。取消交易完成后必须显示实际退款金额，并按原资金池回执；退款校验交付状态、退款上限及责任方，支持已完成订单退款。

### 4.3 账号库存

库存台账以订单为列表行和展开主键，账号是订单关联的库存实体；列表统一按“库存编号、订单号、入库时间、入库负责人、成本”在前，随后展示账号与业务字段。展示库存编号、来源订单、入库时间、入库负责人、成本、业务模式、库存类型、游戏类型、账号标识、平台、状态和未售时长。支持：

- 按状态、业务模式、库存类型和关键词筛选；
- 展开查看执行明细、订单事件、资金明细、返点和合作方；
- 全款售出、在当前来源订单上登记寄售、返点登记；
- 库存中心列表“编辑”和订单台账列表“编辑”均直接展开当前订单详情进入编辑态，不弹新窗口；订单类型、订单编号、账号关联、订单状态和历史审计记录保持只读，账号资料、交付、运营及执行明细中的文本、时间和操作人字段在当前详情内直接修改并统一保存；操作明细固定放在详情末尾；“描述”“作图”仍是独立运营操作，不存在单独的“编辑账号资料”入口；
- 导出当前筛选结果 CSV。

库存中心的“寄售”入口必须携带当前来源订单，将寄售记录写入该订单的运营事件。寄售不新增库存实体、不改变库存状态，不增加“代挂”类型统计；库存详情和订单详情展示当前订单的寄售平台、上架时间、挂牌价格及下架历史。

账号状态为 `IN_STOCK`、`INSTALLMENT`、`SOLD`、`VOID`。库存类型为 `RECOVERY`、`PICKUP`、`CONSIGNMENT`；`PICKUP` 可追踪但不允许通过库存售出动作重复售卖。账号密码按现行账号详情契约直接展示。

#### 4.3.1 账号状态机

账号状态只能由订单事件或分期处置动作驱动，不能由前端直接改写。允许的状态转移如下：

账号状态是**生命周期轴**（`WAITING` / `SOLD` / `VOID`），与库存在场状态 `inventory_status`（`IN_STOCK` / `OUT_OF_STOCK`）是两个独立维度，不得混用。

| 当前状态 | 触发动作 | 下一状态 | 业务说明 |
|---|---|---|---|
| `WAITING` | `BUY_STOCK` | `WAITING` | 自营买入后保留在库，同一账号可再次买入形成新轨迹 |
| `WAITING` | `SELL` | `SOLD` | 登记售出；由 `SALE_MODE=FULL` 或 `SALE_MODE=INSTALLMENT` 区分售出方式 |
| `WAITING` | `VOID` | `VOID` | 账号被取消 |
| `SOLD` | `BUY_STOCK` | `WAITING` | 售出撤销后重新入库 |
| `SOLD` | `RECOVER` | `WAITING` | 分期逾期回收后恢复在库 |
| `SOLD` | `CANCEL_STOCK` | `WAITING` | 买入事实被取消，退回在库 |
| `SOLD` | `CANCEL_SELL` | `WAITING` | 售出冲销后恢复在库 |
| `SOLD` | `CANCEL_SELL_END` | `VOID` | 售出冲销且业务终止 |
| `SOLD` | `VOID` | `VOID` | 账号被取消 |
| `VOID` | 任意业务动作 | 拒绝 | `VOID` 为终态，不再接受新动作 |

### 4.4 分期与回款

系统支持三类分期合约：

| 合约类型 | 来源 | 页面动作 |
|---|---|---|
| `STOCK_SALE` | 已进入库存的自营售出 | 每一期可单独选择服务费；查看期次、登记收款、结清后交付 |
| `PICKUP_SALE` | `TH` 提号订单 | 分期收款、逾期/违约、结清后交付 |
| — | `DG` 代挂订单 | 仅支持全款售出，不创建分期合约 |

合约记录本金、首付、服务费总额、期数、每期服务费、每期应还、首期日期、交付方式和备注；末期用 `final_period_adjustment` 吸收取整尾差。HS 的 `STOCK_SALE` 与 TH 的 `PICKUP_SALE` 每一期均可单独配置 `service_fee_rate`，也可为零；合约层 `per_period_service_fee` 作为默认值。历史 `CONSIGNMENT_SALE` 仅允许读取，不作为新业务创建类型。每期应收 `due_amount` 由当期本金与当期服务费组成。逾期费用可手工填写，非必填，不按逾期天数或比例自动生成。具体利率数值和金额算法由后续业务规则确认。收款必须选择首付或期次并记录日期；只有 `SETTLED` 合约可以执行交付。

分期状态和处置动作按以下规则执行：

| 项目 | 当前定义 |
|---|---|
| 逾期 `OVERDUE` | 期次到期日早于业务日期，且 `received_amount + waived_amount < due_amount` 时，系统将期次标记为逾期；合约存在未结清逾期期次时进入 `OVERDUE`。逾期只改变状态，不新增或冲销应收金额。 |
| 减免 `WAIVED` | 对未收期次登记经授权的减免金额，原 `due_amount` 不改写，只累计 `waived_amount` 并记录原因和审计。减免后收款额与减免额合计达到应收时，期次为 `WAIVED`；部分减免仍保留未收余额。减免不自动生成资金明细。 |
| 展期 | 展期是期次处置动作，不是独立状态。只能对未收、未减免完成的期次执行；更新 `due_on`，保留原到期日、操作人和原因。逾期期次展期后恢复为 `PENDING`，后续按新到期日重新判断。 |
| 违约 `DEFAULTED` | 违约是合约级状态，只能从 `OVERDUE` 合约登记并填写原因。登记后保留未收期次和原应收，不能直接交付或自动核销。 |
| 逾期后回收 | 三类分期合约均可回收关联账号；回收将原关联库存账号恢复为在库并保留原合约关联。 |
| 逾期后出售 | 回收完成后，通过库存中心选择全款或分期出售，形成新的出售事实；全款出售生成 `SELL`，分期出售生成新的分期合约，系统均根据同一账号最近一次未转售的回收处置自动生成 `RESELL` 关联。原分期应收不被新出售金额冲销。 |

期次状态为 `PENDING`、`PARTIAL`、`PAID`、`OVERDUE`、`WAIVED`；合约状态包括 `PENDING`、`ACTIVE`、`OVERDUE`、`SETTLED`、`DELIVERED`、`DEFAULTED`、`CLOSED`、`CANCELLED`。

#### 4.4.1 分期合约与期次状态机

合约状态由付款、逾期、结清、违约、关闭、交付和取消动作驱动：

| 当前状态 | 触发动作 | 下一状态 | 业务说明 |
|---|---|---|---|
| `PENDING` | `CASHFLOW_CREATE[CASHFLOW_REASON=INSTALLMENT_PAYMENT]` | `ACTIVE` 或 `SETTLED` | 登记首笔收入资金明细后生效；本次达到全部应收时继续结清 |
| `PENDING` | `MARK_OVERDUE` | `OVERDUE` | 到期仍未达到应收 |
| `PENDING` | `SETTLE` | `SETTLED` | 应收已通过收款或减免完成 |
| `PENDING` | `CANCEL` | `CANCELLED` | 合约取消 |
| `ACTIVE` | `CASHFLOW_CREATE[CASHFLOW_REASON=INSTALLMENT_PAYMENT]` | `ACTIVE` 或 `SETTLED` | 持续登记收入资金明细；本次达到全部应收时结清 |
| `ACTIVE` | `MARK_OVERDUE` | `OVERDUE` | 存在未结清逾期期次 |
| `ACTIVE` | `SETTLE` | `SETTLED` | 全部应收已完成 |
| `ACTIVE` | `DEFAULT` / `CANCEL` | `DEFAULTED` / `CANCELLED` | 进入违约或取消 |
| `OVERDUE` | `CASHFLOW_CREATE[CASHFLOW_REASON=INSTALLMENT_PAYMENT]` | `OVERDUE` 或 `SETTLED` | 逾期合约继续登记收入资金明细，达到全部应收时结清 |
| `OVERDUE` | `SETTLE` | `SETTLED` | 逾期应收全部完成 |
| `OVERDUE` | `DEFAULT` / `CLOSE` / `CANCEL` | `DEFAULTED` / `CLOSED` / `CANCELLED` | 风险处置、关闭或取消 |
| `SETTLED` | `DELIVER` | `DELIVERED` | 仅结清合约允许交付 |
| `SETTLED` | `CANCEL` | `CANCELLED` | 交付前取消并按取消规则处理 |
| `DEFAULTED` | `CASHFLOW_CREATE[CASHFLOW_REASON=INSTALLMENT_PAYMENT]` | `DEFAULTED` | 违约后收入资金明细保留违约状态 |
| `DEFAULTED` | `CLOSE` | `CLOSED` | 完成风险处置后关闭 |
| `DELIVERED` / `CLOSED` / `CANCELLED` | 任意业务动作 | 拒绝 | 终态不接受新动作 |

期次状态按单期收款、减免、逾期和展期动作流转：

| 当前状态 | 触发动作 | 下一状态 | 业务说明 |
|---|---|---|---|
| `PENDING` / `PARTIAL` / `OVERDUE` | `CASHFLOW_CREATE[CASHFLOW_REASON=INSTALLMENT_PAYMENT]` | `PARTIAL` 或 `PAID` | 收入资金明细未达到应收为部分收款，达到应收为已收齐 |
| `PENDING` / `PARTIAL` | 到期检查 | `OVERDUE` | 到期且收款与减免合计不足应收 |
| `OVERDUE` | `EXTEND` | `PENDING` | 展期后恢复待收，保留原日期与原因 |
| `PENDING` / `PARTIAL` / `OVERDUE` | `WAIVE` | 原状态或 `WAIVED` | 减免未完成时保留原状态，达到应收后为已减免 |
| `PAID` / `WAIVED` | 任意收款、减免或展期 | 拒绝 | 已完成期次不可重复处置 |

减免和违约沿用现有 `order.exception.approve` 异常处置权限，不新增专门审批角色，也不增加额度判断。展期不设单期次数和最长天数限制，只校验新到期日晚于原到期日并要求填写原因。回收后的资产保管期限和转售定价不预设固定规则，只记录实际处置事实并沿用现有库存与订单核算口径；转售收入及相关收益归公司。

### 4.5 客户与合作方

客户档案支持客户编号、名称、联系人、手机、微信、QQ、来源、备注、标签和活字段。联系方式直接展示已建档原值；重复联系方式只提示候选，不阻止建档。

客户详情展示订单参与关系、分期合约、汇总指标和审计记录。客户可停用或合并；`DISABLED`、`MERGED` 客户不能作为新订单参与方。

客户需求状态为 `OPEN`、`CONVERTED`、`CLOSED`：新建进入 `OPEN`，只能从 `OPEN` 转为已转单或已关闭；转单和关闭后不可编辑。

合作方与客户分开建模，类型为 `PEER`（同行）、`SUPPLIER`（供货方）、`PLATFORM`（平台），支持建档、启停和在订单中绑定角色。

### 4.6 资金中心

资金池是可配置主数据，字段包括代码、名称、用途类型、归属和状态。资金归属为 `OWNED`、`CUSTODY`、`THIRD_PART`；停用池保留历史流水，不允许破坏历史归属。

资金中心按一级页面组织为总览、资金明细、工作室运营、押金和对账；资金明细统一展示公司业务资金收支与工作室运营收支，通过 `ledger_type` 列区分账簿，工作室运营同时作为独立维护入口。资金池总览展示收入、支出、转入、转出、现金余额、押金占用和可用余额。资金明细采用顶层账簿与三层属性：

| 层级 | 当前采用的定义 |
|---|---|
| 顶层账簿 | `BUSINESS` 业务资金账簿、`STUDIO` 工作室运营账簿 |
| 现金方向 | `IN` 收入流入、`OUT` 支出流出 |
| 核算属性 | 具体归类收入、成本、费用、收款、付款、返点、押金或划转 |

现金方向和以下核算属性均已确认：

| 核算属性 | 定义 | 典型场景 |
|---|---|---|
| `SELF_REVENUE` | 自营销售或自营分期回款收入 | HS 售出、`STOCK_SALE` 分期回款 |
| `PURCHASE` | 自营或分销账号买入支出 | HS / TH `BUY` 关联的 `OUT` 资金明细 |
| `PURCHASE` | 为客户需求向同行采购账号形成的分销买入支出 | TH 向同行买号 |
| `TH_REVENUE` | 将按客户需求采购的账号卖给客户形成的分销销售收入 | TH 向客户售号 |
| `SERVICE_REVENUE` | 已确认的服务费、佣金等收入 | 分期合约已确认服务费；DG 仅在实际结算口径确认后使用 |
| `REBATE_INCOME` | 返点收入 | `REBATE` 业务事件关联的 `IN` 资金明细 |
| `OPERATING_EXPENSE` | 与具体订单无直接对应的日常经营费用 | 平台费、人工、办公等 |
| `DEPOSIT` | 外部/受托押金的占用、释放或损失 | `DEPOSIT_HOLD`、`DEPOSIT_RELEASE` |
| `EXTERNAL_FUNDING` | 非经营性的外部资金注入或退出 | 股东注资、借款 |
| `INTERNAL_TRANSFER` | 资金池或账户之间的内部调拨 | `TRANSFER` |
| `REVERSAL` | 对原资金事实的反向冲销 | 流水、返点或费用冲销 |

TH 是客户需求驱动的分销买卖：向同行采购形成 `OUT` 买入资金明细，卖给客户形成 `TH_REVENUE` 收入。服务费、佣金和返点按对应收入属性记录；同一核算属性必须关联来源订单、事件、押金或划转记录。

当前前端已提供总览、统一资金明细、工作室运营、押金和对账五个一级页面，支持查询、新增、冲销、押金占用、释放与损失登记、池间划转、单边划转修复、日对账和差异核销；后端接口、权限门控和异常提示已接入。资金流水登记即生效；池间划转由一次事务直接生成共享 `transfer_id` 的一出一入流水，不存在独立划转草稿或二次审核阶段。押金释放更新 `deposits` 并生成同池 `DEPOSIT_RELEASE` 流水，不单独维护释放明细表。

当前实现边界：余额快照（`FIN-01-05`）尚未实现，仍保留为 P3 后续能力；其余本段列出的资金操作已具备前端入口和对应后端接口，仍需在目标部署环境补充端到端联调。

#### 4.6.1 资金明细状态机

资金流水没有独立状态机：登记即参与余额、报表和对账；错误通过新增反向冲销流水处理，原事实保留。

#### 4.6.2 押金、对账与账期状态机

押金状态按占用、释放和损失金额累计计算：

| 当前状态 | 触发动作 | 下一状态 | 业务说明 |
|---|---|---|---|
| 新建押金 | 占用 | `PAID` | 生成押金占用流水，不计入经营损益 |
| `PAID` / `PARTIALLY_RETURNED` | 部分释放 | `PARTIALLY_RETURNED` | 仍有未释放余额 |
| `PAID` / `PARTIALLY_RETURNED` | 全部释放 | `RETURNED` | 释放金额达到押金金额且无损失 |
| `PAID` / `PARTIALLY_RETURNED` | 损失 | 原状态或 `LOST` | 损失未结清时保留原状态，累计损失达到余额后为已损失 |
| `RETURNED` / `LOST` / `CANCELLED` | 任意释放或损失 | 拒绝 | 终态不可重复处置 |

对账记录创建后进入 `OPEN`，提交差异处理说明并核销后进入 `RESOLVED`；`RESOLVED` 不允许重复核销。账期锁定能力（原 `period_locks` 表、`finance.period.lock` 权限与「锁定账期」入口）已整体移除，当前版本不提供账期锁定。

返点作为资金中心的一项核算属性（不单独拆分产品章节）：

返点是 `REBATE` 业务事件，并关联资金明细：返点实际归本方时使用 `CASHFLOW_DIRECTION=IN`、`CASHFLOW_REASON=REBATE`，资金明细通过 `source_type=ORDER_EVENT`、`source_id=event_no` 回指事件。返点金额进入经营收入统计，但必须与订单收益和平台手续费分开核算，避免重复计入销售收入；当前版本不提供“返点退回”专用接口。

业务口径：返点是收入，返点收益为返点金额，金额全站唯一取 `rebate_records.amount`，`rate` 只留痕不参与金额计算；返点登记即完成收入确认，不再生成分次结算流水。报表按返点金额展示，不得再 `+rebate` / `+settled_rebate` 重复加回。`rebate_settlements` 表 / ORM / 编号器于 2026-11-05 下线，已有库历史表保留不 drop。

返点业务事实仍必须关联来源订单，记录 `REBATE_TYPE=BUY/SELL`、渠道、费率、返点金额、实际日期和状态。返点金额由登记人明确填写，规则费率只作留痕，不按成交额、本金或利润反推返点金额。返点登记直接关联一笔 `IN` 返点收入资金明细；如产生平台手续费，另登记一笔 `OUT` 经营支出资金明细。

返点状态按当前记录生命周期使用 `OPEN`、`VOID`；库存详情和订单台账提供返点登记入口，资金中心负责查看收入明细和冲销结果，并受 `rebate.read`、`rebate.create` 权限控制。

#### 4.6.3 返点状态机

返点状态按已审核结算金额与应收返点金额计算，冲销不删除原结算事实，只重新计算有效结算状态：

| 当前状态 | 触发动作 | 下一状态 | 业务说明 |
|---|---|---|---|
| `OPEN` | 部分结算 | `PARTIALLY_SETTLED` | 有效结算金额大于 0 但未达到应收 |
| `OPEN` | 全部结算 | `SETTLED` | 有效结算金额达到应收 |
| `PARTIALLY_SETTLED` | 继续结算 | `PARTIALLY_SETTLED` 或 `SETTLED` | 根据累计有效结算金额重新计算 |
| `PARTIALLY_SETTLED` / `SETTLED` | 冲销结算 | `OPEN` 或 `PARTIALLY_SETTLED` | 结算冲销后按剩余有效金额重新计算 |
| `OPEN` / `PARTIALLY_SETTLED` / `SETTLED` | 取消 | `VOID` | 仅在受控取消动作中使用，取消后不可继续结算 |
| `VOID` | 任意结算或冲销 | 拒绝 | 取消为终态 |

### 4.7 经营报表

经营中心提供以下只读报表：

| 报表 | 内容 |
|---|---|
| 月度损益 | 销售收入、成本、运营费用、返点和经营利润，可按日期区间筛选；返点收益按返点金额统计，平台手续费计入费用 |
| 分润对账 | 人员、订单、利润基数、费率和应付，可按日期区间筛选；当前不登记实际分润出账 |
| 业务损益 | 各业务订单数、收入、成本、利润；返点收入与分期坏账已计入收入 / 成本，“已结算返点 / 未归集返点 / 完整收益”三列已下线 |
| 订单利润 | 订单收入、成本、返点和净利润，可按日期区间筛选；成本统一包含该订单全部支出 |
| 数据中心 | 订单总数与进行中数量；售出成本、库存成本（未售出）、工作室成本、账号售出利润、工作室其他收入和利润合计；利润 = 账号售出利润 + 工作室其他收入 | 后端统一汇总，工作室成本仍由资金中心维护，数据中心只展示经营摘要 |

资金属性分析不再作为产品能力提供；资金日报暂保留为经营中心的只读日报入口。经营中心保留的报表接口支持按权限范围取数，并提供 CSV 导出接口；页面提供现役报表导出按钮、统一起止日期筛选和 `report.export` 权限门控，审计记录单独提供审计查询入口。

### 4.8 设置与可配置能力

- 业务类型：读取业务类型、资金性质和启停状态；后端支持创建、编辑、停用和路由配置，前端支持名称/说明/排序编辑、启停和路由影响预览。
- 资金池：前端支持新增、名称/用途/归属/备注编辑和启停；后端支持编辑、停用、删除保护和余额查询。
- 活字段：支持 `TEXT`、`NUMBER`、`DATE`、`BOOLEAN`、`SELECT`、`MULTI_SELECT`，可按订单、账号、客户、分期、资金池、流水、需求和合作方挂载；有历史值的字段只能停用。
- 经营规则：支持规则定义、版本、生效区间、发布/审批和引用快照；订单、返点、分期创建时保存规则版本与参数快照。
- 人员与团队：管理员可创建、更新、停用、重置密码、设置数据范围、资金池范围和团队归属。
- 标准导入：支持订单、账号、流水、分期、需求五类批次；导入只保存原始行和人工映射，不自动猜测关联。

#### 4.8.1 规则版本与标准导入状态机

规则版本新建为 `DRAFT`，审批发布后进入 `ACTIVE`；已被业务引用的版本不可编辑或删除，历史版本只能通过受控生命周期标记为 `EXPIRED` 或 `SUPERSEDED`，不能改写已产生业务的规则快照。

标准导入批次和导入行均保留原始数据，不直接覆盖业务事实：

| 对象 | 当前状态 | 触发动作 | 下一状态 | 业务说明 |
|---|---|---|---|---|
| 导入批次 | 新建 | 创建批次 | `DRAFT` | 保存原始文件、原始行和来源信息 |
| 导入批次 | `DRAFT` / `MAPPED` | 提交 | `COMMITTED` | 已映射行标记已导入，未映射行保留异常 |
| 导入批次 | `DRAFT` / `MAPPED` | 回滚 | `ROLLED_BACK` | 只改状态和行状态，不删除原始文件与审计 |
| 导入批次 | `COMMITTED` | 创建更正批次 | 原批次 `CORRECTED`，新批次 `DRAFT` | 原批次只读，更正内容进入新批次 |
| 导入行 | `UNMAPPED` | 人工映射 | `MAPPED` | 必须填写关联依据 |
| 导入行 | `UNMAPPED` / `MAPPED` | 跳过 | `SKIPPED` | 必须填写跳过原因 |
| 导入行 | `MAPPED` | 批次提交 | `IMPORTED` | 仅表示该行完成导入确认，不自动生成新业务事实 |
| 导入行 | 非 `IMPORTED` | 批次回滚 | `ROLLED_BACK` | 原始行保留，禁止再次编辑 |

#### 4.8.2 主数据启停与合并规则

主数据停用只阻止未来新业务引用，不删除历史事实；不同对象的状态边界如下：

| 对象 | 状态流转 | 关键约束 |
|---|---|---|
| 客户 | `ACTIVE ↔ DISABLED`；`ACTIVE` 或 `DISABLED → MERGED` | 停用客户不可参与新订单；合并必须指定仍为 `ACTIVE` 的目标客户；`MERGED` 为终态并保留来源编号和审计 |
| 合作方 | `ACTIVE ↔ DISABLED` | 停用合作方不可参与新订单，历史订单仍可查询 |
| 资金池 | `ACTIVE ↔ DISABLED` | 停用池不可承接新流水；已有流水的池只能停用，不能物理删除 |
| 资金池账户 | `ACTIVE ↔ DISABLED` | 停用账户不可承接新流水，历史流水和余额仍可查询 |
| 业务类型 | `DISABLED → ACTIVE`、`ACTIVE → DISABLED` | 只有存在有效资金池路由且目标池启用时才能启用；停用后不可新建订单，历史订单不受影响 |
| 游戏类型 | 启用/停用 | 默认游戏类型不可停用；停用类型不可再设为默认 |
| 业务—资金池路由 | 启用/停用 | 只有启用路由参与新单默认匹配，路由变更不重算历史事件的实际资金池 |

池间划转不单独维护业务状态，而是以同一 `transfer_id` 关联一笔转出和一笔转入流水；正常创建必须原子成对，发现单边记录时只能进入异常修复，不得静默补配或当作新划转。

#### 4.8.3 治理对象生命周期与关联状态

以下对象不参与订单业务状态机，但必须遵守各自生命周期规则：

| 对象 | 生命周期/分类 | 关键约束 |
|---|---|---|
| 人员 | `ACTIVE ↔ DISABLED` | 停用前有进行中订单时必须转交或明确保留；停用后不可登录和被新记录选择，历史经办人保留 |
| 团队 | `ACTIVE ↔ DISABLED` | 停用团队不可用于新的归属配置，历史归属保留 |
| 活字段定义 | `ACTIVE ↔ DISABLED` | 停用后历史值继续展示，新建表单不可填写；已有历史值不能改键/类型，不能物理删除 |
| 通知 | 未读（`read_at` 为空）→ 已读 | 只能由接收人标记已读，已读不可回退为未读；通知不替代业务对象状态 |
| 附件 | 有效（`deleted_at` 为空）→ 软删除 | 删除保留审计和文件追溯，不物理删除，不影响关联业务事实 |
| 订单/返点关联 | `LINKED`、`UNLINKED`、`ORPHAN`、`UNLINKED_TRANSFER` | 这是数据质量分类，不是人工推进的业务状态；补关联或修复必须留痕，禁止自动猜测 |

## 6. 数据与技术约束

1. 金额数据库类型为 `DECIMAL(18,2)`，接口金额以字符串传输，禁止以浮点数参与核算。
2. 所有写操作通过 Service 事务完成，并写入审计日志；路由层不直接修改模型。
3. 业务事件、现金流、库存状态和分期状态必须保持可追溯关联；已登记事实不可直接编辑或删除。
4. API 统一返回 `{code, message, details}` 错误结构；参数校验失败返回 422，并给出字段路径。
5. 请求带 `X-Request-ID`，后端在响应中回传；错误和审计记录使用同一请求上下文。
6. 生产环境使用 JWT 登录和令牌撤销；开发环境仅保留本地角色直通用于权限联调。
7. 数据库通过 Alembic 管理，启动前必须完成迁移和基础种子；历史导入批次保留原始行、映射依据和回滚记录。
8. 资金明细具备现金方向和核算属性；TH 向同行采购归 `OUT + PURCHASE`，向客户售出归 `IN + TH_REVENUE`；客户/合作方押金归 `DEPOSIT`。
