## 九、维护规则

1. **升级即转正**：新版以终态口径全文重写，旧版 `git mv` 进 `archive/`，不在旧稿上打补丁。**归档件一律加 `_已作废` 后缀**（`archive/` 下不允许出现无状态后缀的文档：同一份文档的新旧两版同名时，靠目录区分不够，会被人从旧路径打开当成现行依据）。**含可执行步骤的文档**（上线执行单、迁移操单、演练清单——读者会照着敲命令的那类）还要在正文最顶部加 4 行横幅：①「已作废，不得作为上线/执行依据」；② 一句话说清作废原因（照它做会出什么错）；③ 现行版本文件名；④ 归档日期。只加后缀不加横幅不够 —— 翻到归档的人可能不看文件名，直接照第 0 节的命令执行。既有状态后缀（`_已作废`、`_当前实现版`、`_已合并`、`_已生成`）统一归一为 `_已作废`，不复用同义异形词。
2. **能力下线要留痕**：任何功能下线（如表、枚举、权限点、页面入口）必须在对应事实源文档中显式写入"已移除"段落，并列出原名称，避免后人误以为缺失是遗漏。
3. **文档不得绑定代码实现位置**（2026-11-04 强化为可执行判据）。文档绑代码 = 代码一改文档就散布假信息，且会造出「文档说我为准、我说代码为准」的环路。三级判据：

| 形态 | 例 | 判定 |
|---|---|---|
| **业务契约**：表名、字段名、枚举值、接口路径、错误码、权限点、编号规则 | `stocks.stock_no`、`POST /orders/{id}/links`、`PERM_FUNDS_AUDIT` | ✅ **必须写**。这是文档在定义、代码来遵守的东西，不是绑定 |
| **对齐锚点**：文件 + 符号名 | `core/security.py` 的 `ALL_PERMISSIONS`、`core/state_machine.py` 的 `ORDER_TRANSITIONS` | ✅ 允许。文档需声明「跟谁对齐」；符号改名时有编译/测试兜底 |
| **行号定位**：`文件:行号`、`文件:起-止` | `AppShell.tsx:210`、`OrdersPage.tsx:374-455` | ❌ 禁止。行号必漂，且漂了没有报错 |
| **目录路径定位**：完整实现路径 | `frontend/src/components/layout/AppShell.tsx` | ❌ 禁止。目录会重组（该文件现已移到 `frontend/src/app/`） |

   **唯一例外：时点性证据文档**（代码体检报告、测试执行报告、审计留痕、实测记录）。它们的价值本体就是「那一刻在哪个位置」，删了行号就无法复核。但必须同时满足两条：① 头部显式声明**证据基准日期**；② 显式声明**不得作为现行依据**。且此类文档只增不改，不随代码演进维护。

   判据速查：**这份文档描述的如果是"代码长什么样"，它就该进 `archive/`；描述的是"业务必须怎样"，才配留在正位。**

   **边界：禁的是向代码定位，不是禁引用。** 文档之间可以、也应该互相引用 —— 跨文档定向一律走 `.md` 引用（`[名称](文件.md)` 或 `见 xxx.md`），不走"去代码某个位置看"。文档谱系必须能被读通；只引 `.md` 不引代码位置，是这套体系的成立前提。引用要满足两条：① 目标文件真实存在（归档件写 `archive/xxx.md`，不写裸文件名）；② 引用目标本身有效 —— **一份文档如果引用了已失效或已归档的作品，等于把自己也交出去了**（11-04 那次环路就是这个成因）。
4. **代码不得引用文档**：源码、脚本、CI 配置里不得出现文档文件名或版本号（禁止 `见 xxx_v1.0.md` 这类注释）。原因：文档升版会改名，代码注释随之腐化，且把「文档当权威」会让改文档看起来像改代码。代码注释只写**行为约束本身**，或指向代码内的符号（如 `core/security.py` 的 `PERM_*`）。
5. **新增文档要登记**：任何新增的 `.md` 落入 `docs/` 或仓外目录，必须同步更新本文件的对应章节；自动生成的产物（`testing/测试用例库.md`、`testing/测试报告.md`、`testing/测试结果库/results.jsonl`、`frontend/scripts/test-timing-report.md`）写明"禁手改"并只登记产出脚本，不登记内容。
