## 1. 业务模式（唯一事实源）

### 1.1 模式定义：委托代理制 + 多资金池

工作室出资、员工买号、售出回本、差价入利润池。
**业务与资金池均可自由新增，二者不写死绑定。**

```
              投资款
                │
                ▼
    ┌──────────────────────┐
    │  投资款荷包（本金）   │──► 员工买号 ──► 库存（在途账号）
    │    又称「小荷包」     │──► 付同行 ──► 登记
    └──────────┬───────────┘
               │ 售出打回本金
               ▼
    ┌──────────────────────┐
    │  利润荷包（利润）     │◄── 售出差价
    │    源数据称「利润池」 │◄── 平台返点（成单后附加）
    └──────────────────────┘
```

### 1.1.1 业务分类：四类主业务 + 一类附加收入（业务可新增）

**返点不是独立业务，是四个业务成单后的额外收入。**

| 业务 | 代��� | 业务定义 | 资金性质 |
|---|---|---|---|
| **回收** | `HS` | 客户把号卖给我，我择机卖出 | 库存型 |
| **提号** | `TH` | 买家找我买号，我去同行那里提号卖给他 | 库存型（PICKUP） |
| **代挂** | `DG` | 客户让我帮忙卖他的号，我收服务费 | 零本金型 |
| └ **蹭点** | `DG` | **代挂的一种叫法**，非独立业务 | 零本金型 |
| **代分期** | `DFQ` | 分销分期服务，按合约登记收款和交付 | 历史分类 |
| **返点** | — | **附加收入**，非独立业务 | 纯利润型 |

> **分期出售不是第五类业务**：它是 `HS` 回收库存的出售方式——已有库存账号卖给客户、客户分期付款；`DFQ` 代分期属于分销分期服务，按实际业务登记付款、收款和交付。两者都建立分期合约，但业务来源和核算口径不同。

**术语等价表**（源数据存在同义混用，须归一）：

| 源数据写法 | 归一为 | 说明 |
|---|---|---|
| 蹭点 | `DG` 代挂 | **主理人口述确认：蹭点就是代挂** |
| 氪金联盟提号 / 氪金提号 / 提号 | `TH` 提号 | 同一业务，流水表有简写 |
| 小荷包 / 经营池 / 投资款荷包 | 投资款荷包 | 同一池，4 种叫法 |
| 利润池 / 利润荷包 | 利润荷包 | 同一池，2 种叫法 |

> **「氪金联盟回收」不在归一范围**：实测 10/1 支出 1,544.40 → 10/2 收入 1,544.40，
> 是独立业务，不是 `TH` 提号。

**返点依附于主业务**：

```
一笔「回收」成单 ──► 平台返点（盼之首保6% / 续保3% / 螃蟹收号5%）
一笔「提号」成单 ──► 平台返点
一笔「代挂」成单 ──► 平台返点
一笔「代分期」成单 ──► 平台返点
```

**关键设计含义**：

| 含义 | 说明 |
|---|---|
| 返点不占 `order_type` 主枚举 | 它是**主业务的附加属性**，不是第五类业务 |
| 返点记录必须挂 `source_order_id` | 指向产生它的那笔主业务订单 |
| 返点到账可分次 | 一笔返点记录可有多笔到账明细，分别记录到账日期、手续费和净额 |
| 单笔业务的完整收益 = 主业务利润 + 附加返点 | 报表须合并呈现，否则低估业务收益 |
| 跨期返点需支持 | 平台可能事后结算，返点日期 ≠ 成单日期 |

**源数据现状**：返点被错误地建成独立 `订单类型=返点` 的 19 笔订单，
且**无 `source_order_id` 字段**，仅 6/19 笔能通过金额匹配到主业务，13 笔归属不明。
这是必须修复的结构性缺陷。

**补录策略（已裁决）**：历史 19 笔**后续人工补录** `source_order_id`。

| 阶段 | 策略 |
|---|---|
| M0–M2 | 19 笔全部标 `link_status=UNLINKED`，`source_order_id=NULL`；R5 报表中归入「未归集」行 |
| M3 起 | 新增返点记录**强制必填** `source_order_id`；每次实际到账新增一笔到账明细 |
| 补录期 | 人工补齐 19 笔，补齐后 R5 自动纳入对应业务 |

> 补录前 R5 报表的「附加返点」列显示 `UNLINKED 1,264.98`，
> **不得摊入任何业务**——宁可显示缺口，不做错误归集。

**返点归属推测**（据备注关键词，仅供参考）：

### 1.2 资金池（可自由创建，数量与类型均不固定）

**`pools` 是主数据表。系统不假设池的数量与类型，新增池无需改代码。**

当前两个池是**种子数据**，不是硬编码约束：

| 池 | 源数据名称 | `pool_type` | `ownership` | 用途 |
|---|---|---|---|---|
| 投资款荷包 | 「投资款荷包（本金）」「小荷包」「经营池」 | `INVEST` | `OWNED` | 买号、付同行 |
| 利润荷包 | 「利润荷包（利润）」「利润池」 | `PROFIT` | `OWNED` | 发提成、抵运营消耗 |

#### 池的两个分类维度

| 维度 | 取值 | 作用 |
|---|---|---|
| `pool_type` | `INVEST` / `PROFIT` / `OTHER` | 业务用途分类，可扩展 |
| `ownership` | `OWNED` / `CUSTODY` / `THIRD_PART` | **资金归属，决定是否计入权益** |

`ownership` 是关键：

| 值 | 含义 | 现金头寸 | 权益 |
|---|---|---|---|
| `OWNED` | 自有（工作室的钱） | ✅ 计入 | ✅ 计入 |
| `CUSTODY` | 代管（客户/同行暂存） | ✅ 计入 | ❌ **不计入** |
| `THIRD_PART` | 第三方（平台保证金） | ✅ 计入 | ❌ **不计入** |

> **实测验证**：新增「代客保管池 5,000」+「平台保证金 2,000」后——
> 现金头寸 45,331.53 → 52,331.53（正确纳入），
> 权益 −54,668.47 **纹丝不动**（正确隔离）。
>
> 没有 `ownership` 维度的话，代管资金会被误算成自有，权益虚高。

| 规则 | 说明 |
|---|---|
| **可创建** | 新增池只需在 `pools` 建一行，无需改代码 |
| **可改名/停用** | `status` 字段控制，停用后禁止新增流水 |
| **不可删除** | 有流水的池只能停用，不能物理删除（保住历史归属） |
| **池余额是算出来的** | 由该池的流水汇总得出，不单独存字段 |

> **命名混乱须治理**：源数据里同一个池有 4 种叫法（投资款荷包/小荷包/经营池/本金池）。
> 系统内统一用 `code`（如 `HJ_INVEST` / `HJ_PROFIT`）标识，显示名可改，`code` 不可改。

### 1.3 业务类型（可自由新增，与资金池解耦）

**业务与池是两个独立维度，不写死绑定。**

- **业务**回答「做什么」——回收 / 提号 / 代挂 / 代分期，也可新增
- **池**回答「钱在哪」——投资款荷包 / 利润荷包，也可新增

#### 关系是多对多

```
        order_type_pools
业务 ────────────────────► 池
 TB ──┬── PRINCIPAL ──► 投资款池
      └── PROFIT────► 代客保管池│
           HS ──┬── PRINCIPAL ──► 投资款池
               └── PROFIT ──► 利润池
                    TB2 ──────────► 代客保管池   （TB2 与 TB 共用池）
```

| 关系 | 例子 |
|---|---|
| 一个业务 → 多个池 | 「同行代收」本金走投资款池、利润走代客保管池 |
| 多个业务 → 一个池 | 「同行代收」与「同行挂单」都用代客保管池 |
| 显式覆盖 | 这一单特殊，指定走别的池 |

#### 路由优先级

```
显式指定（order_events.pool_id） > 业务默认路由（order_type_pools） > 报错
```

#### 业务可自由新增

新增业务只需在 `order_type_defs` 建一行，**不改代码、不改表**：

| 场景 | 做法 |
|---|---|
| 新增业务「同行代收」 | `create_order_type(db, "TB", "同行代收", "STOCK")` |
| 配置其资金路由 | `link_order_type_pool(db, "TB", "PROFIT", "HJ_CUSTODY")` |
| 停用某业务 | `is_active=False`，历史订单保留 |

> **实测验证**：新增 `TB`（同行代收）与 `TB2`（同行挂单）两个业务，
> 关联到新建的「代客保管池」，与 `HS/TH/DG/DFQ` 四个原有业务完全并存，
> 恒等式不受影响（① 45,331.53 ④ −54,668.47 均 PASS）。

## 2. 领域模型（三大板块）

### 2.0 订单类型定义（主理人口述，术语唯一事实源）

**四种主业务的资金性质完全不同，模型必须区分；返点是附加收入而非订单。** v1.0 把它们一律当「订单」处理，是资金模型失真的根源。

| 订单类型 | 业务定义 | 资金性质 | 是否占库存 | 本金字段语义 |
|---|---|---|---|---|
| **回收** | 客户把号卖给我 | **库存型** | ✅ 占用 | 买号成本 |
| **提号** | 买家找我买号，我去同行那里提号卖给他 | **库存型（PICKUP）** | ✅ 有提号实体；不计自营资产 | 付同行的钱 |
| **代挂** | 客户让我帮忙卖他的号 | **零本金型** | ❌ 号不是我的 | 恒为 0 |
| **代分期** | 分销分期服务 | **历史分类** | 按合约登记收款和交付 | 按实际登记付款 |
| **返点** | 交易完了平台给我的返利 | **纯利润型** | ❌ | 返点基数（非资金流出） |

#### 各类型的资金流转

```
回收：      经营池 ──买号──► 库存 ──卖出──► 经营池      【占用资金，有跌价风险】
提号：      经营池 ──付同行──► 同行 ──交买家──► 经营池    【PICKUP 实体；不计自营资产，买家回款前暂占可动用现金】
代挂：      客户号 ──我代卖──► 买家                        【零本金，只收服务费】
代分期：    按实际登记付款 ──► 分期收款 ──► 按合约交付【历史流程以现行规则为准】
返点：      平台 ──返利──► 利润池【附加收入，非独立业务】
```

#### 关键分类：自营库存资产占用只算「STOCK 回收 + CREDIT 代分期」；提号实体单列

真实数据核算（2026-07 ~ 10-03）：

| 业务性质 | 类型 | 金额 | 是否计入库存占用 | 是否暂占可动用现金 |
|---|---|---:|---|---|
| **库存型** | `HS` 回收·买号 | 71,305.41 | ✅ 计 | ✅，直至售出回款 |
| **提号库存型** | `TH` 提号·付同行 | 85,985.00 | ❌ **不计自营资产**（PICKUP 单列） | ✅，从付同行至买家回款/取消退款 |
| **历史分类** | `DFQ` 代分期·历史支出 | 2,907.00 | ✅ 计（+账期风险） | ✅，直至分期收回 |
| 账号附加成本 | 代分期介绍费/作图 | 130.88 | ✅，关联账号未售时计入库存成本；售出时结转订单成本 | ✅，已实际支出 |
| **合计** | | **160,328.29** | **历史库存占用上限 74,212.41** | 以未核销余额实时计算 |

> **注意**：提号资金 85,985.00 **不得计入自营库存占用**，否则库存资产会被高估 86,115.88；但每笔 `BUY` 后至对应 `SELL`/`CANCEL` 完成前，仍会减少可动用现金，必须在资金池页显示。
> 提号业务逐笔即时对冲（实测：8/11 付同行 16,688 → 同日收回 16,688；8/20 付 6,000 → 同日收回 6,000），
> 钱只是过一道手，不形成库存资产。

#### 修正后的恒等式②

```
② 已关联库存占用 = Σ(accounts.cost_amount WHERE account.status IN ('在库','分期中')
                       AND 已关联订单.link_status='LINKED')

历史库存占用上限 = Σ(BUY + COST WHERE capital_type IN ('STOCK','CREDIT'))
                 − 已可靠识别的售出成本
                 ≈ 74,212.41（历史参考值，非实时库存）
```

**提号资金未回收（资金池指标，不是自营库存）**：

```
提号已付款未核销 = Σ(TH.BUY.amount 未被 SELL/CANCEL 的 offset_event_id 核销)
```

> 该指标回答“此刻有多少钱已付同行、尚未收到买家回款”。买家先付款时可先记录 `SELL`，指标为 0；同行先收款时则为正数。历史数据缺少可靠的 `offset_event_id` 时显示“不可算”，不得假设为 0。

### 2.1 订单板块

**核心原则：一个真实业务动作 = 一条 `order_events` 记录。** 从模型层面消灭 WPS 的双计问题。

**事实源优先级（强制）**：`order_events` 是业务动作事实源，`cashflow` 是由有资金影响的事件派生的资金事实源；二者以 `order_event_id` 一对一关联，禁止对同一业务动作分别手工录入。`orders.principal` / `orders.profit` / `orders.gross_amount` 均为系统从事件和分期收款汇总的派生字段，不可手工覆盖。`COST`、`PAYMENT`、返点结算写入后必须在同一事务重算订单利润、已收金额与剩余应收。

#### 表结构

| 表 | 作用 | 关键字段 |
|---|---|---|
| `orders` | 订单主表，**只存汇总** | id / **order_no(带业务前缀的业务单号)** / **order_type(引用 `order_type_defs`，首批 HS/TH/DG/DFQ)** / **capital_type** / account_id / **link_status** / owner_id / trade_date / gross_amount / status |
| ↳ 回款池归属 | — | **不在订单上**，记在 `order_events.pool_id`（池可自由创建，订单层写死会无法扩展） |
| `order_events` | 动作事件流（核心） | id / **event_no** / order_id / event_type / amount / **portion(PRINCIPAL/PROFIT/GROSS)** / occurred_on / **pool_id** / counterparty / **offset_event_id** |
| `accounts` | 在途账号 | id / **inventory_no(ACC库存编号)** / **game_account(唯一, 可空)** / game_type / game_password / channel_region / bound_phone / has_secondary / platform / business_mode / inventory_type / buy_date / cost_amount / status / account_description / account_images / note |
| `customers` | 客户主数据 | id / **customer_no** / display_name / contact_name / phone / wechat / qq / source / owner_id / status / tags / note；联系方式不作为唯一键，修改留审计 |
| `order_customer_roles` | 订单—客户参与关系 | id / order_id / customer_id / **role(SELLER/BUYER/CONSIGNOR/INSTALLMENT_CUSTOMER)**；同一客户可在不同订单担任不同角色 |
| `counterparties` | 合作方主数据 | id / **counterparty_no** / display_name / type(PEER/SUPPLIER/PLATFORM) / contact_name / phone / wechat / qq / status / note；同行、供货方、平台不归入客户 |
| `order_counterparty_roles` | 订单—合作方参与关系 | id / order_id / counterparty_id / **role(PEER/SUPPLIER/PLATFORM)**；TH 同行、DFQ 供货方等从此关联 |
| `installments` | 分期合约（`HS` 分期出售或 `DFQ` 代分期的订单从表） | id / **inst_no** / **order_id(唯一 FK，新数据必填)** / **contract_type(STOCK_SALE/ADVANCE_PURCHASE)** / principal / down_payment / periods / paid / status / next_pay_date / **rebind_date**；账号信息从所属订单取得 |

| `rebate_records` | 返点记录（主业务从表） | id / **rebate_no** / source_order_id / channel / rebate_type / rate / base_amount / link_status |
| `rebate_settlements` | 返点结算明细 | id / **settlement_no** / rebate_record_id / settled_on / gross_amount / platform_fee / net_amount / pool_id / cashflow_id |

#### 分期出售、代分期与分期合约（一对一从属）

`installments` 不是独立业务，不能脱离 `HS` 分期出售订单或 `DFQ` 代分期订单存在。关系固定为：

```
HS 分期出售订单（orders） 1 ─── 1 分期合约（installments） ─── 1 库存账号（accounts）
DFQ 代分期订单（orders） 1 ─── 1 分期合约（installments） ─── 订单账号文本快照（account_snapshot）
                                          │
                                          └── N 期次计划（installment_schedules）
```

| 规则 | 说明 |
|---|---|
| 创建 | 新建 `DFQ` 时必须同一提交创建合约；`HS` 仅在“分期出售”时创建合约。未填期数、首付、每期金额、首期应付日、合约总应收不得提交 |
| 合约类型 | `ADVANCE_PURCHASE` 仅对应 `DFQ`；`STOCK_SALE` 仅对应已买入且在库的 `HS` 订单。类型、订单业务和账号来源不一致时阻断提交 |
| 唯一性 | 一个订单至多关联一份分期合约；除 `HS` 分期出售和 `DFQ` 外，其他订单不得关联分期合约 |
| 账号关联 | 合约必须关联所属订单；HS 通过订单取得已在库账号，DFQ 订单本身不关联库存账号。签约后转“分期中”，**仅结清且完成换绑/交付后**转“已售” |
| 生命周期 | DFQ：`BUY` → 签约 → `PAYMENT` → 结清 → 换绑 → `DELIVER`；HS 分期出售：库存 `HS` → 签约 → `PAYMENT` → 结清 → 换绑/交付 → `DELIVER`。`PAYMENT` 是唯一分期收款事实，`DELIVER` 无金额、无现金流，只释放库存并记录交付。`next_pay_date` 逾期未补款自动预警并转“断分期” |
| 金额勾稽 | `总应收 = 首付 + 期数 × 每期金额`；`剩余应收 = 总应收 − paid`；每笔 `PAYMENT` 必须同步增加 `paid`，累计不得超过总应收 |
| 断分期处置 | 转“断分期”时必须记录账号控制权、已收款处理方式、后续催收/收回/转售方案；未完成处置前不得将订单标为已售或将剩余应收视为已实现利润 |
| 历史数据 | 历史分期按标准导入规则处理；新数据不保存独立 `account_id`，不得通过账号文本反推订单 |

#### 事件类型（7 种，封闭枚举）

| event_type | 触发时机 | 资金方向 | 产生差价 | 计入库存 | 适用类型 |
|---|---|---|---|---|---|
| `BUY` 买号 | 动用投资款池买号/付同行 | 池 − amount | 否 | ✅ | `HS` `DFQ` `TH` |
| `COST` 账号/订单附加成本 | 买号后发生的介绍费、作图费等；HS 归集到库存账号，DFQ 归集到订单 | 池 − amount | 否 | ✅（未售时增加成本） | `HS` `DFQ` |
| `SELL` 售出 | 号卖出并回款 | 池 + amount | 是 | 释放 | `HS` `DFQ` `TH` `DG` |
| `PAYMENT` 分期收款 | 客户支付首付或某一期款项 | 池 + amount | 是（仅已实现收款） | ❌ | `HS`（仅分期出售）`DFQ` |
| `DELIVER` 分期交付 | 合约结清后的换绑或账号交付 | 无现金流 | 否 | 释放 | `HS`（仅分期出售）`DFQ` |
| `TRANSFER` 划转 | 跨池或同池账户划转 | 跨池改变各池余额、同池不改变池余额；均不影响合并现金和损益 | 否 | ❌ | 全部 |
| `CANCEL` 撤销 | 提号取消/买家违约 | 池 + amount | 反向调整 | 释放 | `TH` `DFQ` |

> 提号的 `BUY` 与 `SELL` 按普通库存订单处理，不要求互相引用；`offset_event_id` 仅用于事件冲销。
> 成对冲销时自动核销，避免时点错配导致库存虚增。
> 真实案例：8/29 付同行 5,520 → 8/30「提号取消」收回 5,520。

> **新增 `CANCEL`**：实测存在「提号取消 5,520」这类业务，原 4 型事件无法表达。

#### 订单类型与事件组合

| order_type | capital_type | 事件组合 | 库存占用 | 利润 |
|---|---|---|---|---|
| 回收 `HS` | `STOCK` 库存型 | 现款：BUY + COST（如有）+ SELL；**分期出售：BUY + COST + 唯一 STOCK_SALE 合约 + PAYMENT（多次）+ 结清后 DELIVER** | ✅ 占用并释放 | 已收款−买号成本−账号附加成本（未收款不计已实现利润） |
| 提号 `TH` | `STOCK` 提号库存型 | BUY + SELL | ✅ PICKUP（不计自营资产） | 买家价 − 同行价 |
| 代挂 `DG` | `ZERO` 零本金型 | SELL | ❌ | 成交额×抽成 |
| 代分期 `DFQ` | `CREDIT` 历史分类 | BUY + COST（如有）+ PAYMENT（多次）+ **唯一 ADVANCE_PURCHASE 合约** + 换绑完成后 DELIVER | ✅ 占用+账期 | 已收分期款−历史支出−账号附加成本 |
| ~~返点~~ | — | **不是独立业务**，见 `rebate_records` + `rebate_settlements` 附属表 | ❌ | 附加在主业务上 |

#### 账号状态机

```
在库 ──SELL（HS）──► 已售
 │
 ├── 签 HS 分期出售 / DFQ 代分期合约 ──► 分期中 ──结清+换绑+DELIVER──► 已售
 └── 撤单/退货 ──► 已退
```

**入库硬约束**：账号入库（`BUY`）后 7 日内未被任何 `SELL` 事件引用，进「呆滞库存」告警。

#### 设计对策

**① 全部实体自建业务编号（纯顺序号，不含日期；主业务按类型独立编号）**

| 表 | 编号字段 | 格式 | 示例 |
|---|---|---|---|

| `orders`·提号 | `order_no` | `TH` + 4位序号 | `TH0001` |
| `orders`·代挂 | `order_no` | `DG` + 4位序号 | `DG0001` |
| `orders`·代分期 | `order_no` | `DFQ` + 4位序号 | `DFQ0001` |
| `order_events` | `event_no` | 订单号 + `-EV-` + 动作 + 2位流水 | `HS0001-EV-BUY-01` |
| `rebate_records` | `rebate_no` | 来源订单号 + `-RB` + 2位流水；必须关联 `source_order_id` | `HS0001-RB01` |
| `rebate_settlements` | `settlement_no` | 返点单号 + `-CF-` + 2位到账流水 | `HS0001-RB01-CF-01` |
| `accounts` | `inventory_no` | `ACC` + 4位序号 | `ACC0001` |
| `customers` | `customer_no` | `CUS` + 4位序号 | `CUS0001` |
| `counterparties` | `counterparty_no` | `CP` + 4位序号 | `CP0001` |
| `installments` | `inst_no` | 订单号 + `-INS01` | `HS0001-INS01` |
| `cashflow` | `flow_no` | 订单号 + 资金类型 + 流水 | `HS0001-CF-BUY-01` |
| `pools` | `code` | 大写英文 | `HJ_INVEST` |

**编号规则**：
- 纯顺序号，**不含日期**；`HS` / `TH` / `DG` / `DFQ` **分别递增**，均不按天重置。不同业务允许拥有相同数字部分，如 `HS0028` 与 `TH0028`
- `CUS`、`CP` 由各自独立序列在首次保存成功时分配；创建后不可修改、不可复用。客户联系方式仅作重复提示，不作为唯一键；管理员合并时保留目标客户号，来源客户标记 `MERGED` 并保留审计。
- 返点记录使用订单从属号：`HS0001-RB01`、`HS0001-RB02`；每次到账生成到账编号，如 `HS0001-RB01-CF-01`、`HS0001-RB01-CF-02`。
- 订单资金按资金类型独立递增：买号款 `HS0001-CF-BUY-01`、中介费 `HS0001-CF-FEE-01`、作图费 `HS0001-CF-DESIGN-01`、其他成本 `HS0001-CF-OTHER-01`、卖号回款 `HS0001-CF-SELL-01`。
- 统一 4 位（上限 9999），**超出即报错，禁止静默进位**
- 同一编号域内必须唯一，创建后**永不修改、永不复用**；业务编号用于人工沟通、检索和审计，不替代数据库主键
- 数据库自增 `id` 仅作内部外键，不对外暴露、不参与业务关联

> 排序与检索靠 `trade_date` / `occurred_on` 字段，不靠编号。
> 编号只保证唯一与可读，不承担时间语义。

**② 账号用双重标识**

| 标识 | 字段 | 用途 |
|---|---|---|
| 业务编号 | `inventory_no` | 对外引用、人工沟通；即 ACC 库存编号 |
| 账号号 | `game_account`（QQ号等） | 与平台对接、查重唯一键 |

> `game_account` 建唯一索引，但**允许为空**（未取得账号号时先挂单）。
> `绑定手机号` 不作唯一键——实测 32 条只有 11 个不同值。

**③ 历史孤儿数据处理（强制）**

| 情形 | 处理 |
|---|---|
| 89 单无 `account_id` | **不回填**。订单 `account_id` 允许 NULL，标 `link_status=UNLINKED`；账号字段仅是订单对库存账号的关系 |
| 关联失败的旧单 | 报表中归入「不可算」区，**不参与**库存周转/呆滞统计 |
| 3 笔分期无对应账号 | 保留孤立记录，标 `link_status=ORPHAN`；同时 `order_id=NULL`，不得臆造代分期订单 |

> **原则：宁可标记为不可算，不做不可靠的自动匹配。**
> 现有 `linkage.py` 启发式匹配实测仅中 6/89（准确率 6.7%），
> 错误关联会污染利润与库存数据，比缺关联危害更大。

**④ 迁移期双轨运行**

| 阶段 | 策略 |
|---|---|
| M0–M2 | 新数据强制填 `order_no`；HS/DG/TH 订单按实际库存业务关联已建档的 `account_id`，DFQ 仅保留订单账号文本快照；历史数据按标准导入规则处理 |
| M3 起 | 库存周转、呆滞清单等报表**仅统计 `link_status=LINKED` 的数据** |
| 历史部分 | 报表页脚固定标注「2026-07 前的历史订单无账号关联，不计入周转指标」 |

> **影响**：库存周转天数、呆滞库存等指标**从 M0 之后的新数据开始才有值**。
> 现有 89 单历史订单无法回溯，这是数据事实，不做补造。

### 2.2 资金板块

#### 表结构

| 表 | 作用 | 关键字段 |
|---|---|---|
| `pools` | **资金池主数据（可自由创建）** | id / **code(不可改)** / name / **pool_type** / **ownership(OWNED/CUSTODY/THIRD_PART)** / status / note |
| `order_type_defs` | **业务类型主数据（可自由新增）** | id / **code(不可改)** / name / capital_type(默认，可按单覆盖) / is_active / sort_order |
| `order_type_pools` | **业务↔池 多对多路由** | order_type_id / pool_id / portion(PRINCIPAL/PROFIT/GROSS) |
| `cashflow` | 资金流水（唯一入口） | id / **flow_no** / occurred_on / **pool_id(FK必填)** / **nature** / category / direction / amount / order_id / **transfer_id** / remark |
| `categories` | 类别字典 | code / name / is_operating_cost |

> **每笔流水必须指定 `pool_id`**。这是双池模型的第一约束——无池归属的流水无法核算。

#### 现金流性质标签 `nature`（4 值，必填）

| nature | 含义 | 影响池余额 | 影响损益 | 真实数据示例 |
|---|---|---|---|---|
| `EXTERNAL_IN` 外部注入 | 股本 / 借款 | ✅ | ❌ | 投资款 17,500（7/7） |
| `BUSINESS_IN` 经营流入 | 售出打回 / 返点 | ✅ | 仅差价 | 回收本金 700（7/23） |
| `BUSINESS_OUT` 经营流出 | 买号 / 运营 / 薪资 | ✅ | 仅运营消耗 | 房租水电 4,235.31（7/14） |
| `INTERNAL` 跨池划转 | 源池 → 目标池 | 源池− / 目标池+ | ❌ | 新录入必须成对；历史“八月利润转入”待凭证确认 |

> **`INTERNAL` 是跨池划转机制**：一组划转影响两个池。
> 字段 `transfer_id` 关联成对的两条流水（一条 `INTERNAL_OUT`，一条 `INTERNAL_IN`），
> 保证两池增减对称、可追溯。
>
> **验收硬条件**：`INTERNAL` 流水不得计入「经营损益」，只影响池余额。
> 源数据把「八月利润转入 13,470.42」记成了运营收入，会虚增利润——这是必须堵掉的洞。

#### 池间划转规则

| 方向 | 场景 | 是否允许 |
|---|---|---|
| 利润池 → 投资款池 | 利润补充买号资金 | ✅ 允许（须有 `transfer_id`） |
| 投资款池 → 利润池 | 预支利润发工资 | ⚠️ 需主理人确认 |
| 同池内划转 | 微信↔支付宝 | ✅ 允许（**不影响池余额**，只换账户） |

> **跨池划转**会改变源池和目标池各自余额，但不改变合并现金头寸或经营损益；**同池内换账户**（微信/支付宝/银行卡之间）才不改变池余额。

### 2.2.1 资金池页面（P0）

**资金池页面必须将「收入」「支出」「押金」明确分开显示，不能只给一个余额。**
用户进入任一资金池，第一屏应看清楚本期进了多少钱、出了多少钱、多少资金被押金占用，以及还可自由使用多少钱。

| 页面区块 | 展示口径 | 说明 |
|---|---|---|
| 当前余额 | 该池全部现金流水净额 | 现金实际在该池中的余额，含代管/第三方池的现金头寸 |
| 本期收入 | `EXTERNAL_IN` + `BUSINESS_IN` 中 `direction=收入` | 分组展示：投资注入、订单回款、返点、运营退款等 |
| 本期支出 | `BUSINESS_OUT` 中 `direction=支出`，**不含可退押金** | 分组展示：买号/付同行、薪资、房租日用、办公用品、运营等 |
| 押金占用 | `DEPOSIT` 类资金的未退余额 | 独立显示，不混入运营支出；展示已缴、已退、未退、到期日与对手方 |
| 提号已付款未核销 | 已付同行、尚未被同单 `SELL`/`CANCEL` 核销的 `TH.BUY` | 独立风险提示；不计入库存，但已通过现金流减少可动用余额 |
| 可动用余额 | 当前余额 − 押金占用 | 仅适用于 `ownership=OWNED` 的池；是可直接用于买号/运营的金额 |

#### 押金的双口径（强制）

| 押金类型 | 资金池页面归类 | 是否计入经营损益 | 录入规则 |
|---|---|---|---|
| 可退押金（平台保证金、租赁押金等） | **押金占用** | ❌ 不计入 | `category=押金`，记录 `deposit_status=HELD/RETURNED`、对手方、缴纳/预计退回日期；资金可位于 `THIRD_PART` 池 |
| 不可退费用（平台认证费、服务费等） | **支出 → 运营** | ✅ 计入 | `category=运营`，不得标为押金 |
| 押金退回 | **押金占用减少 + 收入明细** | ❌ 不形成利润 | 与原押金记录关联，不得当作业务收入或运营收入 |

> **页面交互规则**：收入、支出、押金三张明细表均可按日期、资金池、类别、对手方、订单号筛选；点击汇总数字进入对应明细。池间划转单独显示「划转」标签，不计入收入或支出汇总。

> **押金现金流规则**：缴纳可退押金记 `BUSINESS_OUT + category=押金`，退回记 `BUSINESS_IN + category=押金退回`；两者均排除运营消耗和业务利润。`deposits` 记录押金权利状态，`cashflow` 记录实际收付，两者必须关联；一笔押金允许多次部分退回。

> **数据模型补充**：新增 `deposits` 表（pool_id / counterparty / paid_amount / returned_amount / status / paid_on / expected_return_on / returned_on / linked_cashflow_id / remark）。押金不单独生成业务编号；押金流水必须关联一条 `deposits` 记录，防止“已退押金”仍占用可动用余额。

#### 配置与历史保护规则

- 字段 `field_key` 创建后不可修改、同一 `entity_type` 内唯一；显示名可修改。
- 有历史值的字段只能停用，不能物理删除；停用后历史页面仍展示，新增记录不再显示。
- `is_required` 只对启用后的新记录生效，不能让历史数据因新增必填字段而失效。
- 活字段按 `applicable_order_types` 控制显示。例如“同行名称”仅在 `TH` 显示，“换绑承诺日”仅在 `DFQ` 显示。
- 活字段值版本随实体保留；导出、筛选和详情页均须支持，默认不进入财务报表计算。

## 3. 核算口径与恒等式（验收标准）

**以下恒等式为系统正确性的硬标准，任何一条不成立即为缺陷。**
双池模型下，①②须**分池计算**，③是全池合并口径。

### 3.1 恒等式①：单池余额

```
池余额(pool) = Σ(该池 EXTERNAL_IN) + Σ(该池 BUSINESS_IN)
             − Σ(该池 BUSINESS_OUT) + INTERNAL 净流入

两个池合并（= 全现金头寸）：
   = 100,000.00 + 131,260.12 + 18,324.42 − 160,328.29 − 43,924.72
   = 45,331.53
```

**已实测通过（差 0.00）**。实现后须能分别输出两个池的独立余额。

### 3.2 恒等式②：库存占用

```
② 已关联库存占用 = Σ(accounts.cost_amount WHERE status IN ('在库','分期中')
                       AND 已关联订单.link_status='LINKED')

历史库存占用上限 = 74,212.41（历史买号及支出现金流口径；含未关联历史记录，
                         不得作为实时库存或周转指标）
   ⚠️ 不含提号 PICKUP 资产 85,985.00（单列，不计自营库存）
```

### 3.3 恒等式③：经营损益（全池合并）

```
③ 经营损益 = Σ四类业务利润 + Σ返点 − Σ运营消耗
            = 33,820.05 + 1,264.98 − 43,924.72
            = −8,839.69
   ⚠️ 须排除 INTERNAL 划转（八月利润转入 13,470.42 不是收入）
```

> **账号附加成本修正**：源数据把「同行代分期介绍费 106.00」与「作图费用 24.88」错放在
> 「账号回收」类别。这 130.88 不是运营支出，而是买号后的附加成本，应关联具体 `HS`/`DFQ`
> 订单并通过 `COST` 事件结转；HS 同步归集到库存账号，DFQ 不创建库存账号。故经营损益维持
> **−8,839.69**；HS 账号尚未售出时成本留在库存，售出后减少对应订单利润；DFQ 直接减少对应订单利润。历史两笔尚未可靠关联账号前，标 `UNLINKED`，不擅自分摊。

### 3.4 恒等式④：权益

```
④ 权益 = **自有池**余额合计 − 股本
        = 45,331.53 − 100,000.00
        = −54,668.47
   ⚠️ 只算 ownership=OWNED 的池；代管资金不计入权益
```

### 3.5 恒等式⑤：双池划转对称性（双池专属）

```
⑤ Σ(INTERNAL_OUT) = Σ(INTERNAL_IN)   按transfer_id 逐对相等
   新录入划转必须逐对相等；历史 9/16「八月利润转入 13,470.42」在补齐原始凭证前标 `UNLINKED_TRANSFER`
```

> **新录入**的任何一条 `INTERNAL` 流水不成对即拒绝入库；历史单边记录保留为数据缺陷并显示在异常工作台，不能自动补造另一侧。

### 3.6 恒等式之间的勾稽关系

```
① = 股本 + ③ + 划转影响
   验证：100,000.00 + (−8,839.69) = 91,160.31
   差额 45,828.78 来自库存沉淀与池内划转

② 库存占用 → 资产层
   在库账号 10 个，占用本金 41,547.83（台账口径，与② 差 12,479.66，因台账漏登记部分买号）
```

### 3.7 历史参考映射：源数据 → 双池模型

> 本表只规定导入资料进入参考区时的归类方式，不是新业务录入的字段来源；新单必须按第 1、2 章和功能规格直接录入。

| 源数据「类别」 | 目标 `nature` | 目标 `pool_id` |
|---|---|---|
| 投资款 | `EXTERNAL_IN` | 投资款荷包 |

| 八月利润转入 | `UNLINKED_TRANSFER`（历史异常） | 暂挂投资款荷包；补齐原始凭证并确认方向后才生成成对 `INTERNAL` |

## 7. 技术方案

### 6.1 选型

| 层 | 选型 | 理由 |

| 后端 | FastAPI + SQLAlchemy 2.0 | 现有代码已用，不引入新栈 |
