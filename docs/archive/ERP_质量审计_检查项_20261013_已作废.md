## 3. 事务一致性 — 达标 ✅

写路径纪律正确：**Service 只 `flush()`，提交统一在 `get_db` 请求边界**（`core/database.py:98-114`：yield 后 `commit()`，异常 `rollback()`）。多步操作同事务：
- 建单 + 客户/合作方角色 + 审计（`orders/service.py:create_order`）
- 登记：事件 + 现金流 + 账号影响 + 审计（`post_event`）
- 跨池划转：成对 `INTERNAL` 流水同 `transfer_id`（`transfer`）

要么全可见、要么全消失。当前 services 未见中途 `commit()`（grep 以 `flush` 为主）。

**风险**：若未来某路由/脚本中途 `db.commit()`，会破坏原子性。须在评审中固化“Service 内禁止 commit”纪律。SQLite 单文件由单一写锁串行化，高并发写会阻塞——当前团队规模（个位数到十几人）可接受。

## 附：审计期间发现的真实缺陷（已修复 ✅）

**`test_audit_contract.py::test_query_filters_and_pagination` 失败（495 通过 / 1 失败 → 已修复转绿）**
- 现象：审计日志按日期过滤返回 0（预期 ≥2）。
- 根因：`AuditLog.occurred_at` 默认 `server_default=func.now()`（**UTC 存储**，`core/audit.py` 不设值），而 `audit/router.py:48-51` 用**本地日期边界**（`datetime.combine(from_date, min/max.time())`）比较。本地凌晨运行时，记录落在 UTC“昨天”，按本地“今天”过滤被排除。
- 影响：所有审计日志日期范围查询在本地早晨会漏掉“当日”记录；该测试在本地早晨必红、傍晚才绿（**非确定性**）。
- 修复方向：统一时区——要么存储/过滤都用 UTC（`from_date`/`to_date` 先转 UTC），要么入库时写本地时间并明确无时区语义；同时让测试用“相对今天”的 UTC 窗口，消除时间依赖。

**关键工程陷阱与处理（已实踩并解决）**

2. **CHECK 命名约定双前缀**：`NAMING_CONVENTION` 的 `ck: ck_%(table_name)s_%(constraint_name)s` 会把 `ck_<表>_xxx` 再拼一次 → `ck_<表>_ck_<表>_xxx`。约束名改为纯后缀（`cost_nonneg`/`rate_nonneg`/`amount_nonneg`），由约定补出干净 `ck_<表>_<后缀>`，ORM 与迁移一致。
3. **幂等**：每个 `create` 先查存在性，已在“干净 0007”或“部分 0008 残留”两种状态下都能安全重跑（生产库此前已残留一个孤儿 `ix_orders_trade_date`，幂等跳过未报错）。

**附：历史遗留的 FK 命名漂移——已于 0009 修复闭环**
- 根因：ECS 库早期迁移（0001–0005）用 `op.create_table` 建表未套 `NAMING_CONVENTION`，FK 落到磁盘为**未命名**；ORM 经约定生成命名 FK（`fk_<表>_<列>`），导致 `alembic check`（尤其 prod 的 SQLAlchemy 2.0.35，FK 名经 `PRAGMA` 反射恒为 NULL）报漂移。SQLite 不存 FK 名、完整性照常生效，原属功能性无害。
- 修复（迁移 `0009_rename_fks_to_named`，2026-10-13 提交 `1f1092c` + 部署）：用 ORM 元数据编译 CREATE TABLE（命名约束正确）→ 建 `_new_` 临时表 → 拷数据 → 删旧表 → 改名 → 在最终表名上重建命名索引（索引必须放 RENAME 之后，否则 `IF NOT EXISTS` 因全局同名索引已存在而静默跳过、被 DROP 旧表带走）。
- 实测：ECS 副本（2.0.35）与本地（2.1.1）均 `alembic check` **零漂移**；ECS 生产库升级后 `alembic check` 零漂移、数据零丢失（12 张业务表升级前本就为空，非重建清空；`pools`/`audit_logs` 等非重建表行数与升级前备份一致）、无 `_new_`/`_alembic_tmp_` 脏表、health OK。

**待办（非代码）**：建议把“改 CHECK/枚举必须重建含该枚举的表 + `alembic check` 双检”写入升级纪律。

**附：金额列 float 存储风险（审计第 2 项提及的残留项）——已评估，结论：非实质风险，不改**
- 现状：`core/money.Amount` 写入时 `Decimal→float` 落 SQLite REAL（`money.py:93-96`），列声明虽为 `NUMERIC(18,2)` 实际以 REAL 存储；读出时 `Decimal(str(float))` 量化回 2 位（`money.py:98-101`）。
- 评估方法（只读）：① 本地生产库 `order_events.amount`（186 行真实数据）SQL 浮点 `SUM=565169.34` 与 Python `Decimal` 求和 **diff=0.00**；② 合成压力测试 2 万行随机 2 位小数 / 1 万行 0.01，SQL 浮点 `SUM` 与 `Decimal` 求和 **diff=0.00**。
- 结论：IEEE double 相对误差 ~1e-16，对“2 位小数、量级 < 1e4”的货币求和，绝对误差远低于半分；加上读出即量化到 2 位的设计兜底，**任何现实业务量级下 float 存储不漂出 1 分**。单值读写亦无损（靠量化）。
- 风险边界：安全性依赖“所有写路径经 `to_money` 量化到 2 位”与“读出经 `Decimal(str(float))` 量化”。若有人绕过 `to_money` 写入非 2 位值，漂移才可能出现。
- 处置建议：**不做 float→DECIMAL/整数分 存储改造**（属高影响 DDL 重构，全列/绑定/契约/测试连锁，零可测收益）；维持现有设计，并将“所有金额写路径必须过 `to_money`”纳入纪律。
- 低成本保险（已落地）：新增 `tests/v1/test_money_float_guard.py`——2 万行合成 2 位小数金额断言 SQL 浮点 `SUM == Decimal SUM`、单值 `Decimal→float→Decimal` 往返无损；一旦有人绕过 `to_money` 或破坏 `Amount` 浮点往返，此处先红。`pytest tests/v1` 500 通过（原 498 + 2）。
