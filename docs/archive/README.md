## 文档升级

1. 现行文档使用稳定文件名，首次发布文档时版本列填写 `V1.0`，在「变更说明」列标记「发布版」。升级以现行正文为基础，更新版本记录中的日期和主要变更。
2. 同一文档一天只记录一个版本。同日继续修改时补充当天的变更说明。下一天有新变更时递增次版本号。整理历史记录时按日期从 V1.0 连续编号，每天保留当天的重要变更。
3. 需要保留被替代版本时，将旧版原件存入对应归档目录，文件名使用 `文件名_V主版本.次版本（已废弃）.md`。同一文档同一天保留最后一版原件，中间稿通过 Git 历史追溯。
4. 审查、测试和 UX 证据按原记录的日期与批次保存，使用 `（历史留存）` 标记。原件载有版本时保留原版本号。归档前核对标题、版本和文件内容，成组保留报告及附件，同名时使用独立档案路径。

开发、验收和发布分别使用现行文档与本次运行证据。ERP 实际发布版本、组件版本和数据库迁移编号由[版本管理](../版本管理.md)按发布记录，发布全量测试按运行批次留存。 [文档目录](../README.md) · [测试流程](../测试流程.md)

## 本地自动归档

- 日常报告生成成功后，旧日期的 Markdown 和 JSON 一并移入 `test-reports/local/`，以 `测试报告_YYYYMMDD（历史留存）` 命名。同名批次放入独立子目录。
- 执行流水裁剪出的 gzip 文件放在 `test-results/local/`，按 `执行记录_YYYYMMDD-HHMMSS（历史留存）.jsonl.gz` 命名。
- 以上两个 `local/` 目录由 Git 忽略。发布前全量测试报告由发布通道按运行批次保存，路径见[测试流程](../测试流程.md)。
