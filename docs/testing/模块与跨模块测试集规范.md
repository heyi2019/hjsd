# 模块与跨模块测试集规范

> 生效日期：2026-11-03｜适用：宜游轩 ERP 测试体系（后端 pytest / 前端 vitest / CI）
> 关联：《测试编号设计规范》《功能编号注册表.csv》《测试用例库.csv》《测试报告.md》
> 依据：Codex 补充指令（模块级 + 跨模块级测试管理能力）

---

## 1. 三个测试层级 + 两种测试范围

### 测试层级（与用例编号前缀一致）
- **UT**：单元测试（不碰数据库/HTTP，纯函数/规则/组件逻辑）。
- **IT**：集成测试（真实 PG 隔离库，验证 API↔Service↔DB 协作；前端组件测试归此）。
- **E2E**：端到端测试（真实浏览器 + 真实后端 + ephemeral 库的完整用户链路；
  `frontend/e2e` 下 15 个 Playwright 规格，库 `heijin_erp_e2e` 每轮重建）。

### 测试范围（对用例的组织方式，不是第四种层级）
- **模块内测试**：验证单个模块（A–F/SYS）内部的功能与业务规则。
- **跨模块测试**：验证多个模块之间的业务流程、数据流转与一致性。

> 关键澄清：**跨模块不是 MT 测试类型**。跨模块用例仍是 IT/E2E，仅额外打「跨模块」标记并关联多个业务模块。

## 3. 跨模块流程编号（FLOW-*）

跨模块业务流程单独建立流程编号 `FLOW-001 …`，用于审计与追踪，但**不产生新的测试类型**。

| 流程编号 | 链路 | 覆盖文件 | 说明 |
|---|---|---|---|
| FLOW-002 | B → D（订单 ↔ 资金） | test_flow_sale / test_flow_distribution / test_flow_installment / test_flow_recycle | 售出/分销/分期/回收：订单状态与资金池余额同源一致 |
| FLOW-005 | F → B（配置 ↔ 业务） | test_flow_config_driven | 表单字段 required 驱动建单校验 |

> 其余链路（C→B 客户↔订单、B→E 订单↔经营、D→E 资金↔经营、SYS→A-F 认证↔全模块）
> 由对应模块的 IT 用例覆盖，不单独立 FLOW 文件；报表一致性由 R1-R5 用例承载。

## 4. 模块测试集（每个模块可独立运行）

实现方式：**复用现有 `run_regression.py` 的文件清单机制**（不复制测试文件、不动业务目录）。
文件 → 功能编号 → 模块字母 的映射统一在 `scripts/test_catalog.py`（单一事实源）。

可用命令（`backend/` 下）：
```
python run_regression.py B            # 模块 B 全部后端测试（UT + IT）
python run_regression.py B --type ut  # 模块 B 仅单元测试
python run_regression.py B --backend-only   # 仅后端（不跑前端 vitest）
python run_regression.py ut           # 全部单元测试
python run_regression.py it           # 全部集成测试
python run_regression.py cross        # 跨模块流程（FLOW-*）
python run_regression.py ci           # 全系统回归
```
- 模块档默认同时运行该模块的**前端**相关测试（vitest，best-effort）；加 `--backend-only` 跳过。
- 一个用例可关联多个模块：跨模块文件（FLOW-*）同时计入其跨度涉及的模块。
- 模块测试结果可独立统计（见《测试报告.md》模块 × 层级矩阵）。

## 5. 跨模块测试集（重点审计链路）

审计优先级（优先资金/订单/库存/报表一致性）：
1. C → B：客户与业务订单（客户角色按单判定、关联订单）
2. B → D：订单与资金流转（事件派生流水、池余额同源）
3. B → E：订单与经营统计（R1 库存健康、R5 业务损益）
4. D → E：资金流水与经营报表（资金日报、损益口径一致）
5. F → B：业务配置与实际业务执行（form_field required 驱动建单）
6. SYS → A-F：身份认证与权限控制（X-Dev-User / JWT / 越权 403）

实现：跨模块用例以 `IT` 类型落地（含 API 级 Playwright 预备），不要求全部经浏览器。
当前已建设 FLOW-002（B↔D）、FLOW-005（F↔B）；其余链路由模块 IT 用例覆盖。

## 6. 测试用例库与执行结果（分离管理）

- 用例定义：`docs/testing/测试用例库.csv`（12 核心字段 + 辅助字段），由
  `scripts/gen_test_case_library.py` 从测试代码自动生成，编号稳定、幂等。
- 执行结果：`docs/testing/测试结果库/results.jsonl`（按 `run_id` 追加，历史不覆盖），
  含 测试编号 / Git Commit / 时间环境 / PASS·FAIL·SKIP·ERROR / 实际结果 / 耗时 /
  失败原因 / 证据引用。三层各有写入通道：后端由 `tests/v1/conftest.py` 执行钩子
  自动写入，前端 vitest 与 E2E 分别由 `record_frontend_results.py` /
  `record_e2e_results.py` 转换写入（见 6.1 / 6.2）。
- 关联键：用例库「测试编号」↔ 执行记录「case_no」；conftest 读 `case_index.json`
  （nodeid→测试编号）实现自动关联。
- 报告：`docs/testing/测试报告.md`（模块×层级矩阵、SKIP/ERROR 单列、跨模块覆盖、
  按功能编号查询）；`scripts/make_test_report.py` 聚合生成。

### 6.0 「合格标准」取值规则（禁写"待确认"占位）

`合格标准` 必须是**可核对**的判据，取值按以下优先级自动推导，不靠人工补写：

| 优先级 | 来源 | 产出示例 |
|---|---|---|
| 1 | docstring 中含期望动词的句子 | `取消后余额回到冻结前水平` |
| 2 | `assert x, "消息"` 的断言消息 | `余额不得为负` |
| 3 | 真实断言**机械推导**（后端 `pytest.raises` / `assert`；前端首个 `expect` 链） | `抛出 Validation，消息匹配「已售账号不能新增 COST」`<br>`断言 third.customer_no != first.customer_no`<br>`断言 expect(...).toHaveBeenCalledWith({ mine: true })` |
| 4 | 用例**完全没有显式断言** | `正常执行不抛异常（用例无显式断言）` |

- 第 3 档的推导结果必须能在源文件中逐字找到（可用子串校验批量验证），不得凭空生成。
- 第 4 档不是文档缺失，而是**测试本身薄弱**（只验证不抛异常）；报告单列为
  「弱标准」风险项，建议补断言 —— 不要再退回 `待确认` 占位（它既不提供信息，
  还会把"测试薄弱"伪装成"业务未澄清"）。
- 前端 `it.each([...])("标题", cb)` 有两组括号，回调体取**第二组**括号内的内容，
  否则会取到 `it.each` 的参数列表而非断言。
- 两个已踩过的解析坑，改生成器时必须守住：
  1. **断言消息只能按「顶层逗号」切分**。`assert f(a, "ACTIVE") == x` 的第一个逗号在
     括号内，按「第一个逗号」取会把实参 `ACTIVE` 当成消息（曾产出 54 条只剩一个值的
     合格标准，如 `ACTIVE` / `50.00` / `种子用户2`）。
  2. **跨行括号断言要续行读完整**。`assert (\n  f(...)\n  == expected\n)` 逐行正则只能
     截到半句（曾产出「断言 persisted == len(...), (」和只剩 `(` 的空白标准）。

### 6.1 前端（vitest）执行记录

执行记录器是 **pytest 插件**，只能记后端。前端 vitest 结果需经
`scripts/record_frontend_results.py` 转成同格式记录追加进同一份 `results.jsonl`，
报告侧无需特判。

```bash
# 一条命令：前端四档全量 + 落库（推荐）
backend/.venv/bin/python backend/run_regression.py fe

# 或分两步（CI 里需要保留原始 JSON 时）
cd frontend && npx vitest run --reporter=json --outputFile=/tmp/vitest.json
backend/.venv/bin/python backend/scripts/record_frontend_results.py --json /tmp/vitest.json
```

关联口径与边界：

- 用例键 = `frontend/src/<相对路径>::<it()/test() 标题>`，与 vitest 运行时 `title` 逐字对应。
- `it.each([...])("按字段数量 %s 使用标准宽度 %s")` 在用例库中记**一条模板**（与后端
  `parametrize` 一个函数一条用例同构），运行时展开的多个变体由记录器**按模板通配归并**
  回这一条，同一条内多状态取最差。
- 标题里含引号（如 `空路径 '/' 重定向到工作台`）必须由字符串扫描器读取，不能用
  `["']([^"']+)["']` 之类正则 —— 会在内层引号处截断，导致用例库存半截标题、永远对不上。
- **不指定 `--project`**：模块档跑任意前端文件若写成 `npm run test:fast -- <files>`，
  不属于 fast 清单的文件会被 vitest 直接过滤，表现为「跑了但一条没执行」却 0 退出（假绿）。
- 未命中（`未命中=N`）必须为 0；不为 0 说明用例库标题与源码漂移或测试未收录，需重生成用例库。

### 6.2 E2E（Playwright）执行记录

E2E 同样不在 pytest 插件的覆盖范围内。`playwright.config.ts` 已配 json reporter
（输出 `frontend/test-results/playwright-report.json`），由
`scripts/record_e2e_results.py` 翻成同格式记录追加进同一份 `results.jsonl`。

```bash
cd frontend && npx playwright test          # 产出 json 报告（config 已配）
cd backend && .venv/bin/python scripts/record_e2e_results.py
# 只统计不写入：加 --dry-run
```

关联口径与边界：

- 用例键 = `frontend/e2e/<规格文件名>::<test() 标题>`。Playwright JSON 的 `spec.file`
  是**相对 testDir 的路径**（`modal-footer.spec.ts`），必须补 `frontend/e2e/` 前缀，
  否则 62 条记录全部落空、报告 E2E 行恒为 0。
- `test.describe(...)` / `test.describe.serial(...)` 命中 `test` + `(` 且第一个参数
  就是字符串，扫描时必须按方法名排除，否则每个分组凭空多出一条「用例」。
- 模板标题（``test(`导航可达：${label}`)``）在用例库中记**一条**，运行时展开的多条
  由记录器按通配归并回这一条，与 `it.each` 同构。
- 状态映射：`expected`→PASS、`unexpected`→FAIL、`flaky`→PASS（`reason` 记「重试后
  通过」）、`skipped`→SKIP。flaky 不能记 FAIL —— 否则报告把「不稳定」误报成「一直红」。
- **未命中必须为 0**；新增规格文件要在 `scripts/test_catalog.py` 的 `E2E_FILE_TO_FUNC`
  登记功能编号，未登记会落 `SYS12` 兜底（报告里能看到，不会静默丢失）。

### 6.3 新增用例与「未执行」的因果关系

执行记录写入时用的是**当时**的 `case_index.json`。新写的用例第一次跑时库里还没有它的
编号，`case_no` 只能写成空串——报告若不处理，这批记录就永远归不到编号上，表现为
「明明刚跑过却显示未执行」（实测新增 13 条后报告 `未执行=13`）。

`scripts/make_test_report.py` 因此在报告阶段按 `nodeid → case_index.json` **反查补号**
（报告一定在用例库生成之后运行，索引必然是最新的），无需为此重跑一遍测试。排查顺序：
先看 `results.jsonl` 里该 `nodeid` 是否有记录 → 再看记录里的 `case_no` 是否为空 →
最后确认 `case_index.json` 里有这个 nodeid。

## 7. CI 分层（GitHub Actions）

`backend-gate.yml` 分层策略：
- **PR / test 分支**：`unit` + `cross` + 核心模块（B/C/D）集成测试。
- **main / master 推送**：全系统回归 `ci`（含跨模块）。
- **workflow_dispatch（手动）**：全量回归。

每次 CI 自动生成用例库 + 报告并上传 artifact（30 天留存）。

前端由 `frontend-gate.yml` 独立分档（static-checks / test-layers / frontend-coverage /
test-react-deep）。E2E 由 `e2e-gate.yml` 独立阻塞（PR / main・test 推送 / 手动）：
真实 Chromium + 真实后端 + 独立库 `heijin_erp_e2e`，每次运行重建，绝不触碰
dev/test/release。

注意：`results.jsonl` 是**本地产物（已 gitignore）**，跨工作流汇不起来，
因此 CI artifact 里的《测试报告》**只含后端执行结果**；需要三层全绿覆盖的报告时，
本地先跑 `run_regression.py fe` 与 `record_e2e_results.py`，再跑 `make_test_report.py`。

## 8. 文件管理边界

- 允许：整理测试目录、规范命名、拆分职责混乱文件、提取共享 Fixtures/Mocks/Helpers、
  建立标签与模块映射、调整测试发现配置及 CI、补齐缺失自动化测试。
- 禁止：擅自重构前后端业务目录、擅自修改业务规则、降低原有断言、删除有效测试场景、
  对未经确认的数据执行清空/重置、擅自推送/合并/部署。

### 8.1 新增测试文件必须进分组（否则等于没写）

`all` / `ci` 档取的是 `run_regression.py` 中 `GROUPS` 的**并集**（`all_paths()`），
不在任何分组里的文件**永远不会被全量回归与 CI 执行**。守卫类测试尤其危险：
它红着没人知道，绿了也没人受益。

- 新增测试文件必须同时加入某个分组（后端模块档靠 `scripts/test_catalog.py` 映射即可自动化，
  但仍建议补齐 `GROUPS` 语义分组），或明确落入某个模块的 `BACKEND_FILE_TO_FUNC`。
- 实际教训（2026-11-03）：`test_list_scope_ui_parity.py`（列表列「界面↔注册表」守卫）
  游离在所有分组之外；前端把报表视图拆成 `reporting/reports/*.tsx` 后，该守卫星
  仍指向只剩 Tab 壳的 `ReportsPage.tsx`，7 条 `RPT_*` 一直失败而无人发现。
  修复后已并入 `unit` 档（纯静态源码比对，0.04s），可随 PR 级 CI 生效。

## 9. 本地执行前置条件（避坑，否则用例全 ERROR 或安全断言失败）

1. **测试库 URL 必须用 psycopg v3 方言**：`postgresql+psycopg://`（项目统一驱动，
   不是 `postgresql://` / `psycopg2`）。用错方言会触发
   `ModuleNotFoundError: No module named 'psycopg2'`——`settings.py` 默认即
   `postgresql+psycopg://…`，pytest 经 conftest 连库时沿用同一方言。
2. **`TEST_DATABASE_URL` 必须放在 `backend/.env` 文件里（gitignore 已忽略），不要 export 成环境变量**。
   `tests/v1/test_settings.py::test_test_database_url_defaults_to_empty` 用
   `Settings(_env_file=None)` 断言「缺省为空」，pydantic 仍会读环境变量——若 export 了该变量，
   此断言必失败。conftest 读不到环境变量时会回落 `settings.test_database_url`（即 `.env` 文件值），
   二者互不冲突。
3. **`TEST_DATABASE_URL` 与 `DATABASE_URL` 必须指向不同库**（conftest 本地校验同名即拒绝 `pytest.exit`），
   且库名均须含 `test`（夹具每个 session 会 `TRUNCATE` 全表）。
4. **PG 实例**：本地为容器 `heijin-db-1`（`127.0.0.1:5433` 映射容器 `5432`，独立卷
   `heijin_pg_data`）；启停见 `deploy/scripts/pg_container.sh up|status`。宿主机无 `psql`，
   备份/恢复一律 `docker exec heijin-db-1`。
5. **推荐运行器**：`/Users/aries/Applications/Python_3.13/bin/python3`
   （sa+pytest 可用）；`run_regression.py` 默认调 `.venv/bin/python`，二者均含 psycopg v3。
6. **生成用例库 / 报告**（均在 `backend/` 下）：
   `python scripts/gen_test_case_library.py`、`python scripts/make_test_report.py`。
   `make_test_report.py` 的「最近结果」按 `run_id` 聚合：同一用例在某次 run 内出现多条记录
   （如参数化变体）时取**最差**状态，避免秒级时间戳碰撞掩盖 FAIL。
