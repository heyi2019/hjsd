# 宜游轩 ERP 测试编号设计规范

> 生效日期：2026-11-03｜适用范围：后端（FastAPI/PG）、前端（Vite/React/Vitest）、CI
> 定位：测试体系编号的"宪法"。所有测试用例、用例库、执行报告统一本规范编号。
> 依据：Codex 补充指令（A—F 六大模块 + SYS 系统级；三级编号；UT/IT/E2E 三类；用例库与执行结果分离）。

---

## 1. 模块划分（A—F + SYS）

| 模块 | 名称 | 含义 | 前端导航 key | 后端代码域 |
|---|---|---|---|---|
| **A** | 工作台 | 首页看板、经营数据聚合 | `dashboard` | `app/reporting`（聚合）、前端 `DashboardPage` |
| **B** | 业务中心 | 订单 / 库存 / 分销 / 分期 / 利润 | `business` | `app/orders`、`app/stocks`、`app/value_added_services` |
| **C** | 客户中心 | 客户 / 线索 / 角色 | `customers` | `app/parties` |
| **D** | 资金中心 | 资金池 / 流水 / 冲销 / 对账 / 返点 | `funds` | `app/finance` |
| **E** | 经营中心 | 报表 R1-R5 / 导出 / 历史迁移 | `operations` | `app/reporting`、`app/legacy_imports`、`backend/scripts` |
| **F** | 设置 | 经营规则 / 表单字段 / 列表列 / 选项 | `settings` | `app/policy`、`app/options`、`app/lists`、`app/foundation` |
| **SYS** | 系统级 | 登录认证 / 权限 / 金额 / 编号 / 状态机 / 审计 / 测试基础设施 / CI 门禁 | — | `app/auth`、`app/core`、`app/audit`、`tests/backend`（夹具/门禁/本规范自身） |

> ⚠️ **重要澄清（避免混淆）**：编号中的 **B = 宜游轩 ERP 的「业务中心」测试分组**，仅字母片段与外部「集团 B 业务线 / B 端业务线」（何邑个人资金运营模型）相同，二者**毫无关系**。任何文档/编号/映射表中出现"B"均指测试体系的业务中心分组，与集团 B 业务线无关。

### 1.1 三种测试层级 + 两种测试范围

- **层级（决定用例编号前缀）**：`UT`=单元测试、`IT`=集成测试、`E2E`=端到端测试。
- **范围（对用例的组织方式，非第四种层级）**：
  - **模块内**：验证单个模块（A–F/SYS）内部功能与业务规则。
  - **跨模块**：验证多模块之间的业务流程、数据流转与一致性。
- 跨模块用例仍是 `IT/E2E` 类型，仅额外打「跨模块」标记并关联多个业务模块；**不为模块测试新增 MT 类型**。

### 1.2 跨模块流程编号 FLOW-*

跨模块业务流程单独建 `FLOW-001 …` 编号（仅用于审计/追踪，**不产生测试类型**）：

| 流程编号 | 链路 | 覆盖文件 |
|---|---|---|
| FLOW-002 | B → D（订单 ↔ 资金） | test_flow_sale / distribution / installment / recycle |
| FLOW-005 | F → B（配置 ↔ 业务） | test_flow_config_driven |

> 其余链路（C→B、B→E、D→E、SYS→A-F）由对应模块的 IT 用例覆盖，详见《模块与跨模块测试集规范》。

## 2. 三级编号规则

```
模块编号    功能编号             测试用例编号
  A          A01 / B01 …         UT-A01-001
  SYS        SYS01 …             IT-A01-001 / E2E-A01-001
```

1. **模块编号**：`A B C D E F SYS`（系统级合为 `SYS`）。
2. **功能编号**：`模块 + 两位数字`，如 `A01`、`B01`、`SYS01`。由实际代码盘点确定（见 `功能编号注册表.csv`），不得仅凭示例分配。
3. **测试用例编号**：`<类型>-<功能编号>-<三位序号>`。
   - 类型前缀：`UT`=单元测试，`IT`=集成测试，`E2E`=端到端测试。
   - 序号在同一 `<类型>-<功能编号>` 内从 `001` 递增，稳定唯一。
   - **同一功能可同时拥有 UT/IT/E2E 三类用例**：`UT-A01-001`、`IT-A01-001`、`E2E-A01-001` 三者共存、互不占用。

完整示例：`UT-B01-001`（单元测试·业务中心·订单创建·第 1 例）。

### 2.1 测试函数标识必须带类名

同一测试文件内可以存在**多个 `Test*` 类下的同名方法**（pytest 允许，如
`TestCreateCustomerGuards::test_empty_display_name_rejected` 与
`TestCounterpartyGuards::test_empty_display_name_rejected`）。因此：

- 用例库「测试函数标识」与编号映射键一律用**限定名** `ClassName::test_name`；模块级函数直接用 `test_name`。
- 用例库生成的 `case_index.json` 中 nodeid 必须与 pytest 真实 nodeid **逐字一致**（含类名），
  否则执行记录关联不到编号 —— 表现为「测了，但报告里永远显示未执行」。
- 违反后果（2026-11-03 实测）：749 / 2557 条（29%）用例属于类内方法，因只记裸函数名而
  **长期在报告中隐身**，且 3 组同名方法撞成同一编号、生成重复行。生成器现已内置
  「编号唯一 / nodeid 唯一」两道断言，重复即中止，不产出串号文件。

## 3. 编号约束（唯一 / 稳定 / 可检索）

- **唯一**：同一 `<类型>-<功能编号>` 下序号不重复；全库 `测试用例编号` 唯一。
- **稳定**：编号一旦分配**冻结**。新增用例只追加新序号；删除/重构用例**不回收**其编号（保留空位，避免历史执行记录错位）。
  用例被删除或改号后，其编号成为**退役编号**：`results.jsonl` 中的历史记录保留不删，但
  `测试报告` 把它单列为「已退役编号（仅存历史记录、不计入统计）」，**不得计入
  PASS/FAIL/SKIP 汇总** —— 否则会出现「模块矩阵全绿、汇总却说 SKIP=1」的自相矛盾。
- **可检索**：编号即索引。用例库（`测试用例库.csv`）、执行结果（`测试结果库/results.jsonl`）、CI 报告三者均以 `测试用例编号` 关联。
- **映射可查**：旧编号 `BIZ-*` 与新风编号通过 `功能编号注册表.csv` 的「关联旧编号」列与用例库「关联旧编号」列双向可查，避免直接覆盖。

## 5. 测试方法 / 合格标准填写规则

- **测试方法**：必填，描述「执行方式 + 步骤」。自动生成格式：`<UT/IT/E2E>：<文件>::<函数>；<隔离方式>；<主操作>`。隔离方式=`无 DB/纯函数`(UT) / `真实 PG 隔离库(TRUNCATE 单事务)`(IT) / `真实浏览器(chromium)+真实后端+常驻 e2e 库(每轮不清数据，按类型补足 IN_STOCK 账号)`(E2E)；主操作=从函数体提取的首个 API 端点或 Service 调用（E2E 为页面端到端操作）。
- **合格标准**：必填，可自动判定的明确断言。优先取测试函数 docstring 的预期句（剥离 `BIZ-*` 前缀与 `(高)` 等优先级标记）；无法从代码/文档确定时**标记「待确认」**，不得自行创造合格标准。
- **业务规则不明确**：用例库该行「合格标准」写「待确认」，并在备注列登记待澄清点。

---

## 6. 文件管理

- 测试文件保持**语义化命名**（`test_<功能>.py` / `test_*_contract.py`），**不**为整齐而大规模改名；编号与文件的映射由 `功能编号注册表.csv` + 用例库「自动化测试文件路径」列承载。
- 不改动业务代码目录（`app/`），仅新增测试体系文档与 `scripts/`、`tests/backend/_report/` 下的支撑脚本。
