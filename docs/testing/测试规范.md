# 测试规范

> 本文是测试体系的唯一规范：分层架构、编号与模块、用例库与执行结果、CI 分层、文件边界、本地执行约束。
> 分层与执行入口见 `tests/README.md`，测试顺序见 [测试流程](../测试流程.md)；开发、本地验收见 [研发流程](../研发流程.md)，阿里云发布见 [发布流程](../发布流程.md)。文档与代码冲突时以代码为准。历史版本由 git 追溯。

## 1. 分层架构

| 层 | 验证对象 | 依赖 | 落地 |
|---|---|---|---|
| **UT** 单元 | 单一规则、纯函数、静态守卫 | 不碰 DB / 网络 / 真实 HTTP | `tests/backend/unit/`、`tests/frontend/unit/` |
| **IT** 集成 | 组件真实协作（API ↔ Service ↔ DB）、组件渲染 | 真实 PG 隔离库 / jsdom | `tests/backend/integration/`、`tests/frontend/module/` |
| **E2E** 端到端 | 用户完整操作链路 | 真实 Chromium + 独立临时库 | `tests/e2e/<区域>`，按需本地运行；规格变更及全量档由前端门禁运行 |

黑盒 / 白盒是**正交维度**，不与分层混淆：黑盒验输入 → 操作 → 输出 → 数据状态（业务正确性）；白盒验分支 / 异常 / 事务 / 并发 / 幂等（实现正确性）。同一用例可同时承担两者。

**跨模块不是第四种测试类型**：跨模块用例仍是 IT / E2E，仅额外打「跨模块」标记并关联多个业务模块。

## 2. 业务规则验证优先级

先定义正确，再验证正确。优先级从高到低：

1. **金额精度与计算**：`core/money.py`（`Amount` / `DECIMAL(18,2)` / `to_money()`），禁止 float。
2. **状态机**：订单 / 库存状态转换，非法流转必须拒绝。
3. **判重与幂等**：入库判重、重复收支、已售复购确认。
4. **权限**：未登录 / 越权 / 敏感字段按权限范围展示。
5. **事务一致性**：失败回滚不得产生幽灵数据。

需求不明确的规则**登记待确认**，不自行发明。禁止修改业务规则以迁就测试、禁止降低断言制造绿色。

## 3. 编号与模块

- 测试编号前缀即层级：`UT-` / `IT-` / `E2E-`，完整格式为 `<层级>-<功能编号>-<序号>`。
- 现役功能编号权威清单是 `docs/testing/测试元数据台账.csv` 的 `FEATURE` 记录；模块字母映射收敛在 `manifest.json` 的 `regionByCode` 与 `tests/config/catalog.py`，不在代码里各写一份。

| 模块 | 名称 | 范围 |
|---|---|---|
| A | 工作台 | 首页看板、经营数据聚合 |
| B | 业务中心 | 订单 / 库存 / 分销 / 分期 / 利润 |
| C | 客户中心 | 客户 / 线索 / 角色 |
| D | 资金中心 | 资金池 / 流水 / 冲销 / 对账 / 返点 |
| E | 经营中心 | 月度损益 / 分润对账 / 业务损益 / 订单利润 / 数据中心 / 导出 |
| F | 设置 | 表单字段 / 列表列 / 选项 |
| SYS | 系统级 | 登录认证 / 权限 / 金额 / 编号 / 状态机 / 审计 / 测试基础设施 / CI 门禁 |

跨模块业务流程另建 `FLOW-001 …` 流程编号用于审计追踪，**不产生新的测试类型**。当前已建设：

| 流程编号 | 链路 | 说明 |
|---|---|---|
| FLOW-002 | B → D（订单 ↔ 资金） | 售出 / 分销 / 分期 / 回收：订单状态与资金池余额同源一致 |
| FLOW-005 | F → B（配置 ↔ 业务） | 表单字段 `required` 驱动建单校验 |

其余链路（C→B、B→E、D→E、SYS→A–F）由对应模块的 IT 用例覆盖，不单独立 FLOW 文件；报表一致性由各业务报表用例承载。

## 4. 模块与跨模块测试集

实现方式：**复用 `run_regression.py` 的文件清单机制**，不复制测试文件、不动业务目录。文件 → 功能编号 → 模块字母的映射统一在 `tests/config/catalog.py`（单一事实源）。

在 `backend/` 下：

```bash
python run_regression.py B                 # 模块 B 全部后端测试（UT + IT）
python run_regression.py B --type ut      # 模块 B 仅单元测试
python run_regression.py B --backend-only # 仅后端（不跑前端 vitest）
python run_regression.py ut               # 全部单元测试
python run_regression.py it               # 全部集成测试
python run_regression.py cross            # 跨模块流程（FLOW-*）
python run_regression.py ci               # 全系统回归
python run_regression.py fe               # 前端四档全量 + 执行记录落库
```

模块档默认同时运行该模块的前端相关测试（vitest，best-effort）；一个用例可关联多个模块，模块结果可独立统计。

跨模块审计优先级：C→B（客户 ↔ 订单）、B→D（订单 ↔ 资金）、B→E（订单 ↔ 经营）、D→E（资金 ↔ 报表）、F→B（配置 ↔ 执行）、SYS→A–F（认证 ↔ 全模块）。跨模块用例以 `IT` 类型落地，不要求全部经浏览器。

## 5. 用例库与执行结果（分离管理）

- **用例定义**：`docs/testing/测试用例库.csv`，由 `scripts/gen_test_case_library.py` 从测试代码自动生成，编号稳定、幂等，**禁手改**。
- **执行结果**：`docs/testing/测试结果库/results.jsonl`，按 `run_id` 追加、历史不覆盖，**不入库**。后端由 `tests/backend/conftest.py` 钩子写入；前端 vitest 与 E2E 分别由 `record_frontend_results.py` / `record_e2e_results.py` 转换写入。
- **关联键**：用例库「测试编号」↔ 执行记录 `case_no`；conftest 读 `case_index.json`（nodeid → 测试编号）自动关联。索引缺失时由入库的《测试用例库.csv》自举恢复，否则全新 checkout 会按排序重排、与入库快照错位。
- **报告**：`docs/testing/测试报告_YYYYMMDD.md/.json`，由 `scripts/make_test_report.py` 聚合生成；按日期命名，现役目录只留最新一份，过期件由生成器移入 `testing/报告归档/`（不入库）。

### 5.1 「合格标准」取值规则

`合格标准` 必须是**可核对**的判据，按以下优先级自动推导，不靠人工补写：

| 优先级 | 来源 | 示例 |
|---|---|---|
| 1 | docstring 中含期望动词的句子 | `取消后余额回到冻结前水平` |
| 2 | `assert x, "消息"` 的断言消息 | `余额不得为负` |
| 3 | 真实断言**机械推导**（后端 `pytest.raises` / `assert`；前端首个 `expect` 链） | `抛出 Validation，消息匹配「已售账号不能新增 COST」` |
| 4 | 用例完全没有显式断言 | `正常执行不抛异常（用例无显式断言）` |

第 3 档的推导结果必须能在源文件中逐字找到；第 4 档不是文档缺失，而是**测试本身薄弱**，报告单列为「弱标准」风险项，建议补断言 —— 不要再退回 `待确认` 占位（它既不提供信息，还会把「测试薄弱」伪装成「业务未澄清」）。

改生成器时必须守住两个已踩过的解析坑：

1. **断言消息只能按顶层逗号切分**。`assert f(a, "ACTIVE") == x` 的第一个逗号在括号内，按「第一个逗号」取会把实参当成消息（曾产出 54 条只剩一个值的合格标准）。
2. **跨行括号断言要续行读完整**。逐行正则只能截到半句（曾产出只剩 `(` 的空白标准）。
3. 前端 `it.each([...])("标题", cb)` 有两组括号，回调体取**第二组**，否则会取到参数列表而非断言。

### 5.2 前端与 E2E 记录口径

执行记录器是 **pytest 插件**，只能记后端；前端与 E2E 必须转成同格式记录追加进同一份 `results.jsonl`，报告侧无需特判。

```bash
# 前端：一条命令全量 + 落库，或分两步保留原始 JSON
backend/.venv/bin/python backend/run_regression.py fe
cd frontend && npx vitest run --reporter=json --outputFile=/tmp/vitest.json
backend/.venv/bin/python backend/scripts/record_frontend_results.py --json /tmp/vitest.json

# E2E：config 已配 json reporter
cd frontend && npx playwright test
cd backend && .venv/bin/python scripts/record_e2e_results.py   # 只统计不写入：--dry-run
```

- 前端用例键 = `frontend/src/<相对路径>::<it()/test() 标题>`；E2E 用例键 = `tests/e2e/<区域>/<规格文件名>::<test() 标题>`。Playwright JSON 的 `spec.file` 是相对 `testDir` 的路径，必须补 `tests/e2e/` 前缀，否则记录全部落空。
- 模板标题（前端 `it.each`、E2E 反引号模板）在用例库中记**一条**，运行时展开的多条由记录器按通配归并回这一条，同一条内多状态取最差。
- 标题里含引号必须由字符串扫描器读取，不能用 `["']([^"']+)["']` 之类正则，会在内层引号处截断。
- `test.describe(...)` / `test.describe.serial(...)` 命中 `test` + `(` 且首参是字符串，扫描时按方法名排除，否则每个分组凭空多一条「用例」。
- E2E 状态映射：`expected`→PASS、`unexpected`→FAIL、`flaky`→PASS（`reason` 记「重试后通过」）、`skipped`→SKIP。flaky 记 FAIL 会把「不稳定」误报成「一直红」。
- **不指定 `--project`**：模块档跑任意前端文件若写成 `npm run test:fast -- <files>`，不属于 fast 清单的文件会被直接过滤，表现为「跑了但一条没执行」却 0 退出（假绿）。
- **未命中必须为 0**；不为 0 说明用例库标题与源码漂移或测试未收录。新增 E2E 规格要在 `tests/config/catalog.py` 的 `E2E_FILE_TO_FUNC` 登记功能编号，未登记会落 `SYS12` 兜底。

### 5.3 新增用例与「未执行」的因果关系

执行记录写入时用的是**当时**的 `case_index.json`。新写的用例第一次跑时库里还没有它的编号，`case_no` 只能写成空串——报告若不处理，这批记录永远归不到编号上（表现为「明明刚跑过却显示未执行」）。`make_test_report.py` 因此在报告阶段按 `nodeid → case_index.json` **反查补号**（报告一定在用例库生成之后运行），无需重跑测试。排查顺序：先看 `results.jsonl` 里该 `nodeid` 是否有记录 → 再看 `case_no` 是否为空 → 最后确认索引里有这个 nodeid。

## 6. CI 分层

- `backend-gate.yml`：普通发布按完整提交范围选测；结构性变更或范围无法确定时跑 `ci`，手动指定全量或不传范围也跑 `ci`。测试库基线检查和报告生成按工作流执行，报告 artifact 保留 7 天。
- `frontend-gate.yml`：执行静态检查与构建；有前端相关变更时按范围选测，无相关变更时跑 `quick`，指定全量或范围无法确定时运行 `test:ci`（含 deep）。
- 日常 `dev` push 和 PR 不自动触发云端门禁；本地按改动验证，必要时可手动触发三道门禁。
- 生产发布由 `main-ci-cd` 在同一个发布提交上调用 lint、前端和后端三道门禁，全部成功后才开始构建镜像及部署；不再为 `main` 另行触发重复门禁。
- E2E 保留在 `tests/e2e/<区域>`，可按需本地运行；规格变更时由 `frontend-gate` 运行受影响规格，共享配置变更、手动指定前端全量以及生产数据库重建时运行完整浏览器测试。`e2e-gate` / `coverage-gate` 已下线。
- `results.jsonl` 是本地产物（已 gitignore），跨工作流汇不起来，因此 CI artifact 里的报告**只含后端执行结果**；要三层全绿覆盖，本地先跑 `run_regression.py fe` 与 `record_e2e_results.py`，再跑 `make_test_report.py`。

## 7. 文件管理边界

- **允许**：整理测试目录、规范命名、拆分职责混乱文件、提取共享 Fixtures/Mocks/Helpers、建立标签与模块映射、调整测试发现配置及 CI、补齐缺失自动化测试。
- **禁止**：擅自重构前后端业务目录、擅自修改业务规则、降低原有断言、删除有效测试场景、对未经确认的数据执行清空/重置、擅自推送/合并/部署。

### 7.1 新增测试文件必须进分组

`all` / `ci` 档取的是 `run_regression.py` 中 `GROUPS` 的**并集**（`all_paths()`），不在任何分组里的文件**永远不会被全量回归与 CI 执行**。守卫类测试尤其危险：它红着没人知道，绿了也没人受益。

新增测试文件必须同时加入某个分组，或明确落入某个模块的 `BACKEND_FILE_TO_FUNC`。实际教训：列表列「界面 ↔ 注册表」守卫曾游离在所有分组之外，前端把报表视图拆成 `operations/reports/*.tsx` 后，该守卫仍指向只剩 Tab 壳的页面，7 条 `RPT_*` 一直失败而无人发现；修复后并入 `unit` 档。

## 8. 数据库安全红线

1. 单元测试尽量不碰 DB；集成测试只用 `TEST_DATABASE_URL` 指向的隔离库。
2. `conftest` 强制：库名含 `test`、黑名单 release/prod、本地禁止与 dev 同库；**新增测试不得绕过**。夹具每个 session 会 `TRUNCATE` 全表。
3. 禁止连接生产 / 上线库；严禁真实支付 / 放款 / 外部通知副作用。
4. 任何建库 / 清库 / 迁移 / 结构变更**先确认目标环境可恢复性**。
5. 不得并发启动多个后端 pytest 进程指向同一测试库（TRUNCATE 竞态）。
6. 附件读写测试必须使用独立临时存储目录，不能将测试文件写入开发环境附件目录；测试库与文件存储均需隔离。

## 9. 本地执行前置条件

1. **测试库 URL 必须用 psycopg v3 方言** `postgresql+psycopg://`；用错会触发 `ModuleNotFoundError: No module named 'psycopg2'`。
2. **测试库配置默认写在项目根目录 `.env`** 的 `TEST_DATABASE_URL` 中；进程环境变量优先，`ERP_ENV_FILE` 可显式指定其他配置文件。不要把 `backend/.env` 当成常规配置入口。
3. 本地 **`TEST_DATABASE_URL` 与 `DATABASE_URL` 必须指向不同库**；测试库名必须含 `test`，且不得包含 `release` / `prod` 等禁用关键字。开发库无须在库名中包含 `test`。CI 的一次性隔离数据库可按门禁配置使用同一地址。
4. **PG 实例**：本地为容器 `heijin-db-1`（`127.0.0.1:5433` 映射容器 `5432`）；启停见 `deploy/scripts/pg_container.sh up|status`。宿主机无 `psql`，备份 / 恢复一律 `docker exec heijin-db-1`。
5. **本机运行器**：运行 `python3 backend/scripts/setup_test_environment.py` 准备依赖和独立 Redis；直接运行 pytest 使用 `scripts/ops/test-local.sh`，分组回归使用相同的 Python 3.13 和隔离依赖。本机和后端 CI 使用 `backend/requirements-dev.lock.txt` 锁定开发及传递依赖，并以生产锁文件约束共同依赖；更新方式见 README。CI 按其配置使用自身 Python 环境；lint 仍使用 `backend/.venv`。
6. **生成用例库 / 报告**（均在 `backend/` 下）：`python scripts/gen_test_case_library.py`、`python scripts/make_test_report.py`。报告的「最近结果」按 `run_id` 聚合，同一用例在某次 run 内出现多条记录时取**最差**状态。

### 9.1 开发修改后的自动验证

- 任何执行者（Codex、WorkBuddy 或其他协作者）完成代码、测试或测试配置修改后，必须自动运行与变更范围匹配的测试，不等待用户另行提醒。
- 前端可执行 `cd frontend && npm run test:changed`：脚本根据当前未提交改动选择对应业务区域；公共层、夹具、分层配置及无法确定影响范围的改动运行完整前端测试。
- 普通 React 测试层的最大 worker 数为 4；`react-deep` 层按其独立配置运行。不要靠设置 `REACT_WORKERS` 环境变量假定已更改 Vitest 配置。
- 测试失败时不得直接交付或提交：先保留失败信息，修复实现或测试问题，再重新执行对应测试，直到结果明确。
- 需要预览测试范围时执行 `npm run test:changed -- --list`；涉及跨模块、里程碑收口或发布前，再执行 `npm run test:full` 与 `npm run test:full:deep`。
- 外部编辑器产生的修改也必须在下一次协作继续前检查工作区，并执行同一套变更测试。

发布前验证与云端 `dev` 交接顺序见 [测试流程](../测试流程.md)。

## 10. 新增测试自检清单

- [ ] 明确功能编号与业务规则（来自映射表或已确认契约）。
- [ ] 断言覆盖正常 / 边界 / 失败；集成测试验证 **DB 状态**而非仅响应码。
- [ ] 不修改业务规则以迁就测试；不降低断言制造绿色。
- [ ] 不新增对生产库的连接；不引入真实外部副作用。
- [ ] 文件已进 `GROUPS` 或模块映射，能被全量回归与 CI 执行。
- [ ] 本地运行通过后再提交；改动只跑针对性用例，不默认全量。
