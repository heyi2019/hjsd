## 步骤 0 · 开工前两个硬前置（不满足就别往下走）

ECS 上执行：

```bash
docker --version && docker compose version
curl -sS -m 20 https://registry-1.docker.io/v2/ | head -1
```

| 检查 | 通过判据 | 失败处置 |
|---|---|---|
| Docker 可用 | 两条版本号都打印 | `apt install docker.io docker-compose-v2` 或按官方脚本装 |
| **镜像仓库可达** | 返回 `401 Unauthorized`（这是正常握手）或任意 JSON | 配阿里云镜像加速器：`/etc/docker/daemon.json` 写 `{"registry-mirrors":["https://<你的ID>.mirror.aliyuncs.com"]}` 后 `systemctl restart docker` |

**预拉基础镜像（最关键的一步，离线构建能力全靠它）**：

```bash
docker pull alpine:3.20 && docker pull node:22-alpine
```

> 判据：两条都显示 `Status: Downloaded newer image` 或 `Image is up to date`。
> 若这里失败，`deploy.sh` 会在 `docker compose build` 阶段就中断，且报错位置在 `FROM` 行，容易误判成代码问题。
> **不进这一步就别继续**：既是构建前提，也能提前暴露网络问题。

## 步骤 2 · 写生产配置（唯一含密钥的环节）

```bash
cd /opt/heijin/deploy
cp env/.env.production.example .env
SECRET=$(openssl rand -hex 32)
sed -i "s|^JWT_SECRET_KEY=.*|JWT_SECRET_KEY=${SECRET}|" .env
grep -E '^(JWT_SECRET_KEY|DATABASE_URL|CORS_ORIGINS)' .env
chmod 600 .env
```

| 判据 | 期望 | 说明 |
|---|---|---|
| `JWT_SECRET_KEY` | 64 位十六进制，**且不是** `replace-with-*` | 以 `replace-with-` 开头的值会被 `settings.py` 直接拒绝启动（这是刻意设计的拦截） |
| `DATABASE_URL` | `sqlite:///./data/heijin_erp_v1.db` | 相对路径解析到容器 `/app/data`，对应卷 `erp_db` |
| `CORS_ORIGINS` | 空值 | 前端由 nginx 同源反代 `/api/v1/`，浏览器不跨域；填了不存在的域名会污染白名单 |

> **不要把 `ADMIN_PASSWORD` 写进 `.env`**：该文件通过 `env_file` 注入 backend 常驻进程环境，任何 `docker inspect` 都能读到。用下一步的临时 `export`。

## 步骤 3 · 首次部署

```bash
cd /opt/heijin/deploy
export ADMIN_PASSWORD='<至少 12 位强密码>'
bash scripts/deploy.sh
```

脚本依次执行：`build` → 库不存在则跳过备份 → `alembic upgrade head`（失败自动 `stamp_baseline` 兜底）→ 预置经营规则 → `up -d` → 建/更新 admin → `ps` → 健康检查。
**全程约 3–6 分钟**（首次构建为主）。

| 阶段 | 通过判据 | 失败处置 |
|---|---|---|
| 构建 | 出现 `Image deploy-backend Built` / `deploy-frontend Built` | 回到步骤 0 检查基础镜像与网络 |
| 迁移 | `Running upgrade -> 0001` | 报 `Can't locate revision` 说明旧版本戳，脚本自带 `stamp_baseline.py` 兜底，看它打印的缺口清单 |
| 预置规则 | 打印各 `policy_code` 结果 | 出现 0 条且无报错 → 检查 `policy_definitions` 是否为空 |
| 服务 | `docker compose ps`：backend `Up (healthy)`、frontend `Up`（前端未配 healthcheck，只有 `Up` 属正常） | backend 非 healthy：`docker compose logs backend` |
| 健康检查 | `{"status":"ok",...}` | 见下方排查 |

## 步骤 4 · 验收（7 项，全部通过才算上线）

ECS 上执行：

```bash
# 1 服务状态：backend 应为 healthy，frontend 为 Up
docker compose ps

# 2 健康端点
curl -s http://127.0.0.1/api/v1/health

# 3 首页可访问且带安全头（CSP 必须在）
curl -sI http://127.0.0.1/ | grep -iE 'HTTP/|content-security-policy|x-frame-options'

# 4 API 反代通（应返回 401/422，而不是 404/502）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/api/v1/auth/me

# 5 生产已关闭文档（应为 404）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/docs

# 6 正式库已生成且非空壳
docker compose exec -T backend ls -l /app/data/heijin_erp_v1.db

# 7 库里有 admin
docker compose exec -T backend python -c "
import sqlite3;c=sqlite3.connect('/app/data/heijin_erp_v1.db')
print(c.execute('select username,role from users').fetchall())"
```

| # | 判据 |
|---|---|
| 1 | backend `Up (healthy)`；frontend `Up`（前端未配 healthcheck，`Up` 即正常） |
| 2 | 返回 `{"status":"ok",...}` |
| 3 | 200 且响应头含 `Content-Security-Policy` 与 `X-Frame-Options`（**首页也要有**，这是 `5f02a7b` 修过的继承阻断缺陷） |
| 4 | 401 或 422（有响应即反代通） |
| 5 | 404 |
| 6 | 文件存在，约 700–800 KB |
| 7 | 含 `('admin','ADMIN')` |

浏览器验收（本机）：打开 `http://<ECS_IP>/` → 出现登录页 → 用 `admin` + 步骤 3 的密码登录 → 进入工作台 → 打开业务中心、资金、设置各页无白屏。
**再按一次 `Cmd+R` 强刷**，确认 SPA 深链不 404。

## 步骤 5 · 备份双保险（上线当天就要挂）

ECS 上：

```bash
# 立刻跑一次，确认脚本可用（应输出 BACKUP_OK ...）
bash /opt/heijin/deploy/scripts/backup_daily.sh

# 挂 cron：每日 03:20 快照
( crontab -l 2>/dev/null; echo '20 3 * * * /bin/bash /opt/heijin/deploy/scripts/backup_daily.sh >> /var/log/heijin_backup.log 2>&1' ) | crontab -
crontab -l | tail -2
```

本机执行：

```bash
# 首次手动拉取，确认 SSH 免密与卷名正确
bash /Users/aries/黑金时代/deploy/scripts/pull_backup.sh --host root@<ECS_IP>

# 成功后再挂 cron：每日 04:10
( crontab -l 2>/dev/null; echo '10 4 * * * /bin/bash /Users/aries/黑金时代/deploy/scripts/pull_backup.sh --host root@<ECS_IP> >> ~/heijin_pull.log 2>&1' ) | crontab -
```

| 判据 | 期望 |
|---|---|
| ECS 侧 | `BACKUP_OK path=/app/data/backups/heijin_erp_v1_<时间戳>.db size=... sha256=...` |
| 本机侧 | `SHA256 通过 1 份 / 异常 0 份；integrity 异常 0 份`，落地 `~/heijin_backups/` 只有 `.db` + `.sha256` |
| 保护逻辑 | 若 ECS 备份损坏，本机脚本退出码 1 且**不覆盖**本地原有备份（坏文件留在 `.incoming`） |

> 前提：本机需能免密 SSH 到 ECS（`ssh-copy-id root@<ECS_IP>`）。本机在 NAT 后也没问题——是本机主动拉取，不需要 ECS 反向连本机。

## 步骤 7 · 若要搬迁本地 486 条历史数据（可选分支）

> 先裁决：本机 `backend/data/heijin_erp_v1.db` 里 486 订单 / 107 客户是否为真实业务数据。
> 若为「是」，按下面顺序执行；若为「否」，跳过本步，生产库保持空库。

```bash
# ① 本机导出在线快照（WAL 安全，产出单文件 + sha256）
/Users/aries/Applications/Python_3.13/bin/python3 /Users/aries/黑金时代/backend/scripts/backup_db.py \
  --db /Users/aries/黑金时代/backend/data/heijin_erp_v1.db \
  --out-dir /Users/aries/黑金时代/backend/data/backups --keep 5

# ② 上传到 ECS
scp /Users/aries/黑金时代/backend/data/backups/heijin_erp_v1_<时间戳>.db* root@<ECS_IP>:/tmp/

# ③ ECS 上放进卷并恢复（restore 会自动校验 SHA256 + integrity，旧库保留为 .bak）
cd /opt/heijin/deploy
docker compose cp /tmp/heijin_erp_v1_<时间戳>.db backend:/app/data/import.db
docker compose exec -T backend python scripts/restore_db.py --backup /app/data/import.db --force
docker compose restart backend

# ④ 复核订单数
docker compose exec -T backend python -c "
import sqlite3;c=sqlite3.connect('/app/data/heijin_erp_v1.db')
print('orders=', c.execute('select count(*) from orders').fetchone()[0])"
```

| 判据 | 期望 |
|---|---|
| 订单数 | 486（与本机一致） |
| 迁移版本 | `alembic_version = 0001`（本机已压平，无需再迁移） |
| 登录 | admin 可用于登录（本地库的 admin 密码一并搬过来了，若忘记走 `create_admin.py` 重置） |

> **顺序很重要**：先 `deploy.sh` 让库存在并完成迁移，再 restore 覆盖。反过来会在迁移前替换文件，可能把版本戳弄乱。

## 步骤 8 · 回滚

| 场景 | 动作 |
|---|---|
| 镜像/代码有问题，服务起不来 | `cd /opt/heijin/deploy && docker compose down`（**不要加 `-v`**），回退代码后重跑 `deploy.sh` |
| 数据被改坏 | 从 `/app/data/backups/` 或本机 `~/heijin_backups/` 取最近一份 → `restore_db.py --force` → `docker compose restart backend` |
| 误执行 `down -v` | 卷已删除，**只能用本机 `~/heijin_backups/` 的异地备份恢复**——这就是步骤 5 存在的意义 |

> `docker compose down -v` 会删掉 `erp_db` 卷，等于删库。生产环境禁止使用；确实要重建才允许，且必须先确认异地备份可读。
