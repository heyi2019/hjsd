## 步骤 0 · 开工前硬前置 + 选构建路径

**先选路径，两者后续命令不同：**

| 路径 | 前置条件 | 上线耗时 | 适用 |
|---|---|---|---|
| **A 离线镜像（推荐）** | 只需 `docker load` | 约 3 分钟 | ECS 访问 Docker Hub / pypi / npm 任一不通时 |
| B 在线构建 | 四个源全部可达：Docker Hub、alpine 源、pypi、npm | 约 6–10 分钟 | 网络畅通，或希望 ECS 自行产镜像 |

> 判断依据很简单：**路径 A 把四个网络依赖压成零**。镜像已在 Mac 上交叉构建为 `linux/amd64`
> 并实测可运行（x86_64 / Python 3.12.13 / 依赖可导入 / nginx 安全头齐全），ECS 只做解包。
> 本项目镜像不由 CI 产出，若走路径 B 而 ECS 拉不到 `alpine:3.20`，构建会断在 Dockerfile 的
> `FROM` 行，报错形似代码问题——这是上线当天最容易误判的坑。

ECS 上先执行通用检查：

```bash
docker --version && docker compose version
uname -m
```

| 检查 | 通过判据 | 失败处置 |
|---|---|---|
| Docker 可用 | 两条版本号都打印 | `apt install docker.io docker-compose-v2` 或按官方脚本装 |
| **CPU 架构** | `x86_64` | 若是 `aarch64`，本离线包不可用（包内镜像是 amd64），须在 ECS 本机重建 |

### 路径 A · 离线镜像（推荐）

```bash
cd /opt/heijin
sha256sum -c heijin-images-1.0.0-amd64.tar.gz.sha256   # 判据：输出 OK
gunzip -c heijin-images-1.0.0-amd64.tar.gz | docker load
docker images | grep heijin                            # 判据：两行，均 1.0.0
docker image inspect heijin-backend:1.0.0 --format '{{.Architecture}}'   # 判据：amd64
```

> `sha256sum -c` 不能省：47 MB 走 scp 中断重传会得到「能 load 但层损坏」的包，
> 而损坏通常在容器启动时才暴露成 `exec format error` 或 `no such file or directory`。

### 路径 B · 在线构建

```bash
curl -sS -m 20 https://registry-1.docker.io/v2/ | head -1
docker pull alpine:3.20 && docker pull node:22-alpine
```

| 检查 | 通过判据 | 失败处置 |
|---|---|---|
| 镜像仓库可达 | 返回 `401 Unauthorized`（正常握手）或任意 JSON | 配阿里云镜像加速器：`/etc/docker/daemon.json` 写 `{"registry-mirrors":["https://<你的ID>.mirror.aliyuncs.com"]}` 后 `systemctl restart docker`，**仍不通就改用路径 A** |
| 基础镜像 | 两条都显示 `Downloaded newer image` 或 `Image is up to date` | 同上 |

> `deploy.sh` 已内置同样的预检并会**在 build 之前**中断：拉不到时直接打印加速器配置命令与
> 离线导入方案，不会让你在一堆构建日志里找 `FROM` 行的 `TLS handshake timeout`。
> 但这属于「事后兜底」——预拉成功才说明镜像仓库真的通。

## 步骤 2 · 写生产配置（唯一含密钥的环节）

```bash
cd /opt/heijin/deploy
cp env/.env.production.example .env
SECRET=$(openssl rand -hex 32)
sed -i "s|^JWT_SECRET_KEY=.*|JWT_SECRET_KEY=${SECRET}|" .env
grep -E '^(JWT_SECRET_KEY|DATABASE_URL|CORS_ORIGINS)' .env
chmod 600 .env
```

| 判据 | 期望 | 说明 |
|---|---|---|
| `JWT_SECRET_KEY` | 64 位十六进制，**且不是** `replace-with-*` | 以 `replace-with-` 开头的值会被 `settings.py` 直接拒绝启动（这是刻意设计的拦截） |
| `DATABASE_URL` | `sqlite:///./data/heijin_erp_v1.db` | 相对路径解析到容器 `/app/data`，对应卷 `erp_db` |
| `CORS_ORIGINS` | 空值 | 前端由 nginx 同源反代 `/api/v1/`，浏览器不跨域；填了不存在的域名会污染白名单 |

> **不要把 `ADMIN_PASSWORD` 写进 `.env`**：该文件通过 `env_file` 注入 backend 常驻进程环境，任何 `docker inspect` 都能读到。用下一步的临时 `export`。

## 步骤 3 · 首次部署

**路径 A（离线镜像）—— 加 `ERP_SKIP_BUILD=1`：**

```bash
cd /opt/heijin/deploy
export ADMIN_PASSWORD='<至少 12 位强密码>'
ERP_SKIP_BUILD=1 bash scripts/deploy.sh
```

**路径 B（在线构建）—— 原样执行：**

```bash
cd /opt/heijin/deploy
export ADMIN_PASSWORD='<至少 12 位强密码>'
bash scripts/deploy.sh
```

脚本依次执行：`校验/构建镜像` → 库不存在则跳过备份 → `alembic upgrade head`（失败自动 `stamp_baseline` 兜底）→ 预置经营规则 → `up -d` → 建/更新 admin → `ps` → 健康检查。
**耗时：路径 A 约 2–3 分钟，路径 B 约 6–10 分钟**（首次构建为主）。

> `ERP_SKIP_BUILD=1` 不是"少做一步"的偷懒开关：它会逐个校验 `heijin-backend:1.0.0` /
> `heijin-frontend:1.0.0` **存在且架构为 amd64**，任一不满足立即 `exit 1`。缺镜像时给出
> 明确的 `docker load` 命令，架构不符时指出「arm64 镜像在 x86_64 上会 exec format error」。

| 阶段 | 通过判据 | 失败处置 |
|---|---|---|
| 镜像 | 路径 A：`✓ heijin-backend:1.0.0 (amd64)` / `✓ heijin-frontend:1.0.0 (amd64)`；路径 B：`Image heijin-backend:1.0.0 Built` | 路径 A 报缺镜像 → 回步骤 0 的 `docker load`；报架构不符 → 离线包是 arm64 的，重新导出。路径 B → 回步骤 0 检查基础镜像，或直接改走路径 A。npm 已走 `registry.npmmirror.com` |
| 迁移 | `Running upgrade  -> 0001` | 报 `Can't locate revision` 说明旧版本戳，脚本自带 `stamp_baseline.py` 兜底，看它打印的缺口清单 |
| 预置规则 | 打印 6 条定义 + 4 条版本（`WRITE_DOWN`/`REFUND` 显示"待配置"属正常） | 出现 0 条且无报错 → 检查 `policy_definitions` 是否为空 |
| 服务 | `docker compose ps`：backend `Up (healthy)`、frontend `Up`（前端未配 healthcheck，只有 `Up` 属正常） | backend 非 healthy：`docker compose logs backend` |
| 健康检查 | `{"status":"ok",...,"app_version":"1.0.0"}` | 见下方排查 |

> 在 Mac 上演练路径 A 时会看到 `The requested image's platform (linux/amd64) does not match
> the detected host platform (linux/arm64/v8)` 警告——那是 QEMU 模拟的提示，**ECS 是原生
> x86_64，不会出现**。这条警告在本机演练时属正常。

### 本步产出的管理员账号

系统**没有任何预置密码**（基线迁移不插 `users` 行，代码里也无默认口令常量）。账号完全由 `create_admin.py` 在此时生成：

| 项 | 值 |
|---|---|
| 用户名 | `admin`（固定，脚本内字面量） |
| 密码 | 上面 `export ADMIN_PASSWORD='...'` 的那个值，**明文只存在于你输入它的那一刻** |
| 角色 | `ADMIN`，权限为该角色全量（`ROLE_ADMIN: ALL_PERMISSIONS`） |
| 数据范围 | `owner_scope=ALL`（跨团队可见） |
| 存储形式 | `pbkdf2_sha256$240000$<salt>$<digest>`，每账号独立 16 字节随机盐，不可逆 |

> **两个必须知道的点**
> 1. **漏传 `ADMIN_PASSWORD` 时库里是 0 个用户**，`deploy.sh` 只打警告不中断 → 能打开登录页但无人可登。补跑一次 `export ADMIN_PASSWORD=... && bash scripts/deploy.sh` 即可。
> 2. **初始密码不会强制首次修改**（`create_admin.py` 直接建 User，绕过了 `must_change_password=True` 的常规路径）。上线后请走 设置 → 修改密码 手动改一次，`POST /auth/change-password` 需要旧密码。

忘记密码或需要重置（幂等，已存在则覆盖 hash 并置回 `ADMIN`/启用）：

```bash
cd /opt/heijin/deploy
export ADMIN_PASSWORD='新强密码'
docker compose exec -T -e ADMIN_PASSWORD="$ADMIN_PASSWORD" backend python scripts/create_admin.py
```

## 步骤 4 · 验收（8 项，全部通过才算上线）

ECS 上执行：

```bash
# 1 服务状态：backend 应为 healthy，frontend 为 Up
docker compose ps

# 2 健康端点 + 版本号（app_version 必须是 1.0.0）
curl -s http://127.0.0.1/api/v1/health | tr ',' '\n' | grep -E 'status|app_version'

# 3 首页可访问且带安全头（CSP 必须在）
curl -sI http://127.0.0.1/ | grep -iE 'HTTP/|content-security-policy|x-frame-options'

# 4 API 反代通（应返回 401/422，而不是 404/502）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/api/v1/auth/me

# 5 生产已关闭文档（应为 404）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/docs

# 6 正式库已生成且非空壳
docker compose exec -T backend ls -l /app/data/heijin_erp_v1.db

# 7 库里有 admin
docker compose exec -T backend python -c "
import sqlite3;c=sqlite3.connect('/app/data/heijin_erp_v1.db')
print(c.execute('select username,role from users').fetchall())"

# 8 镜像 tag 与发布版本一致（deploy.sh 从 backend/app/version.py 解析生成）
docker images --format '{{.Repository}}:{{.Tag}}' | grep heijin
```

| # | 判据 |
|---|---|
| 1 | backend `Up (healthy)`；frontend `Up`（前端未配 healthcheck，`Up` 即正常） |
| 2 | `status` 为 `ok`，**且 `app_version` 为 `1.0.0`**（对不上说明线上不是这个版本，先查清再验业务） |
| 3 | 200 且响应头含 `Content-Security-Policy` 与 `X-Frame-Options`（**首页也要有**，这是 `5f02a7b` 修过的继承阻断缺陷） |
| 4 | 401 或 422（有响应即反代通） |
| 5 | 404 |
| 6 | 文件存在，约 700–800 KB |
| 7 | 含 `('admin','ADMIN')` |
| 8 | 显示 `heijin-backend:1.0.0` 与 `heijin-frontend:1.0.0`（出现 `:latest` 说明 version.py 没被解析，看 deploy.sh 告警） |

浏览器验收（本机）：打开 `http://<ECS_IP>/` → 出现登录页 → 用 `admin` + 步骤 3 的密码登录 → 进入工作台 → 打开业务中心、资金、设置各页无白屏。

```bash

# 成功后再挂 cron：每日 04:10

```

| 判据 | 期望 |
|---|---|
| ECS 侧 | `BACKUP_OK path=/app/data/backups/heijin_erp_v1_<时间戳>.db size=... sha256=...` |
| 本机侧 | `SHA256 通过 1 份 / 异常 0 份；integrity 异常 0 份`，落地 `~/heijin_backups/` 只有 `.db` + `.sha256` |
| 保护逻辑 | 若 ECS 备份损坏，本机脚本退出码 1 且**不覆盖**本地原有备份（坏文件留在 `.incoming`） |

> 前提：本机需能免密 SSH 到 ECS（`ssh-copy-id root@<ECS_IP>`）。本机在 NAT 后也没问题——是本机主动拉取，不需要 ECS 反向连本机。

## 步骤 8 · 回滚

| 场景 | 动作 |
|---|---|
| 镜像/代码有问题，服务起不来 | `cd /opt/heijin/deploy && docker compose down`（**不要加 `-v`**），回退代码后重跑 `deploy.sh` |
| 数据被改坏 | 从 `/app/data/backups/` 或本机 `~/heijin_backups/` 取最近一份 → `restore_db.py --force` → `docker compose restart backend` |
| 误执行 `down -v` | 卷已删除，**只能用本机 `~/heijin_backups/` 的异地备份恢复**——这就是步骤 5 存在的意义 |

> `docker compose down -v` 会删掉 `erp_db` 卷，等于删库。生产环境禁止使用；确实要重建才允许，且必须先确认异地备份可读。
