# 业务域目录与跨层命名规范

## 版本变更记录

| 版本 | 日期 | 变更说明 |
| --- | --- | --- |
| V1.0 | 2026-11-25 | 发布版。登记前端、后端和测试的业务域、子模块及文件命名约定 |

适用于宜游轩 ERP 的前端、后端及自动化测试。新增或迁移文件时，先确定业务域和功能模块，再按文件职责和测试对象命名。

## 1. 一级业务域

| 统一目录名 | 业务板块 |
| --- | --- |
| `workbench` | 工作台 |
| `business` | 业务中心 |
| `customers` | 客户中心 |
| `finance` | 资金中心 |
| `operations` | 经营中心 |
| `settings` | 设置 |

前端业务目录使用 `frontend/src/<业务域>/`，后端使用 `backend/app/<业务域>/`。测试先按执行层归档，再使用同样的业务域名。

| 测试 | 目录格式 |
| --- | --- |
| 前端 Vitest | `tests/frontend/<unit 或 module>/<业务域>/` |
| 后端 pytest | `tests/backend/<unit 或 integration>/<业务域>/` |
| 浏览器 E2E | `tests/e2e/<业务域>/` |

例如，资金中心源码和测试的业务域名统一为 `finance`。导航键和 API 路径按现有接口契约管理，资金中心的导航键为 `funds`。业务域之外的应用外壳、基础层和测试基础设施继续按职责归属。

## 2. 二级功能模块

业务域内有多个独立功能、且需要分别维护时，按功能设二级目录。同一功能在各层设有子目录时，使用相同模块名，例如资金域的 `cashflow`、`deposits`、`reconciliation`，业务域的 `orders`、`inventory`、`installments`。

单文件功能或整个业务域的入口可留在域根。域内跨功能的实现和测试归域根或域内 `shared/`；跨业务域的测试工具和公共用例归相应测试层的 `shared/`，系统级守卫归 `system/`。浏览器跨域流程沿用现有的 `cross/` 归属。

## 3. 文件命名与对应

| 文件 | 命名约定 | 示例 |
| --- | --- | --- |
| 前端页面、组件 | 用页面或组件名作为主名。页面入口可用 `Page` 后缀 | `FinancePage.tsx`、`ReconciliationTab.tsx` |
| 前端测试 | 保留被测页面、组件或模块的主名，按需加关注点，以 `.test.ts` 或 `.test.tsx` 结尾 | `FinancePage.test.tsx`、`FinancePage.reconciliation.test.tsx` |
| 后端 Python 模块 | 使用 `snake_case`，文件名表达职责；ORM 模型沿用现有命名和位置 | `balances.py`、对账模块的 `service.py` |
| 后端 pytest | 使用 `test_<对象或业务行为>.py`，可加场景或职责以区分同一模块的不同覆盖 | `test_pool_balances_batch.py`、`test_finance_reconciliation_service.py` |
| Playwright 规格 | 用业务流程名作为主名，以 `.spec.ts` 结尾 | 文件名体现用户完成的流程 |

一一对应落实在**业务域、功能模块和被测对象**上。同一模块可包含多个实现与测试文件。比如资金对账在各层归 `finance/reconciliation`，前端由 `ReconciliationTab.tsx` 承担对账界面，页面级测试用 `FinancePage.reconciliation.test.tsx`，后端用 `test_finance_reconciliation_service.py` 验证对账服务。

## 4. 新增与迁移

1. 新增文件前，先核对各层已有的业务域和模块名。拆分已有模块时，按职责保留可追溯的文件主名。
2. 迁移源码或测试时，同步更新导入、测试 mock 和路径选测配置。拆分后端测试文件时，按[测试规范](testing/测试规范.md)同步清单、分组、功能映射和测试元数据台账。
3. 功能编号和既有测试编号随原功能、原用例保留。涉及自动化用例文件或名称的调整，重新生成统一用例库并核对编号映射。

前端目录与导航边界见[应用架构](应用架构.md)，测试分层与执行规则见[测试规范](testing/测试规范.md)。
