# 黑金时代发布流程

## 1. 发布链路

发布只从本地 `main` 推送云端 `main`，`dev` 不直接发布：

```text
dev（本地 5188/8123）
  → 本地验证
本地 main worktree（5199/8125）
  → 推送 origin/main
CI 门禁
  → 构建镜像并部署阿里云 ECS
```

当前本地 worktree：

| 用途 | 目录 | 分支 | 前端 | 后端 |
|---|---|---|---:|---:|
| 开发 | `/Users/aries/黑金时代` | `dev` | 5188 | 8123 |
| 发布验收 | `/Users/aries/黑金时代-main` | `main` | 5199 | 8125 |

发布基准以本地为准：本地 `dev` 是系统定义的最新代码，本地 `main` 是经过本地验证的发布基线。云端 `main` 只接受本地发布结果，不得反向覆盖本地分支；云端新增提交如需保留，必须逐项适配后再进入本地开发流程。

## 2. 发布前检查

必须满足：

- `dev` 的改动已提交，并已在 5188/8123 验证。
- 改动已合入本地 `main`。
- 本地 `main` 已在 5199/8125 完成回归和关键页面验收。
- `git status --short` 无意外未提交文件。
- 版本号不需要手动修改；自动发版会按提交类型升版并生成发布说明。
- 确认本次发布不会把本地开发库或生产数据导出到发布包。

## 3. 推送云端 main

在本地 `main` worktree 执行：

```bash
cd /Users/aries/黑金时代-main
git status --short --branch
git log -1 --oneline
git push origin main:refs/heads/main
```

不要从 `dev` 直接推送云端 `main`。

## 4. CI/CD

推送后由 GitHub Actions 执行：

```text
origin/main
  → 自动判断更新级别并生成 release 提交
  → 自动生成 RELEASE.md 与本轮提交摘要
  → lint-gate / frontend-gate / backend-gate
  → deploy-production
  → 阿里云 ECS Docker Compose
```

CI 通过 lint、前端检查/测试、前端构建和后端核心测试后自动发布；E2E 只按需手动运行，不作为发布门禁。

### 自动版本规则

自动发版根据本轮提交标题判断版本号：

| 提交类型 | 更新级别 | 示例 |
|---|---|---|
| `fix:`、`chore:`、`docs:`、`test:`、`ci:` | 小更新，patch +1 | `0.0.9 → 0.0.10` |
| `feat:` | 大更新，minor +1 | `0.0.9 → 0.1.0` |
| `feat!:`、`fix!:` 或包含 `BREAKING CHANGE` | 超级更新，major +1 | `0.0.9 → 1.0.0` |

每次自动发版都会：

- 把版本同步到后端、前端和根 `package-lock.json`；
- 在 `RELEASE.md` 写入本轮提交、Bug 修复、功能更新和发布时间；
- 在 GitHub Actions Summary 输出版本、提交清单、门禁耗时、部署耗时和最终结果。

因此，发布完成后需要把云端自动生成的 `chore(release): vX.Y.Z` 提交拉回本地 `main` 和 `dev`。

代码提交的 CI 门禁未全部通过时不得继续发布。不要绕过 CI 手工执行生产部署。

本轮有哪些提交、修复了什么 Bug、增加了什么功能，以 GitHub Actions Summary 和 `RELEASE.md` 为准。

## 5. 发布后同步本地 main 和 dev

CI 将云端 `main` 发布成功后，必须把发布结果同步回本地 `main`，再同步到本地 `dev`：

```bash
cd /Users/aries/黑金时代-main
git fetch origin main
git log --oneline main..origin/main
git merge --ff-only origin/main

cd /Users/aries/黑金时代
git merge main
```

如果快进失败或云端有本地没有的业务提交，先停止同步并逐项评估；不得强制覆盖本地 `main`、`dev` 或远端 `main`。同步完成后重新检查 5199/8125 和 5188/8123。

## 6. 阿里云 ECS 发布

生产部署目录：

```text
/opt/heijin/deploy
```

服务器约定：

- 前端通过 Nginx 对外提供 80/443。
- 后端只通过 Compose 内网访问。
- PostgreSQL 数据库端口只绑定本机，不开放公网。
- 生产密钥、数据库密码和 `.env` 不进入 Git 或发布包。

发布后在 ECS 现场检查：

```bash
ssh heijin-prod
cd /opt/heijin/deploy
docker compose ps
docker compose exec -T backend curl -fsS http://127.0.0.1:8123/api/v1/health
```

同时确认：

- backend、frontend、db 容器均为 healthy/running。
- 页面可以打开，登录和本次变更的关键路径可用。
- Alembic 版本、表数量和关键业务数据符合发布前基线。
- 发布前备份成功，备份文件和校验文件存在。

## 7. 数据库备份与回滚

正式备份使用 PostgreSQL 自定义格式：

```bash
cd /opt/heijin/deploy
bash scripts/backup_daily.sh
```

恢复必须使用仓库脚本，不要直接打包运行中的 PostgreSQL 数据目录：

```bash
bash scripts/restore_pg.sh --backup /opt/heijin/backups/<backup>.dump --yes
```

发生异常时：

1. 立即停止继续发布，不重复执行迁移或清库。
2. 保存 CI 日志、容器日志、健康检查和数据库版本信息。
3. 按当前版本的回滚说明恢复镜像或数据库。
4. 回滚后重新检查登录、关键读写路径和数据基线。

## 8. 安全边界

- 不在公网开放 8123、8125、5432 或 Docker API。
- `JWT_SECRET_KEY` 必须使用随机强密钥。
- 生产 `CORS_ORIGINS` 不允许使用 `*`。
- 不使用历史 SQLite 部署说明执行 PostgreSQL 正式发布。
- 发布流程有变化时，只更新本文件，历史版本放入 `docs/archive/`。
