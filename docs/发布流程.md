# 黑金时代发布流程

> 2026-11-11 更正：远端 `test` / `dev` 分支与 `auto-merge-test-to-main` 已删除，远端只剩 `origin/main`。`test` 从来不是测试环境，旧链路推送它会直接触发生产发布；`git push origin main:refs/heads/test` 已失效，照做既不会发布，也绝不能当作验收。

## 1. 发布链路

发布只从本地 `main` 推送到 `origin/main`，`dev` 不直接推送远端：

```text
dev（本地 5188/8123）
  → 本地验证并提交
本地 main worktree（5199/8125）
  → 合并 dev、回归与关键页面验收
  → git push origin main
GitHub Actions 门禁
  → deploy-production（push main 自动触发）
  → 阿里云 ECS 原地增量升级
```

当前本地 worktree：

| 用途 | 目录 | 分支 | 前端 | 后端 |
|---|---|---|---:|---:|
| 开发 | `/Users/aries/黑金时代` | `dev` | 5188 | 8123 |
| 发布验收 | `/Users/aries/黑金时代-main` | `main` | 5199 | 8125 |

发布基准以本地为准：本地 `dev` 是系统定义的最新代码，本地 `main` 是经过本地验证的发布基线。远端 `origin/main` 是**唯一远端分支，也是生产发布分支**，只接受本地发布结果，不得反向覆盖本地分支；若远端出现本地没有的提交，必须逐项适配后再进入本地开发流程。

**`push origin main` 等同发布生产**：不要用它做验证性推送。`deploy-production` 对 `push main` 没有路径过滤，连只改 `RELEASE.md` 的提交也会触发生产部署。

## 2. 发布前检查

必须满足：

- `dev` 的改动已提交，并已在 5188/8123 验证。
- 改动已合入本地 `main`。
- 本地 `main` 已在 5199/8125 完成回归和关键页面验收。
- `git status --short` 无意外未提交文件。
- 版本号三处一致（`scripts/ops/bump_version.sh --check`）、迁移、测试和 `RELEASE.md` 的当前版本章节已同步。
- 涉及数据库结构或种子的版本，已按当期《生产上线执行单》（每次上线现场产出，本仓不维护通用版）完成 ECS 现场前置检查（备份 → 演练 → `schema_diff.py` 差异核对 → 主键体检），不能靠 CI 自动部署代替。
- 确认本次发布不会把本地开发库或生产数据导出到发布包。

## 3. 推送 origin/main（等同发布生产）

在本地 `main` worktree 执行：

```bash
cd /Users/aries/黑金时代-main
git status --short --branch
git log -1 --oneline
git push origin main
```

不要从 `dev` 直接推送 `origin/main`。旧命令 `git push origin main:refs/heads/test` 已失效：远端无 `test` 分支、也无自动合并工作流，执行它只会新建一条孤立远端分支，不触发任何部署。

## 4. CI/CD

推送后由 GitHub Actions 执行（各门禁的实际触发范围以 workflow 文件 `on:` 为准）：

```text
origin/main（push）
  → lint-gate / frontend-gate / coverage-gate / e2e-gate / backend-gate
  → deploy-production：构建镜像 → 上传 ECS → deploy.sh 原地增量 → 健康检查 → 打 tag
```

- `deploy-production` 由 `push main` 自动触发，也可用 `workflow_dispatch` 手动补发 / 验证；`rollback.yml` 是手动一键回滚入口。
- `deploy.sh` 默认不清库（`RESET_DATABASE=false`），内置 B4 售出表单作用域补齐与升级前后库状态不变量自检，任一校验失败即中止发布；`reset_database=true` 只用于全新数据库初始化，正式升级禁止启用。
- 结构性升级（DDL / 种子 / 字段数变化）按当期《生产上线执行单》在 ECS 现场做**原地增量**：备份 → 演练 → 用新代码跑 `schema_diff.py` 只补缺失 → `APP_VERSION` 换镜像 → **换镜像之后**再做结构比对（旧容器没有新代码）。本仓 `docs/archive/` 只有已作废旧版执行单，不得照做；CI 部署只负责换镜像与自检，不代替执行单的现场抄录、B4 与主键体检等步骤。
- 门禁未全部通过时不得继续发布；CI 失败按第 7 节处置，不要绕过门禁重复执行部署脚本。

## 5. 发布后同步回本地 dev

远端 `main` 就是本次 push 的源，本地 `main` 无需再同步；只需把发布结果带回 `dev`，避免分叉：

```bash
cd /Users/aries/黑金时代
git fetch origin main
git log --oneline main..origin/main   # 正常应为空
git merge main
```

如果 `origin/main` 出现本地没有的业务提交，先停止同步并逐项评估；不得强制覆盖本地 `main`、`dev` 或远端 `main`。同步完成后重新检查 5199/8125 和 5188/8123。

## 6. 阿里云 ECS 发布

生产部署目录：

```text
/opt/heijin/deploy
```

服务器约定：

- 前端通过 Nginx 对外提供 80/443。
- 后端只通过 Compose 内网访问。
- PostgreSQL 数据库端口只绑定本机，不开放公网。
- 生产密钥、数据库密码和 `.env` 不进入 Git 或发布包。

发布后在 ECS 现场检查：

```bash
ssh heijin-prod
cd /opt/heijin/deploy
docker compose ps
docker compose exec -T backend curl -fsS http://127.0.0.1:8123/api/v1/health
```

同时确认：

- backend、frontend、db 容器均为 healthy/running。
- 页面可以打开，登录和本次变更的关键路径可用。
- Alembic 版本、表数量和关键业务数据符合发布前基线。
- 发布前备份成功，备份文件和校验文件存在。

## 7. 数据库备份与回滚

正式备份使用 PostgreSQL 自定义格式：

```bash
cd /opt/heijin/deploy
bash scripts/backup_daily.sh
```

恢复必须使用仓库脚本，不要直接打包运行中的 PostgreSQL 数据目录：

```bash
bash scripts/restore_pg.sh --backup /opt/heijin/backups/<backup>.dump --yes
```

备份保留窗口已统一为默认 7 天（`backup_daily.sh` / `backup_local.sh` / `pull_backup.sh` / `pg_pitr_backup.sh` 与 CI artifact 均默认 7）；ECS `/opt/heijin/backups/` 是唯一权威副本，本地副本已清退，无异地兜底。恢复前确认 dump 与 `.sha256` 校验文件都在。

发生异常时：

1. 立即停止继续发布，不重复执行迁移或清库。
2. 保存 CI 日志、容器日志、健康检查和数据库版本信息。
3. 按当前版本的回滚说明恢复镜像或数据库。
4. 回滚后重新检查登录、关键读写路径和数据基线。

## 8. 安全边界

- 不在公网开放 8123、8125、5432 或 Docker API。
- `JWT_SECRET_KEY` 必须使用随机强密钥。
- 生产 `CORS_ORIGINS` 不允许使用 `*`。
- 不使用历史 SQLite 部署说明执行 PostgreSQL 正式发布。
- 禁止 push 到已删除的 `test` 分支，或新建临时远端分支代上线。
- 发布流程有变化时，只更新本文件并同步 `docs/README.md` 的登记描述；历史发布事实以 `RELEASE.md` 为准，不再把旧版流程复制进 `docs/archive/`。
