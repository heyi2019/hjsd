# 发布流程

> 本文覆盖从云端 `dev` 发布到 `main`、阿里云 ECS 上线检查及回滚。开发见 [研发流程](研发流程.md)，测试见 [测试流程](测试流程.md)，版本规则和记录见 [版本管理](版本管理.md)。

> **推送 `origin/main` 等同生产上线，必须由用户明确指示，不得作为常规步骤自动执行。**

## 1. 发布到 origin/main

### 1.1 发布前检查

- 待发布的 `dev` 改动已提交并推送，在 `5188/8123` 完成相关测试和关键页面验收；如提前手动运行了云端门禁，核对其结果。
- 工作区无意外未提交文件；核对云端 `dev` 和 `main` 的提交及差异，确认实际发布范围。若 `main` 有 `dev` 不包含的提交，先评估并制定处理方案，不覆盖或强推。
- 先按 [版本管理](版本管理.md) 给用户版本建议和本次更新清单；用户指定版本时，更新 `VERSION` 并在发版准备提交中记录 `Release-Version: x.y.z`。
- 确认本次发布不会把本地开发库或生产数据导出到发布包。
- 涉及表单字段 / 种子 / 数据库结构的版本，已备齐 ECS 现场当期执行单，并确认现场能执行 `backend/scripts/split_sale_form_scopes.py`（B4）。
- 包含事件资金流水订单关联调整的版本，在切换新代码前对目标库执行 `PYTHONPATH=. python scripts/backfill_event_cashflow_order_id.py`（工作目录为 `backend`）。若脚本报告无法关联的流水，先修复来源数据再发布；脚本在同一事务中回填，不会保留部分结果。
- **V1.0.0 本次例外**：用户已确认将阿里云 `heijin_erp` 重建为空库，仅初始化结构、基础配置和管理员，不导入原生产或本地业务数据；发布准备提交必须按第 1.4 节写明一次性重建标记。其他版本仍按原地增量发布。

### 1.2 推送

`dev` 不直接部署。取得用户明确发布指示后，在云端将已核对的 `dev` 内容合入 `main`；更新 `main` 会触发生产发布。合入前再次确认目标分支、提交和发布范围；不得创建本地 `main` 分支或 worktree，也不得强推。若无法安全合入，停止并先处理差异。

### 1.3 CI/CD 与自动版本规则

推送后由 `main-ci-cd.yml`（push `main` 唯一触发点）执行自动发版与发布链路：

```text
origin/main（push）
  → main-ci-cd：使用用户指定版本或按提交类型判断级别，生成 chore(release) 提交并推回 main
  → 并行调用三道门禁，均检出并验证同一个 release sha
  → 三道门禁全部成功后调用 deploy-production，构建镜像、上传并部署到 ECS
  → 健康检查成功后，记录实际发布日期和时间
```

| 提交类型 | 更新级别 | 示例 |
|---|---|---|
| `fix:`、`chore:`、`docs:`、`test:`、`ci:` | 小版本，加 `0.0.1` | `0.0.9 → 0.0.10` |
| `feat:` | 大版本，加 `0.1.0` | `0.0.9 → 0.1.0` |
| `feat!:`、`fix!:` 或含 `BREAKING CHANGE` | 超大版本，加 `1.0.0` | `0.0.9 → 1.0.0` |

项目根目录的 `VERSION` 是唯一发布版本，前后端不单独维护版本号。用户指定的版本优先于自动级别；发版准备时在 [版本管理](版本管理.md) 写入待发布记录和本轮提交，部署与健康检查成功后记录实际发布日期和时间。GitHub Actions Summary 输出版本、提交清单和门禁结果。

- `deploy-production` 由 main-ci-cd 调用或手动触发，**不由 push 直接触发**。自动发布以作业依赖等待门禁，不占用 runner 轮询。
- 手动部署选择等待门禁时，需要在目标提交上单独触发并通过三道独立门禁；自动发布的可复用门禁不会产生可供此轮询识别的独立运行记录。
- `coverage-gate` / `e2e-gate` 已下线；`frontend-gate` 的全量模式包含真实后端浏览器 E2E，生产重建时必须执行。
- `chore(release)` 推回会二次触发 main-ci-cd，工作流已加跳过保护，不会重复升版或重复部署。
- 三个门禁未全绿时不得继续发布；不要绕过 CI 手工执行生产部署。
- 门禁在云端 `main` 更新后执行；若失败，生产不会部署，但 `main` 已包含本次提交，修复前需保留并检查失败记录。

### 1.4 V1.0.0 一次性空库重建

1. 发布前在服务器受限的 `deploy/.env` 中配置管理员初始密码 `ADMIN_PASSWORD`（至少 8 位），不要把密码写入代码、提交、发布记录或日志。空库会创建 `admin` 管理员；原有订单、库存、客户、用户及自定义配置不会导入。
2. 经用户发布指示、完成本地验收后，在发布准备提交的**正文**同时写入以下两行，确保这次自动发布选择空库重建：

   ```text
   Release-Version: 1.0.0
   Reset-Production-Database: empty
   ```

3. 发布工作流仅接受 V1.0.0 的该标记；V1.0.0 缺少标记时会中止，不会悄悄按增量发布。工作流运行前后端全量测试并等待三道门禁全绿后上传，先停止前后端写入，生成独立备份并校验，再只重建 `heijin_erp` 数据库；其他数据库及附件数据卷保留。
4. 使用活动迁移 `0001` 初始化结构、业务类型、默认资金账户、选项和表单基础配置，再创建管理员并检查服务。旧业务数据和旧用户不会写入新库。
5. 重建开始前会在服务器保存一次性状态标记；同一版本重试不会再次清库。若重建过程中失败，保留备份和标记，检查现场后再处理；不要反复触发重建。

常规发布不设置重建标记，继续按原地增量执行。

## 2. 发布后核对

核对三道门禁、部署和健康检查结果，记录实际发布版本及提交。获取云端 `main` 和 `dev` 的最新状态，检查自动生成的版本记录及分支差异；`origin/dev` 仍是开发主线，不以 `main` 反向覆盖本地代码。若发布产生需要带回 `dev` 的版本信息或其他差异，先逐项评估并采用安全方式处理，不得强推或用 `reset --hard` 覆盖提交。

## 3. 阿里云 ECS 部署与现场检查

生产部署目录 `/opt/heijin/deploy`。前端通过 Nginx 提供 80/443，后端只经 Compose 内网访问，PostgreSQL 端口只绑本机，不开放公网；生产密钥、数据库密码和 `.env` 不进入 Git 或发布包。

发布后在 ECS 现场检查：

```bash
ssh heijin-prod
cd /opt/heijin/deploy
docker compose ps
docker compose exec -T backend curl -fsS http://127.0.0.1:8123/api/health
```

同时确认：

- backend、frontend、db 和 rate-limit 容器均为 healthy/running；客户限流配置使用外部 Redis 时，也必须验证后端连接实际指向的 Redis：

  ```bash
  docker compose exec -T backend python3 -c 'from app.core.settings import get_settings; from redis import Redis; assert Redis.from_url(get_settings().customer_rate_limit_redis_url, socket_connect_timeout=2, socket_timeout=2).ping(); print("客户限流 Redis 连接正常")'
  ```
- **B4 不在 `deploy.sh` 内自动执行**：已有库升级须在 ECS 现场按当期执行单手动跑 `backend/scripts/split_sale_form_scopes.py`，并核对 SALEREC / SALETH / SALEDG 三份字段集非空；`deploy.sh` 只做发布前后只读不变量校验。
- 页面可打开，登录和本次变更的关键路径可用。
- Alembic 版本、表数量、主键约束（`pg_constraint.contype='p'`）和关键业务数据符合发布前基线。
- 发布前备份成功，备份文件和校验文件存在。

**常规上线采用原地增量**：先备份，在演练库恢复并进行结构比对；发现差异时先制定并核实迁移方案，再部署新镜像、按方案执行迁移并复核结构和数据。`schema_diff.py` 只读比对，不会补齐缺失结构，且只接受 `heijin_erp_drill_` 开头的演练库。V1.0.0 本次空库重建按第 1.4 节执行。

## 4. 数据库备份与回滚

正式备份使用 PostgreSQL 自定义格式，不要直接打包运行中的 PostgreSQL 数据目录：

```bash
cd /opt/heijin/deploy
bash scripts/backup_daily.sh
```

数据库恢复会覆盖当前库并短暂停止后端；确认确需恢复、目标库和备份文件均正确后，使用仓库脚本执行：

```bash
cd /opt/heijin/deploy
bash scripts/restore_pg.sh --backup /opt/heijin/backups/<backup>.dump --yes
```

发生异常时：

1. 立即停止继续发布，不重复执行迁移或清库。
2. 保存 CI 日志、容器日志、健康检查和数据库版本信息。
3. 按当前版本的回滚说明恢复镜像或数据库。
4. 回滚后重新检查登录、关键读写路径和数据基线。

## 5. 安全边界

- 不在公网开放 `8123`、`8125`、`5432` 或 Docker API。
- `JWT_SECRET_KEY` 必须使用随机强密钥；生产 `CORS_ORIGINS` 不允许使用 `*`。
