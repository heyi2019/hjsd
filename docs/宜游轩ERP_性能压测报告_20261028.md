## 四、写入路径压测（POST /orders 建单）——修复闭环

| 场景 | 修复前 | 修复后终态 |
|------|--------|-----------|
| 串行 20 单 | p50 5.7ms，100% 成功 | p50 6.2ms，100% 成功（无回归） |
| 10 并发 × 5 轮 | **13/50 成功，37 失败 500** | **50/50 成功，0 失败** |
| 并发 p50 / p95 | 41.0 / 86.5ms（13 个幸存者偏差） | 61.4 / **207.2ms**（真实锁排队，全员成功） |

- **根因**：`core/numbering.py::allocate_number` 「SELECT→Python+1→UPDATE 绝对值写」，SQLite 忽略 `with_for_update`，并发发出重复单号撞 `orders.order_no` 唯一约束（日志取证 39 次）。
- **修复**（commit `800faea`）：单语句**条件相对递增 + RETURNING**（`SET current_value=current_value+1 WHERE current_value<max RETURNING`），SQLite 单写锁天然串行；上限校验进 WHERE，超限零消耗，`SEQUENCE_EXHAUSTED` 语义不变；需 SQLite ≥ 3.35（venv 实测 3.53.4）。
- **回归锁**：`test_numbering.py` 新增 8 线程 × 3 全周期唯一性用例（独立 WAL 文件库）；单跑 7/7、+m2 组合 20/20。
- 注：修复后并发 p95 207ms 是 50 个请求全部含锁等待的真实水位，仍远低于 500ms SLA；修复前 86.5ms 只统计了 13 个幸存请求。

## 六、容量规划（按生产 2 核修正）

- **当前形态可承载**：~10 VU（p95 < 1s）；30 VU 开始排队；50 VU p95 8s（压测机实测）。
- **2 核服务器预估**：饱和点前移至 ~20–30 VU；p95 在 50 VU 下预计 12–16s。
- **2 核上的部署建议**：
  1. `uvicorn --workers 2`（每核 1 worker）+ 前端 Nginx/Caddy 静态托管——CPU 利用率翻倍；
  2. SQLite 单写者模型下多 worker 读没问题、写仍串行（取号已改为相对递增，写冲突安全）；
  3. 弃用 `--reload`（watchfiles 常驻开销 + 非生产形态）；
  4. 登录 PBKDF2 44ms/次在 2 核上占比更高，建议登录接口限流（如 10 req/min/IP）。
- **10x 目标判定**：2 核 + SQLite + Python 全量报表，当前架构**不满足** 10x；数据量过万行后报表端点将劣化至秒级（单请求基线已有 108ms 尾部）。

## 七、优化建议（分级，V1.2 终态）

1. ✅ 取号竞态——已修复（`800faea`）+ 复测 50/50 + 回归测试锁死。
2. ✅ 8123 双进程——已收敛单实例。

**P1（下一步，高峰容量主矛盾）**

**P2（长期）**
5. 显式 `PRAGMA busy_timeout`（当前依赖 python sqlite3 默认 5s）。
6. 登录限流；`/accounts` 尾部延迟顺带观察。
