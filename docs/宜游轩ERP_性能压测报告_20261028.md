## 四、写入路径压测（POST /orders 建单）

| 场景 | 结果 |
|------|------|
| 串行 20 单 | 100% 成功，p50 5.7ms，p95 29ms |
| 10 并发 × 5 轮（50 单） | **仅 13 成功，37 失败（74%）HTTP 500** |

**根因链（已取证 `/tmp/heijin_backend_8123.log`，39 次 `UNIQUE constraint failed: orders.order_no`）：**

`core/numbering.py::allocate_number` 采用「SELECT current_value → Python +1 → UPDATE 绝对值写入」：
1. SQLite 忽略 `with_for_update()`（代码注释也自认仅 PG 有效）；
2. 两个并发事务都读到同一个 `current_value=N`，各自算出 N+1；
3. 后提交者在 `orders.order_no` 唯一约束上炸掉，异常未捕获 → 裸 500；
4. `get_db` 无 `busy_timeout`、写事务非 `BEGIN IMMEDIATE`，跨进程（见发现#2）下同样存在 SQLITE_BUSY 500 风险。

**修复方向（待裁决，未擅自改码）**：
- 写事务改 `BEGIN IMMEDIATE`（engine 层或写路径显式开启）；
- UPDATE 改相对递增 `current_value = current_value + 1`，消除绝对值覆盖；
- 或捕获 IntegrityError → 409/有限重试。
- 另建议统一：`PRAGMA busy_timeout`（如 5000ms）兜底。

## 七、优化建议（分级）

**P0（立即，正确性+环境）**
1. 修 `allocate_number` 取号竞态（BEGIN IMMEDIATE + 相对递增 + IntegrityError 兜底），并发建单 500 是数据正确性缺陷，不只是性能问题。
2. 裁决并清理 8123 双进程，收敛唯一启动入口。

**P1（高峰容量）**
3. 生产/高峰形态弃用 `--reload` 单进程：多 worker 或多实例只读分离；SQLite 下建议「单写多读」或迁移 PG 后再水平扩。
4. 报表热点改 SQL 端聚合：`quality/metrics`（全表加载 reconciliation/cashflow/schedule/event/attachment 五张表再 Python 过滤）、`r5_business_pnl`（`select(Order, OrderEvent)` 全量 ORM 水合）、`order_profit`。当前 8k 行尚可（基线 <50ms），按增速预计数万行时将劣化至秒级。
5. SQLite `busy_timeout` + 写路径重试，杜绝跨进程锁冲突裸 500。

**P2（长期）**
6. 登录 PBKDF2 76ms×高并发占 CPU：登录接口限流即可，无需降强度。
7. `/accounts` 列表尾部延迟（93ms）纳入下次报表聚合改造顺带观察。

## 九、P0 修复与复测验证（V1.1，2026-10-28 06:00）

### 9.1 修复内容

**① 取号竞态（P0-1，已修复并提交）**
`app/core/numbering.py::allocate_number` 由「SELECT 读值 → Python +1 → UPDATE 绝对值写」改为**单语句条件相对递增 + RETURNING**：
- `UPDATE ... SET current_value = current_value + 1 WHERE sequence_key = ? AND current_value < max RETURNING current_value`——SQLite 单写锁天然串行，后到者等前者提交后拿到 +1 后的值；
- 上限校验进 WHERE：超限零命中、不消耗号，`SEQUENCE_EXHAUSTED` 语义不变；
- 需 SQLite ≥ 3.35（后端 venv 实测 3.53.4 ✅）。

**② 8123 双进程收敛（P0-2，已执行）**
终止 PID 47538（127.0.0.1，早前会话临时拉起、/tmp 日志），保留 PID 807（0.0.0.0，LAN E2E 依赖，项目 logs）。本机流量回落 807 实测正常。

### 9.3 回归测试

- `tests/v1/test_numbering.py` 新增 `test_concurrent_allocation_is_unique`：8 线程 × 3 次全周期取号（独立 WAL 文件库，与生产 journal 模式一致），断言 24 号全唯一且连续；
- 既有语义 6 用例全保：递增、跨类型独立、回滚空洞不复用、超限不消耗、peek 不消费、未知序列拒绝；
- 实测：单跑 7/7 过；`test_numbering.py + test_m2.py`（服务层取号链路）组合 20/20 过。
- **测试基建教训**：conftest 的 `v1_engine` 是 `journal_mode=MEMORY`，多连接「读锁升级写锁」会死锁假象且污染后续用例——并发类测试必须自带 WAL 独立库。
