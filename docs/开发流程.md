# 黑金时代开发流程

## 1. 分支与本地环境

开发与发布使用两个本地 worktree：

| 用途 | 分支 | 目录 | 前端 | 后端 | 本地数据库 |
|---|---|---|---:|---:|---|
| 日常开发与验证 | `dev` | `/Users/aries/黑金时代` | `5188` | `8123` | `heijin_erp_dev` |
| 合并后验收与发布 | `main` | `/Users/aries/黑金时代-main` | `5199` | `8125` | `heijin_erp_dev` |

访问地址：

- `dev` 前端：http://127.0.0.1:5188/
- `dev` 后端文档：http://127.0.0.1:8123/docs
- `main` 前端：http://127.0.0.1:5199/
- `main` 后端文档：http://127.0.0.1:8125/docs

两套环境代码和端口隔离，但当前共用 `heijin_erp_dev` 数据库。涉及写入数据的验证会被两套环境看到，不能把该数据库当作数据隔离环境。`heijin_erp_test` 与 `heijin_erp_e2e` 分别由后端单测夹具与 E2E 夹具使用；`heijin_erp_release` 库已下线，禁止引用。

### 系统基准

- 本地 `dev` 是系统定义的最新代码基线，开发、修复和功能判断以本地代码为准。
- 本地 `main` 是由本地 `dev` 验证后形成的发布基线。
- **远端只剩 `origin/main`，它就是生产发布分支**；`origin/test`、`origin/dev` 与 `auto-merge-test-to-main` 已于 2026-11-11 删除。推送 `origin/main` 等同生产上线，不得用于验证性推送。
- 远端存在本地没有的提交时，只能逐项检查后选择性适配；禁止用远端强制覆盖本地分支，禁止新建 `test` 等临时远端分支代上线。

## 2. 日常开发

始终在 `dev` worktree 修改代码：

```bash
cd /Users/aries/黑金时代
git switch dev
```

前后端常驻服务会自动重载代码。开发时只使用 `5188/8123` 验证：

```text
前端：http://127.0.0.1:5188/
后端健康检查：http://127.0.0.1:8123/api/v1/health
```

功能完成后，先按 [测试流程](测试流程.md) 完成开发环境验证，再提交 `dev`：

```bash
cd /Users/aries/黑金时代
git status
git add <changed-files>
git commit -m "<message>"
```

## 3. 将 dev 合并到本地 main

验证通过后，在 `main` worktree 合并 `dev`：

```bash
cd /Users/aries/黑金时代-main
git status
git switch main
git merge dev
```

如果发生冲突，解决并完成合并后再继续；无法安全处理时使用：

```bash
git merge --abort
```

合并完成后，在 `5199/8125` 环境按 [测试流程](测试流程.md) 做一次 main 验收。

## 4. 由本地 main 推送 origin/main 发布

`dev` 不直接推送远端。确认本地 `main` 验收通过、且已完成 [发布流程](发布流程.md) 的发布前检查后，在 `main` worktree 执行：

```bash
cd /Users/aries/黑金时代-main
git status
git log -1 --oneline
git push origin main
```

推送后由 GitHub Actions 执行门禁和部署：

```text
origin/main（push）
  → lint-gate / frontend-gate / coverage-gate / e2e-gate / backend-gate
  → deploy-production（自动构建镜像并部署 ECS）
```

- 没有 `test` 分支，也没有 `test → main` 的自动合并；`push origin main` 直接触发生产部署，`deploy-production` 无路径过滤，纯文档提交同样会部署。
- 涉及数据库结构或种子的版本，按当期《生产上线执行单》（每次上线现场产出，本仓不维护通用版）在 ECS 现场做原地增量前置检查，CI 部署不代替执行单。
- 不要手工把 `dev` 推到远端，也不要绕过门禁直接在生产环境重复执行部署脚本。

## 5. 发布后把 origin/main 同步回 dev

远端 `main` 就是本次 push 的源，本地 `main` 无需再同步；只需把发布结果带回 `dev`：

```bash
cd /Users/aries/黑金时代
git fetch origin main
git log --oneline main..origin/main   # 正常应为空
git merge main
```

如果发现 `origin/main` 包含本地没有的业务提交，立即停止并先建立备份引用；逐项评估后再适配，不要使用 `reset --hard` 覆盖本地提交，也不要强推远端。`dev` 同步冲突时同样暂停，解决后重新执行 [测试流程](测试流程.md)。

## 6. 常用检查

```bash
# 查看两个 worktree
git -C /Users/aries/黑金时代 worktree list

# 查看 dev 状态
git -C /Users/aries/黑金时代 status --short --branch

# 查看 main 状态
git -C /Users/aries/黑金时代-main status --short --branch
```
