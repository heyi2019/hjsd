## 1. 文档边界

本字典定义**新业务的固定物理契约**，事实来源为 `backend/app/domain/` 下的 ORM 模型与 `app/domain/enums.py`。任何与本文冲突的旧 PRD、旧迁移说明、旧测试报告均以本文为准。

历史资料仅按迁移映射以参考记录导入；历史列、旧表和脏值**不得**扩展或改变以下结构。字段名一律取数据库物理名，表名一律取 `__tablename__`。

**生成方式**：本文 §2/§3/§4 由脚本反射 SQLAlchemy `Base.metadata` 与 `enums.py` 全量实测生成（v2.6），逐表逐字段与 ORM 零漂移。业务口径裁决（§8 及各类约束说明）为长期有效的人工约定，不随字段增删改变。

**中文映射规则**：所有物理标识符统一以 `英文（中文）` 内联标注，四类全覆盖——§2 表名（34 张现役表）、§3 枚举类名（35 个）与枚举取值、§4 字段名（300 个业务字段）。§4 字段按业务语义译名；§3 枚举取值中文优先取前端 `labels.ts` 权威文案源（如 `ACCOUNTING_ATTRIBUTE_LABEL`、`FUND_FLOW_SOURCE_LABEL`），无前端文案的按业务语义给出；同名不同义的取值（如 `OPEN`/`ACTIVE`）按枚举类分别限定，不共用一张表。代码物理名始终是检索键与接口值，中文仅供阅读，不替代物理名。公共审计列（`id` / `created_by` / `updated_by` / `created_at` / `updated_at`）与非 ORM 的迁移表（`alembic_version` / `db_version`）不逐项标注。

## 5. 编号规则

序列定义在 `document_sequences`，由 `app/core/numbering.py` 发放，**唯一、不可改、不可复用，不强制无断号**。

| 对象      | 格式                       | padding |
| ------- | ------------------------ | ------- |
| 业务订单    | `HS` / `TH` / `DG` + 流水号 | 4       |
| 客户      | `CUS0001`                | 4       |
| 合作方     | `CP0001`                 | 4       |
| 客户需求    | `REQ0001`                | 4       |
| 通知      | `NTF0001`–`NTF9999`      | 4       |
| 附件      | `ATT0001`                | 4       |
| 资金流水·支出 | `ZC00001`                | 5       |
| 资金流水·收入 | `SR00001`                | 5       |
| 库存      | `KU_00001`               | 5       |
| 返点记录    | `HS0001-RB01`            | —       |

订单编号域随业务动态生成（`ensure_sequence` 按 `order_type_defs.sequence_key/prefix`）；`ORDER_DFQ` 已随代分期下线删除。库存编号在建 BUY 事件（HS/TH）或建单（DG）时发放。返点记录编号为 `HS0001-RB01`，其资金流水按收支方向使用 `ZC`/`SR` 全局流水号；`rebate_settlements` 表已于 2026-11-05 下线。

通知编号不得超过 `NTF9999`，不会复用；其余序列的 padding 为最小位数。通知编号不足时，产生通知的操作会整体回滚并提示管理员处理，不会漏记通知或只保存部分业务数据；部署前应先检查各环境通知序列及现有编号。

## 6. 活字段边界

**可配置**：标签、渠道等级、账号卖点、预计上架日、客户偏好、客户来源细分、预算、常用平台、跟进备注、合作方备注。

**不可配置**：客户编号、称呼/昵称、微信号、QQ、手机号、订单参与关系、金额、池、收支方向、事件/业务类型、正式关联、库存/利润/应收计算字段。

参与核算的活字段必须升格为固定字段。活字段按 `order_form_fields`（定义）+ 各表 `form_extra`（值）落地，八类实体作用域见 §3.2。

客户新建时以微信号、QQ、手机号查询重复候选并返回提示，**不强制拦截**；仅管理员可合并，合并迁移订单参与关系、分期客户关系、需求与引用，来源置 `MERGED` 并保留原编号与完整审计。

## 7. 分润配置边界

多人利润分配仅保存归属配置，不创建资金流水；公司分润比例可在设置中调整，默认盈利 40% / 亏损 50%，已有订单按原人员占比实时重算。返点金额唯一取登记值，费率只留痕不反推。


固定不可配置项：DG 代挂沿用统一 `SELL` 事件登记卖出金额与订单利润，寄售方经 `CONSIGNOR` 关联，不配抽成比例或单独结算公式。

多人分配规则：`order_profit_allocations` 的 `allocation_type` 表示分润归属（`BUY` / `SELL` / `OPERATION`）或 `COMPANY`（不绑人），`role` 取 `AllocationRole`；分配基数按订单全部收入与支出计算，返点已包含在收入中，不重复加计；买号/售出执行人自动绑定不可手改；四项合计必须 100%。

## 8. 口径裁决（长期有效）

1. 利润 = 单订单全部收入 − 全部支出（可正/负/0），权威原语 `shared/order_amounts.py::order_cashflow_profit`；收入 = 流水 IN + 返点，支出 = 流水 OUT + 分期坏账 + 分期回收的非现金库存成本；返点是收入「其中项」禁止再加；月度经营损益的「其中返点」独立 `sum(RebateRecord.amount)`。
2. 金额一律 `DECIMAL(18,2)` / `Amount`，禁止 float；有流水的池、历史字段和核心凭证禁止物理删除，只能停用 / 取消 / 冲销修正。订单和库存凭证均保留；历史删除接口拒绝删除，不能级联清除事件、流水、返点、押金或分期记录。
3. `total` 语义 = 成交总额（gross），不等于 principal + profit。
4. 返点关联用业务编号：返点事件的 `order_events.source_type='REBATE'`、`source_id=rebate_no`（形如 `HS0001-RB01`），替代旧口径事后回填 `form_extra['rebate_record_id']`；审计 `entity_id` 与流水 `source_id` 同用业务编号，不用数据库自增主键。
5. 资金只到池一级，系统余额为池内流水有符号和（排除押金损失重分类流水，与资金总览 `cash_balance` 同源，见第 12 条），无「开户余额」概念。支出和内部划转不受当前余额限制，余额允许为负；内部划转仍须原子生成等额的一出一入流水。
6. 分期按钮可用性由后端 `installments/action_availability.py` 计算并随 `available_actions` 下发给前端回显；前端不按状态数组自行判定。未指定收款期次时按到期日、期号顺序选择有剩余应收的期次；已收款或无剩余应收的期次不能减免或展期。最后一个逾期期次通过收款、减免或展期消除后，尚未结清的合约按是否已有收款恢复待收或进行中；违约合约保持违约状态。新收款的动作操作人与对应资金流水逐笔关联，修改时同步更新并遵守资金账户范围；无法可靠反推单笔流水的历史期次汇总保留为只读。
7. 蹭点→DG；氪金联盟提号/氪金提号/提号→TH；小荷包/经营池→`HJ_INVEST`；介绍费、作图费等支出统一登记为 `cashflow` 的 `OUT`，按资金原因和来源业务关联，不新增账号附加 `COST`；八月利润转 `UNLINKED_TRANSFER`，无原始凭证不补另一侧。
8. 导入订单一律不自动匹配账号（`account_id` 留空），由人工后续补录；不阻塞新单上线。v2.8 已删除 `link_status` 关联状态字段，不再以状态标签标记配对质量。
9. 迁移活动链只有活基线 `0001`（`create_all` + `seed_catalog`）：改 ORM 即改基线、加内置字段改 `catalog_seed.py` blob，**不再加增量迁移**；结构落后的库不得 `stamp`。上线是原地增量补缺失，不是覆盖重建。已有库的默认资金账户唯一索引和工作室押金订单约束，通过 `backend/scripts/ensure_funds_constraints.py --apply` 在显式指定 `ERP_CONSTRAINT_DATABASE_URL` 后补齐；脚本先锁表检查历史数据，发现异常即停止，不自动修改历史记录。
10. `game_password` 明文存储为既定裁决，不加密、不脱敏。
11. 押金分两类并各自归账簿（v3.2）：业务押金（`BUSINESS`，入驻平台 / 房租等保证金，登记在 `counterparty_id`、`source_order_id` 可选）与工作室运营押金（`STUDIO`，禁挂 `source_order_id`），由 `deposits.ledger_type` 区分，占用/释放/损失/取消四条派生流水同账簿；两类都不进损益、不二次扣减可用余额（STUDIO 押金同样不进工作室收支面板）；工作室侧日常运营收支仍走「工作室支出」页。
12. 余额快照（`FIN-01-05`，v3.3）：创建对账时立即固化当时截至对账日期的系统余额到 `balance_snapshots`，并非日终快照；判重键 `(pool_id, snapshot_on)`，同池同日多账户对账只保留首次快照（历史台账不可篡改、不回改）。允许更正已对账期间的流水和押金，原对账与首次快照保持不变；可通过只读 `GET /balance-snapshots` 查询。**对账 `system_balance` 与资金总览 `cash_balance` 同口径**：均经 `business_cashflow_filter()` 排除「押金损失重分类流水」（`DEPOSIT + OUT + 非 DEPOSIT_HOLD`），因押金损失 = −利润、不是第二笔现金流出。
13. 数据中心利润 = 当前已售出账号在所选期间的订单收支净额 + 所选期间工作室其他收入 − 所选期间工作室成本；在途成本是所选期间入库且目前仍在库的成本，押金占用为当前值。月度经营利润 = 期间订单收入 + 工作室其他收入 − 订单支出 − 运营费用；工作室收支及其冲销按流水发生日期归期，返点已包含在订单收入中，不重复加计。
14. `POST /cashflows`、`POST /orders/{id}/cashflows` 和 `POST /orders/{id}/events` 支持 `Idempotency-Key`。同一用户、同一接口目标和同一键重试时，返回该次提交的结果，余额和流水只变更一次。同一键的请求内容变更时返回 `409 IDEMPOTENCY_KEY_CONFLICT`。不同的提交键代表独立操作。

分期逾期回收时，未收应收计入原合约坏账，手填回收成本形成新库存和新订单的非现金成本，不生成资金流水。重售在新订单核算并自动关联原合约，原有分润配置不重算。
