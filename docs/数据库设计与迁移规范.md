# 宜游轩 ERP · 数据库设计与迁移规范

## 版本记录

| 版本 | 日期 | 变更摘要 |
|---|---|---|
| v2.0 | 2026-11-10 | 合并原《数据库 DDL 与迁移方案》和《数据库建设实施方案》；统一当前 PostgreSQL、迁移、回滚与验收口径 |

> 依据：PRD v1.3、数据字典 v2.0、API 规范 v1.2。本文定义数据库结构、约束、迁移和验收规则；具体业务口径以数据字典和代码测试为准。

## 1. 数据库策略

| 场景 | 方案 |
|---|---|
| 本地开发 | PostgreSQL，开发库与测试库分离；当前本地开发库为 `heijin_erp_dev` |
| 自动化测试 | 使用独立测试库或临时库，禁止连接开发库、生产库 |
| 生产环境 | 阿里云 ECS Docker Compose 内的 PostgreSQL，数据卷持久化 |
| 金额 | `DECIMAL(18,2)` + Python `Decimal`，禁止 float |
| 迁移 | Alembic 管理；每次变更必须有 revision、备份、升级后检查 |
| 删除 | 有流水的池、历史字段和核心凭证禁止物理删除，使用停用/取消 |

SQLite 只作为历史 MVP 或取证材料，不作为当前运行时数据库，也不得用于正式发布。

## 2. 建设顺序

`pools` → `order_type_defs` → `order_type_pools` → `policy_definitions` → `policy_versions` → `customers` / `counterparties` → `stocks` → `orders` → `order_customer_roles` / `order_counterparty_roles` → `order_profit_allocations` → `order_events` → `cashflow` → `installments` → `installment_schedules` → `rebate_records` → `deposits` → `field_definitions` / `entity_extra_values`.

## 3. 核心表约束

| 表 | 主键/唯一键 | 关键约束 |
|---|---|---|
| `pools` | `id`, `code UNIQUE` | ownership 仅允许 OWNED/CUSTODY/THIRD_PART；有流水禁止删除 |
| `order_type_defs` | `id`, `code UNIQUE` | capital_type 必须是已登记类型 |
| `order_type_pools` | `UNIQUE(order_type_id, portion)` | 外键关联订单类型和资金池 |
| `stocks` | `id`, `stock_no` | `stock_no` 为 KU_ 五位编号；`game_account` 和手机号不唯一 |
| `customers` | `id`, `customer_no UNIQUE` | 联系方式非唯一；停用客户不得参与新订单 |
| `counterparties` | `id`, `counterparty_no UNIQUE` | type 仅允许 PEER/SUPPLIER/PLATFORM；停用合作方不得参与新订单 |
| `orders` | `id`, `order_no UNIQUE` | 订单类型必须存在主数据；账号可为空 |
| `order_customer_roles` | `UNIQUE(order_id, customer_id, role)` | 角色必须是已登记角色 |
| `order_counterparty_roles` | `UNIQUE(order_id, counterparty_id, role)` | 角色必须是已登记角色 |
| `order_events` | `id`, `event_no UNIQUE` | 关联订单/资金池；金额大于 0 |
| `cashflow` | `id`, `flow_no UNIQUE` | 必须有关联资金池；来源订单、事件或押金可追溯 |
| `installments` | `id`, `inst_no UNIQUE`, `order_id UNIQUE` | STOCK_SALE/PICKUP_SALE/CONSIGNMENT_SALE 分别对应 HS/TH/DG |
| `installment_schedules` | `UNIQUE(installment_id, period_no)` | 支持部分收款、逾期和状态流转 |
| `rebate_records` | `id`, `rebate_no UNIQUE` | 新数据必须有来源订单；金额取 `base_amount` |
| `deposits` | `id` | 缴纳和退回通过 `cashflow.deposit_id` 追溯 |
| `policy_definitions` | `id`, `policy_code UNIQUE` | 规则定义与业务快照分离 |
| `policy_versions` | `UNIQUE(policy_definition_id, version, effective_from)` | 已被引用的版本不可更新/删除 |
| `order_profit_allocations` | `UNIQUE(order_id, user_id, role)` | 同订单有效分配比例合计 100% |
| `field_definitions` | `UNIQUE(entity_type, field_key)` | 有历史值只能停用 |
| `entity_extra_values` | `UNIQUE(entity_type, entity_id, field_definition_id)` | 活字段不得覆盖固定核算字段 |

`rebate_settlements` 已下线：新库不建此表，已有库历史表保留，不执行 drop。

- `cashflow(pool_id, occurred_on)`、`cashflow(nature)`、`cashflow(transfer_id)`
- `orders(order_type, trade_date)`、`orders(link_status)`

## 5. 数据导入与异常处理

历史导入仅属于 P2 参考能力，旧库和原始 JSON 只读，迁移只写新库：

- 无可靠关联的订单标记 `UNLINKED`，不得自动匹配账号。
- 无可靠来源的返点不得入账。
- 无法确认订单/账号的分期标记 `ORPHAN`。
- 无原始凭证的利润转入标记 `UNLINKED_TRANSFER`，不得补造双边流水。
- 每次人工补链记录原始记录、依据、操作者、时间和变更前后值。
- 每阶段输出行数、异常数和对账结果。

## 6. 迁移、发布与回滚

1. 发布前备份数据库，并记录 schema 版本和迁移前核算快照。
2. 使用 Alembic 执行升级，禁止在生产库直接手工 DDL。
3. 执行迁移后对账、外键检查、索引检查和 API smoke test。
4. 任一步骤失败，停止写入；按发布流程恢复备份或执行对应 downgrade。
5. 发布成功后保存迁移报告、版本号、核算结果和异常数量。
6. 不得用手工改余额或删除业务数据掩盖迁移问题。

正式 PostgreSQL 备份使用 `pg_dump -Fc`，恢复使用 `pg_restore` 或仓库提供的恢复脚本；禁止直接打包运行中的 PostgreSQL 数据目录。

## 7. 验收清单

- [ ] 所有表、外键、唯一索引和检查约束由迁移脚本创建。
- [ ] 新增 HS/TH/DG、资金池和路由无需修改数据库结构。
- [ ] 订单、事件、现金流、账号、分期、返点、押金、客户/合作方关系和活字段均有事务测试。
- [ ] 新 INTERNAL 流水逐对相等。
- [ ] 可退押金不进入经营损益。
- [ ] 迁移可重复执行，金额精度为两位且无 float。
- [ ] 生产发布前后核对 Alembic 版本、表数量、关键业务数据和备份完整性。
