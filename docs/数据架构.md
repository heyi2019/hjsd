## 1. 存储与库环境

- **引擎**：PostgreSQL 16，驱动 `psycopg[binary]` 3.x；本机容器 `heijin-db-1` 映射 `5433`，dump / restore 走 `docker exec`。生产在 ECS，无本地生产库连接。
- **本机数据库**：开发使用 `heijin_erp_dev`。测试入口以独立测试连接配置创建本轮临时 PostgreSQL 库，测试结束后清理；E2E 也使用每轮临时库，失败时保留供排查。不得使用开发库跑测试。
- **配置**：后端读取 `ERP_ENV_FILE` 指定文件，或依次读取仓库根目录及 `backend` 的 `.env`；环境变量可覆盖配置。`TEST_DATABASE_URL` 是创建独立测试库的连接配置，必须为本机测试地址且不得与开发库相同。
- **物理表**：34 张 ORM 表；另有 Alembic 版本表及历史迁移审计表，见数据字典。

## 3. 字段口径（双口径计数）

- **444 个物理列** = **300 个业务字段** + **144 个公共审计列**（`id` / `created_by` / `updated_by` / `created_at` / `updated_at`，按各表实际存在计；`revoked_tokens` 等表无这些列）。
- §4 数据字典只登记业务字段；公共审计列按约定存在，不逐表重复。
- **金额**：一律 `Amount` / `DECIMAL(18,2)`，禁止 float 参与计算；写库前统一 `to_money()`。
- **扩展字段**：各业务表以 `form_extra`（JSON）承载活字段值，活字段定义集中在 `order_form_fields`，作用域由配置决定；有历史值的字段只能停用，不能改键或物理删除。
- **时间**：全库统一本地无时区时间；`notifications.read_at` 已统一为本地口径（曾为全库唯一 UTC 写入点）。

## 4. 枚举体系

- 共 **35 个业务枚举类**，物理取值以 `app/domain/enums.py` 为事实源，数据库以 CHECK 约束闭集校验（约束名随枚举值生成，改枚举须对目标数据库按 DROP → 回填 → ADD 的顺序处理，顺序错会整体回滚）。
- 关键闭集：`BusinessMode`（SELF/DISTRIBUTION）、`InventoryType`（RECOVERY/PICKUP/CONSIGNMENT）、`OrderStatus`（ACTIVE/INSTALLMENT/COMPLETED/CANCELLED）、`InstallmentStatus`（8 态）、`CashflowLedgerType`（BUSINESS/STUDIO）、`Direction`（IN/OUT）、`AccountingAttribute`（15 值）、`CashflowSourceType`（8 值）、`SequenceKey`（10 个编号域）。
- 同名不同义的取值按枚举类限定中文，不共用译名表；中文仅供阅读，物理名始终是检索键与接口值。

## 5. 编号规则

序列定义存 `document_sequences`（`sequence_key` / `prefix` / `padding` / `current_value`），由编号器发放，**唯一、不可改、不可复用，不强制无断号**。

| 对象            | 格式                        | padding |
| ------------- | ------------------------- | ------- |
| 业务订单          | `HS` / `TH` / `DG` + 流水号  | 4       |
| 客户 / 合作方 / 需求 | `CUS` / `CP` / `REQ` + 四位 | 4       |
| 通知            | `NTF` + 四位                | 4       |
| 资金流水          | 支出 `ZC` / 收入 `SR` + 五位    | 5       |
| 库存            | `KU_` + 五位                | 5       |
| 分期合约          | `HS0001-FQ`；重建为 `HS0001-FQ-02` 等 | — |
| 返点记录          | `HS0001-RB01`（业务编号串联）     | —       |

订单编号域随业务类型动态生成；库存编号在新建库存账号时发放，包括普通建单和分期回收形成新库存。通知编号上限为 `NTF9999`，其余序列的 padding 为最小位数。分期合约和返点记录按订单派生编号。审计 `entity_id` 与流水 `source_id` 一律用业务编号，不用自增主键。详细编号规则见[数据字典](数据字典.md)。

附件不再发放业务编号，上传与删除审计关联所属业务对象的编号；历史附件编号与既有审计保留用于追溯。

## 6. 数据血缘与口径权威

数据从业务动作流向报表，单一口径来源如下（禁止另起计算）：

| 数据主题  | 权威来源 / 原语                                                | 下游            |
| ----- | -------------------------------------------------------- | ------------- |
| 订单利润  | 共享原语 `order_cashflow_profit`（全部收入 − 全部支出）                | 分润、月度损益、业务损益、数据中心 |
| 资金余额  | `cashflow` 按 `direction` 有符号和；`available = cash_balance` | 资金总览、对账       |
| 返点收入  | `rebate_records.amount`，登记即确认收入                          | 利润、月度损益「其中返点」   |
| 分期应收款 | `installment_schedules` 期次计划，减免不改写原应收                    | 合约状态、回款       |
| 报表月份  | Python 层月键归一（非 SQL `strftime`）                           | 全部按月报表        |

- **报表同源**：月度损益与订单利润共用现金流汇总原语；返点是收入「其中项」，禁止重复加回；冲销按毛额呈列。
- **押金**：净额 = 收入 − 支出；正数为利润，负数的相反数为损失，不是第二笔现金流出；占用与释放同池登记流水。

## 7. 结构治理与迁移

- **活动迁移链只有基线 `0001`**（`create_all` + `seed_catalog`）；改 ORM 即改基线，不加增量迁移。`backend/scripts/check_baseline.sh` 在临时库比对 ORM 与基线，CI 强制 0 差异。
- **上线是原地增量**：dump → drill → schema_diff → 换镜像 → 比对，绝不 `stamp` 落后库、不覆盖重建。改枚举 CHECK、加非空列等破坏性变更必须前置数据体检（实测 0 行或全 NULL 才可删）。
- **清理纪律**：能力下线不留兼容层——旧枚举、旧列、旧表、旧编号域全清，仅保留确认旧字段不存在的守卫断言与历史审计标签。

## 8. 数据安全

- `game_password` 明文存储为既定裁决，不加密不脱敏；无订单操作权限时接口置空。
- 权限为「角色 + 数据范围」两层：数据范围由 `owner_scope` + `pool_ids` + `team_ids` 决定，明细按可见资金账户过滤。
- 写路径一律 Service 事务 + `record_audit`，审计动作取 `AuditAction` 闭集；审计日志不可编辑、不可删除。
- 越权对象统一返回 `404 RESOURCE_NOT_FOUND`，不泄露是否存在；权限不足返回 `403 PERMISSION_DENIED`。
