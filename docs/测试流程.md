# 测试流程

## 版本变更记录

| 版本 | 日期 | 变更说明 |
| --- | --- | --- |
| V1.0 | 2026-11-25 | 发布版。登记日常选测和发布前全量测试报告流程 |

> 本文说明日常改动、云端 `dev` 验证和发布前的测试顺序。测试分层、数据库安全及用例管理以 [测试规范](testing/测试规范.md) 为准；开发和阿里云上线分别见 [研发流程](研发流程.md)、[发布流程](发布流程.md)。

## 1. 确定范围与环境

1. 根据改动选择相关后端测试、前端测试和关键页面；共享依赖或跨模块变动扩大测试范围。纯文档改动检查内容、链接及相关契约。
2. 数据库测试使用独立测试库，核对 `TEST_DATABASE_URL` 与开发库、上线库及生产库隔离；测试夹具可能清理测试数据。具体配置和安全限制见 [测试规范](testing/测试规范.md)。
3. 在本地 `dev` 的 `5188/8123` 完成开发验证；云端门禁在正式发布时运行，必要时可手动触发。不再使用本地 `main` 环境。

## 2. dev 修改后验证

- 后端执行与变更相关的 pytest 或 `run_regression.py` 分组；数据结构变动还要验证迁移与数据库基线。
- 前端执行 `cd frontend && npm run check`、`npm run test:changed`；涉及构建、依赖或发布时运行 `npm run build`。
- 交互或前后端联动改动检查涉及的列表、详情、创建、编辑、删除和权限路径，按需查看浏览器控制台及请求结果。
- 测试失败先保留错误、修复并复测，再提交或交付。常规 React 测试层最大 4 workers，其他分层按 [测试规范](testing/测试规范.md) 中的配置执行。

## 3. 推送云端 dev

本地验证通过后，按用户要求提交；推送 `origin/dev` 需要用户另行授权，推送后核对云端提交。日常推送和 PR 更新不自动触发云端门禁。

需要提前进行云端验证时，可手动触发 lint、frontend、backend 门禁。手动前后端门禁未提供变更范围时自动运行全量；前端全量包括浏览器 E2E。手动指定变更范围时，E2E 按规格和关键源码路径选测；也可显式选择 `full_suite` 运行全量。GitHub 发布会自动运行三道门禁，按完整提交范围选测；公共结构变更或范围不可靠时扩大范围。本地 CI/CD 发布执行完整本地门禁。

GitHub 发布按本次推送 `main` 前后的完整提交差异选择测试；需要指定范围时可将仓库根相对路径用英文逗号连接，通过 `TEST_CHANGED_PATHS` 传给 `npm run test:changed`。未检测到前端变更时，该命令不会运行测试，不能将其视为验收通过。

## 4. 发布前验证与交接

1. 发布前按影响执行验证：需要全量时，保留该次全量测试报告，记录实际 ERP `VERSION`、候选提交号、覆盖的测试范围及通过／失败结果；报告与用例库分别保存。按所选发布通道执行构建及必要的数据库基线检查，并记录未解决问题。
2. 真实浏览器 E2E 按需在本地执行。发布时，E2E 规格和订单、资金、认证等关键源码变更触发对应规格，共享配置变更运行完整浏览器测试。生产数据库重建必须运行前后端全量和浏览器 E2E。三道门禁通过后才开始部署。测试范围见 [测试规范](testing/测试规范.md)。
3. 验证完成后依据 [版本管理](版本管理.md) 准备版本建议及更新内容，再按 [发布流程](发布流程.md) 进行发布前检查。推送 `origin/main` 必须有用户明确发布指示。

### 全量测试报告

- 本地发布运行 `prepare` 后，报告位于 `outputs/local-release/reports/<ERP版本>-<提交短号>-<批次>/release-test-report.md`。报告列出各阶段通过、失败或未执行，并在终端打印路径。
- GitHub 正式发布进入全量档时，在本次 Actions 运行的 Summary 和产物 `full-release-report-<run_id>-<run_attempt>` 查看 `release-test-report.md`。全量门禁通过且报告上传成功后才部署。详细测试日志和各门禁产物位于同一次 Actions 运行。
- 每次全量运行单独留存，失败和重跑均可按批次查找。报告的 ERP 版本取被测候选提交中的 `VERSION`。成功出具报告与测试通过分别核对。
