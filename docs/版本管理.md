# 版本管理

## 版本来源

- [VERSION](../VERSION) 是项目发布版本的来源。前端构建、后端和部署镜像使用此版本，每次发布分别登记实际前端版本和后端版本。
- 本文件统一保存项目版本规则和版本发布记录；重置前的历史记录可在 [Git 历史](https://github.com/heyi2019/hjsd/blob/2ebd308bdb8f8bf9fddf1f99fad19c7a388572b1/RELEASE.md)查看，与重置后的版本系列分开。
- `dev`、`main` 使用同一个发布版本时，以分支和 Git 提交号区分代码，不额外创建前后端版本号。
- 数据库迁移编号取该次候选提交的 Alembic head。它用于对应数据库结构，独立于 ERP 应用版本。

## 版本级别

| 更新级别 | 递增方式 | 当前为 `1.0.0` 时的示例 | 适用情况 |
|---|---|---|---|
| 小版本 | 增加 `0.0.1` | `1.0.1` | 问题修复、小调整、兼容性优化 |
| 大版本 | 增加 `0.1.0` | `1.1.0` | 新增或较大范围调整功能，次版本后面的数字归零 |
| 超大版本 | 增加 `1.0.0` | `2.0.0` | 不兼容变更或用户确定的重大版本，后两位归零 |

级别应结合实际改动和影响判断；提交类型可辅助判断，不替代对业务变化的检查。

## 用户提出发布时

1. 确认用于比较的上次发布版本、提交和待发布范围；如果无法核实实际上线版本，要说明采用的比较基线，不把自动生成的发布记录当作上线成功证明。
2. 检查这次包含的提交和实际改动，区分已提交、未提交及不属于本次发布的工作。
3. 用户提出发布时，先整理版本号变化建议和本次改版内容说明，请用户确认；同时说明验证结果及未解决的问题。确认同一次发布后，按所选发布通道继续，不重复询问已确认的版本和内容。
4. 用户指定具体版本时，以用户指定的版本为准；发现重复标签、已有版本记录或其他冲突时，说明实际冲突，不覆盖历史记录。
5. 用户只要求版本建议时，不升版或部署。正式发布须有明确发布指令；明确指定版本并要求发布时，按该授权执行，不重复询问同一事项。

## 发版执行

- 按 [发布流程](发布流程.md) 选择通道。GitHub 发布将确认的 `dev` 内容合并进 `main` 并触发云端门禁。本地 CI/CD 发布固定 `origin/dev` 当前提交，直接走本地门禁和部署。
- 按用户确定的版本更新 `VERSION` 并提交；已是目标版本时无需改写文件。发版准备提交的正文包含 `Release-Version: x.y.z`，例如 `Release-Version: 0.2.0`。
- 自动发版读取并校验该标记，保留用户选择的版本，在本文件生成待发布记录和提交摘要；已有待发布记录会保留人工填写的内容。标记与 `VERSION` 不一致、已有发布记录或标签冲突时中止。
- 未指定版本标记时，自动流程按提交类型提供默认升版：修复等为小版本，`feat` 为大版本，`!` 或 `BREAKING CHANGE` 为超大版本。
- 每条记录包含 ERP 版本、前端版本、后端版本、数据库迁移编号、发布日期、发布时间、发布状态和本次更新内容。准备阶段按候选提交填版本和迁移编号。
- 发布日期和发布时间采用北京时间，准备阶段均填写“待发布”。自动发布在部署及健康检查成功后填写实际日期和时间，保留原有更新说明；失败或未执行部署时仍为待发布。
- 人工发布须先核实部署和健康检查成功，再运行 `python3 scripts/ops/record_release_published.py x.y.z` 记录实际发布时间，并提交本文件。重复运行不会覆盖已记录的时间。
- 发布准备、自动生成摘要或提交代码均不代表已上线；以实际部署结果为准。
