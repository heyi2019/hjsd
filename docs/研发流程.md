# 研发流程

> 本文覆盖 `dev` 开发、测试和合并至本地 `main` 后的验收。测试顺序见 [测试流程](测试流程.md)、细则见 [测试规范](testing/测试规范.md)，发布到阿里云、上线检查及回滚见 [发布流程](发布流程.md)；历史版本由 git 追溯。
>
> **红线：推送 `origin/main` 等同生产上线，必须单独确认，不得作为常规步骤自动执行。**

## 1. 环境与分支基准

开发与发布使用两个本地 worktree，代码、端口、数据库三隔离：

| 用途 | 分支 | 目录 | 前端 | 后端 | 本地数据库 |
|---|---|---|---:|---:|---|
| 日常开发与验证 | `dev` | `/Users/aries/黑金时代` | `5188` | `8123` | `heijin_erp_dev` |
| 合并后验收与发布 | `main` | `/Users/aries/黑金时代-main` | `5199` | `8125` | `heijin_erp_release` |

访问地址：

| 环境 | 页面 | 健康检查 | 接口文档 |
|---|---|---|---|
| dev | http://127.0.0.1:5188/ | http://127.0.0.1:8123/api/health | http://127.0.0.1:8123/docs |
| 本地 main | http://127.0.0.1:5199/ | http://127.0.0.1:8125/api/health | http://127.0.0.1:8125/docs |

两个 worktree 根 `.env` 是**各自独立的实体文件**（2026-11-11 已拆分原先 main → dev 的 symlink），改任一不影响另一套；涉及写入数据的验证须注明在哪个环境执行。本地 `heijin_erp_release` **不是生产库**，生产库在 ECS `heijin_erp`。

系统基准：

- 本地 `dev` 是系统定义的最新代码基线，开发、修复和功能判断以本地代码为准。
- 本地 `main` 是由 `dev` 验证后形成的发布基线。
- 云端只有 `origin/main`，它就是生产发布分支，**不是测试环境**，不反向覆盖本地代码。
- 云端存在本地没有的提交时，只能逐项检查后选择性适配；禁止直接把 `origin/main` 整体合入本地，禁止用远端强制覆盖本地分支。

## 2. 日常开发

始终在 `dev` worktree 修改代码，前后端常驻服务自动重载，开发时只用 `5188/8123` 验证：

```bash
cd /Users/aries/黑金时代
git switch dev
```

提交纪律：先 `git status --short` 核对变更清单，只按 pathspec 暂存自己的文件，禁 `git add -A` / `--no-verify`，不代提交并发会话文件。

```bash
git status --short
git add <changed-files>
git commit -m "<message>"
```

## 3. 本地验证

### 3.1 自动化检查

根据本次变更选择必要检查；`dev` 验证通过并合入本地 `main` 后，再针对相同变更复验：

```bash
cd /Users/aries/黑金时代/backend        # 或 /Users/aries/黑金时代-main/backend
.venv/bin/python -m pytest ../tests/backend/unit/system/test_settings.py  # 示例，替换为相关测试

cd ../frontend
npm run check
npm run test:changed
```

按用户裁决，**默认只跑与改动直接相关的测试文件 / 用例**；涉及构建、依赖或发布时补跑 `npm run build`。全量回归仅在里程碑收口、发版前或改动确实跨多模块时执行。测试顺序见 [测试流程](测试流程.md)，分层、数据库配置与命令见 [测试规范](testing/测试规范.md)。

### 3.2 按改动范围选择测试

| 改动范围 | 最低要求 |
|---|---|
| 纯前端组件或交互 | `npm run check`、相关 Vitest、5188/5199 页面人工验收 |
| API、权限、状态机 | 后端相关 pytest / regression、前端相关页面验收 |
| 数据模型或迁移 | 后端迁移测试、相关 API 测试、数据库状态检查 |
| 前后端联动功能 | 前后端检查、关键写路径人工验收，dev 与 main 各验证一次 |

开发协作约束：任何执行者（Codex、WorkBuddy 或其他协作者）每次修改完成后，都必须自动运行与改动范围匹配的测试；前端默认使用 `cd frontend && npm run test:changed`，不需要用户重复提醒。测试失败必须先修复并复测，通过后才能汇报完成或提交。公共层、测试夹具、分层配置等变更按脚本规则扩大到 `quick`；跨模块收口、里程碑和发布前再运行 `npm run test:full` 与 `npm run test:full:deep`。

本地 `main` 合并后通常没有未提交改动；复验时须根据合并前后的提交差异选择相关测试，或用 `TEST_CHANGED_PATHS` 指定路径。`test:changed` 未检测到前端变更时不运行测试，不能将其视为验收通过。

本地日常验证不默认跑真实浏览器 E2E；`e2e-gate` 与 `coverage-gate` 已于 2026-11-11 下线，CI 只剩 lint / frontend / backend 三个门禁。独立 `heijin_erp_e2e` 库留给本地夹具，需要页面体检时按本地联调指南的 UX audit 说明单独执行。

### 3.3 人工验收

重点验证本次修改涉及的列表、详情、创建、编辑、删除和权限路径，检查浏览器控制台与页面有无 4xx/5xx。两轮顺序固定：**先 `dev`（5188/8123），合并后本地 `main`（5199/8125）再验一次**。

main 验收失败时先不要推送 `origin/main`，回到 `dev` 或在 main 合并提交上定位问题。

### 3.4 数据纪律

- 本地两套环境各用独立库、互不共用：`dev` → `heijin_erp_dev`，本地 `main` → `heijin_erp_release`；`heijin_erp_test` / `heijin_erp_e2e` 分别由后端单测与 E2E 夹具使用。
- 禁止在本地开发验证中连接生产库。
- 测试失败时保留错误输出、请求路径和复现步骤，不要用清库或回滚数据掩盖问题。

## 4. 合并 dev 到本地 main

`dev` 验证通过后，在 `main` worktree 合并：

```bash
cd /Users/aries/黑金时代-main
git status
git switch main
git merge dev          # 优先 --ff-only；冲突无法安全处理时 git merge --abort
```

合并完成后按第 3 节在 `5199/8125` 环境做一次 main 验收。验收通过后如需上线，按 [发布流程](发布流程.md) 检查并等待用户明确发布指示。
