# 研发流程

> 本文覆盖 `dev` 开发、本地验证、推送云端 dev 与发布上线。测试顺序见 [测试流程](测试流程.md)、细则见 [测试规范](testing/测试规范.md)，发布到阿里云、上线检查及回滚见 [发布流程](发布流程.md)；历史版本由 git 追溯。
>
> **红线：推送 `origin/main` 等同生产上线，必须单独确认，不得作为常规步骤自动执行。**
>
> **开发主线是云端 `origin/dev`。本地工作区只是推送前的临时验证副本，不是独立开发阵地，不留独有提交、分支或 worktree。**

## 1. 环境与分支基准

开发只在本地临时工作区 `/Users/aries/黑金时代`（分支 `dev`）进行，验证用 `5188/8123`，数据库 `heijin_erp_dev`：

| 用途 | 分支 | 目录 | 前端 | 后端 | 本地数据库 |
|---|---|---|---:|---:|---|
| 临时验证副本 | `dev` | `/Users/aries/黑金时代` | `5188` | `8123` | `heijin_erp_dev` |

访问地址：

| 环境 | 页面 | 健康检查 | 接口文档 |
|---|---|---|---|
| dev 本地副本 | http://127.0.0.1:5188/ | http://127.0.0.1:8123/api/health | http://127.0.0.1:8123/docs |

系统基准（2026-11-23 用户裁决）：

- **云端 `origin/dev` 是唯一开发主线**；云端 `origin/main` 是生产发布分支，**不是测试环境**，不反向覆盖本地代码。
- **本地不创建 `main` 分支或 worktree**（已删除 `/Users/aries/黑金时代-main`）；main 仅存于云端，本地 `git fetch` 可见 `origin/main`。
- 本地 `dev` 工作区只是 agent 推送前的临时 checkout：每次任务先把它刷成云端 dev 的镜像，改完验证后推回，本地不留任何独有提交、分支或 worktree。
- 也不建本地 agent 分支 / worktree。云端的分支权威来源是 `origin/dev`，本地一律以它为准。

## 2. 日常开发（云端 dev 闭环）

每次任务按以下闭环执行，真相源始终是 `origin/dev`：

```bash
cd /Users/aries/黑金时代

# 1. 开工同步：本地须 clean；把本地副本刷成云端 dev 镜像
git status --short                      # 必须为空
git pull --ff-only origin dev

# 2. 改动 + 验证（见第 3 节）
#    ... 修改代码 ...
#    ... 跑针对性测试 ...

# 3. 回写云端 dev
git status --short
git add <changed-files>                 # 只按 pathspec 暂存自己的文件
git commit -m "<message>"
git -c http.version=HTTP/1.1 push origin dev
```

提交纪律：先 `git status --short` 核对变更清单，只按 pathspec 暂存自己的文件，禁 `git add -A` / `--no-verify`，不代提交并发会话文件。推送用 `http.version=HTTP/1.1` 规避偶发的 HTTP2 framing / SSL 静默失败；推送后用 `gh api repos/heyi2019/hjsd/branches/dev --jq .commit.sha` 核验云端 HEAD（不能只看本地 `origin/dev`）。

日常推送 `dev` 和更新 PR 不自动启动云端门禁；必要时可手动运行。GitHub 发布时，`main-ci-cd` 会在同一个 release sha 上调用三道门禁。

## 3. 本地验证

### 3.1 自动化检查

根据本次变更选择必要检查，在推送云端 dev 前完成：

```bash
cd /Users/aries/黑金时代
scripts/ops/test-local.sh -q tests/backend/unit/system/test_settings.py  # 示例，替换为相关测试

cd frontend
npm run check
npm run test:changed
```

按用户裁决，**默认只跑与改动直接相关的测试文件 / 用例**；涉及构建、依赖或发布时补跑 `npm run build`。全量回归仅在里程碑收口、发版前或改动确实跨多模块时执行。测试顺序见 [测试流程](测试流程.md)，分层、数据库配置与命令见 [测试规范](testing/测试规范.md)。

### 3.2 按改动范围选择测试

| 改动范围 | 最低要求 |
|---|---|
| 纯前端组件或交互 | `npm run check`、相关 Vitest、5188 页面人工验收 |
| API、权限、状态机 | 后端相关 pytest / regression、前端相关页面验收 |
| 数据模型或迁移 | 后端迁移测试、相关 API 测试、数据库状态检查 |
| 前后端联动功能 | 前后端检查、关键写路径人工验收 |

开发协作约束：任何执行者（Codex、WorkBuddy 或其他协作者）完成修改后，按影响选择有意义的测试；前端可使用 `cd frontend && npm run test:changed`。测试失败须处理并如实报告。公共层、测试夹具、分层配置及无法确定影响范围的变更，脚本会选择完整前端测试；跨模块收口、里程碑和发布前按影响选择验证范围。

`test:changed` 未检测到前端变更时不运行测试，不能将其视为验收通过。

本地日常验证不默认跑真实浏览器 E2E；修改 E2E 规格时运行受影响规格，修改 E2E 共享配置时运行完整浏览器测试。CI 的浏览器验证属于 frontend 门禁，使用临时隔离库。

### 3.3 人工验收

重点验证本次修改涉及的列表、详情、创建、编辑、删除和权限路径，检查浏览器控制台与页面有无 4xx/5xx。在本地 `dev` 副本（5188/8123）验收，确认无问题后按第 2 节推送 `origin/dev`。

### 3.4 数据纪律

- 本地验证用独立库 `heijin_erp_dev`；`heijin_erp_test` / `heijin_erp_e2e` 分别由后端单测与 E2E 夹具使用。旧 `heijin_erp_release` 遗留库不参与现行开发，保留数据时不得擅自清理。
- **测试库铁律**：跑测试前必须核 `TEST_DATABASE_URL` ≠ dev（应含 `test`），`conftest` 会 TRUNCATE 全表；只跑针对性测试，禁动不动全量。
- 禁止在本地开发验证中连接生产库。
- 测试失败时保留错误输出、请求路径和复现步骤，不要用清库或回滚数据掩盖问题。

## 4. 发布上线

`dev` 验证通过并推送 `origin/dev` 后，按确认的通道执行 [发布流程](发布流程.md)。

- GitHub 发布在云端把已确认的 `dev` 内容合并进 `main`，触发 `main-ci-cd`。三道门禁通过后构建镜像并部署 ECS。
- 本地 CI/CD 发布固定 `origin/dev` 当前提交，经本地完整检查后部署 ECS。该通道无需合并 `main`。

更新 `origin/main` 会触发生产发布，须取得明确发布指示。
