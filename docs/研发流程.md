# 研发与发布流程

> 本册合并原《开发流程》《测试流程》《发布流程》，覆盖 `dev` 开发 → 本地 `main` 验收 → `origin/main` 发布 → 同步回本地的完整链路。历史版本由 git 追溯，不另存归档。
>
> **红线：推送 `origin/main` 等同生产上线，必须单独确认，不得作为常规步骤自动执行。**

## 1. 环境与分支基准

开发与发布使用两个本地 worktree，代码、端口、数据库三隔离：

| 用途 | 分支 | 目录 | 前端 | 后端 | 本地数据库 |
|---|---|---|---:|---:|---|
| 日常开发与验证 | `dev` | `/Users/aries/黑金时代` | `5188` | `8123` | `heijin_erp_dev` |
| 合并后验收与发布 | `main` | `/Users/aries/黑金时代-main` | `5199` | `8125` | `heijin_erp_release` |

访问地址：

| 环境 | 页面 | 健康检查 | 接口文档 |
|---|---|---|---|
| dev | http://127.0.0.1:5188/ | http://127.0.0.1:8123/api/v1/health | http://127.0.0.1:8123/docs |
| 本地 main | http://127.0.0.1:5199/ | http://127.0.0.1:8125/api/v1/health | http://127.0.0.1:8125/docs |

两个 worktree 根 `.env` 是**各自独立的实体文件**（2026-11-11 已拆分原先 main → dev 的 symlink），改任一不影响另一套；涉及写入数据的验证须注明在哪个环境执行。本地 `heijin_erp_release` **不是生产库**，生产库在 ECS `heijin_erp`。

系统基准：

- 本地 `dev` 是系统定义的最新代码基线，开发、修复和功能判断以本地代码为准。
- 本地 `main` 是由 `dev` 验证后形成的发布基线。
- 云端只有 `origin/main`，它就是生产发布分支，**不是测试环境**，不反向覆盖本地代码。
- 云端存在本地没有的提交时，只能逐项检查后选择性适配；禁止直接把 `origin/main` 整体合入本地，禁止用远端强制覆盖本地分支。

## 2. 日常开发

始终在 `dev` worktree 修改代码，前后端常驻服务自动重载，开发时只用 `5188/8123` 验证：

```bash
cd /Users/aries/黑金时代
git switch dev
```

提交纪律：先 `git status --short` 核对变更清单，只按 pathspec 暂存自己的文件，禁 `git add -A` / `--no-verify`，不代提交并发会话文件。

```bash
git status --short
git add <changed-files>
git commit -m "<message>"
```

## 3. 本地验证

### 3.1 自动化检查

`dev` 与本地 `main` 各跑同一组必要检查：

```bash
cd /Users/aries/黑金时代/backend        # 或 /Users/aries/黑金时代-main/backend
.venv/bin/python -m pytest

cd ../frontend
npm run check
npm run build
```

按用户裁决，**默认只跑与改动直接相关的测试文件 / 用例**；全量回归仅在里程碑收口、发版前或改动确实跨多模块时执行。

### 3.2 按改动范围选择测试

| 改动范围 | 最低要求 |
|---|---|
| 纯前端组件或交互 | `npm run check`、相关 Vitest、5188/5199 页面人工验收 |
| API、权限、状态机 | 后端相关 pytest / regression、前端相关页面验收 |
| 数据模型或迁移 | 后端迁移测试、相关 API 测试、数据库状态检查 |
| 前后端联动功能 | 前后端检查、关键写路径人工验收，dev 与 main 各验证一次 |

本地日常验证不默认跑真实浏览器 E2E；`e2e-gate` 与 `coverage-gate` 已于 2026-11-11 下线，CI 只剩 lint / frontend / backend 三个门禁。独立 `heijin_erp_e2e` 库留给本地夹具，需要页面体检时按本地联调指南的 UX audit 说明单独执行。

### 3.3 人工验收

重点验证本次修改涉及的列表、详情、创建、编辑、删除和权限路径，检查浏览器控制台与页面有无 4xx/5xx。两轮顺序固定：**先 `dev`（5188/8123），合并后本地 `main`（5199/8125）再验一次**。

main 验收失败时先不要推送 `origin/main`，回到 `dev` 或在 main 合并提交上定位问题。

### 3.4 数据纪律

- 本地两套环境各用独立库、互不共用：`dev` → `heijin_erp_dev`，本地 `main` → `heijin_erp_release`；`heijin_erp_test` / `heijin_erp_e2e` 分别由后端单测与 E2E 夹具使用。
- 禁止在本地开发验证中连接生产库。
- 测试失败时保留错误输出、请求路径和复现步骤，不要用清库或回滚数据掩盖问题。

## 4. 合并 dev 到本地 main

`dev` 验证通过后，在 `main` worktree 合并：

```bash
cd /Users/aries/黑金时代-main
git status
git switch main
git merge dev          # 优先 --ff-only；冲突无法安全处理时 git merge --abort
```

合并完成后按第 3 节在 `5199/8125` 环境做一次 main 验收。

## 5. 发布到 origin/main

### 5.1 发布前检查

- `dev` 改动已提交，并已在 `5188/8123` 验证；改动已合入本地 `main`，且 `5199/8125` 回归与关键页面验收通过。
- `git status --short` 无意外未提交文件，两端 worktree 状态干净。
- 版本号不手动修改；自动发版按提交类型升版并生成发布说明。
- 确认本次发布不会把本地开发库或生产数据导出到发布包。
- 涉及表单字段 / 种子 / 数据库结构的版本，已备齐 ECS 现场当期执行单，并确认现场能执行 `backend/scripts/split_sale_form_scopes.py`（B4）。

### 5.2 推送

`dev` 不直接发布。确认本地 `main` 验收通过后，在 `main` worktree 执行：

```bash
cd /Users/aries/黑金时代-main
git status --short --branch
git log -1 --oneline
git push origin main:refs/heads/main
```

### 5.3 CI/CD 与自动版本规则

推送后由 `main-ci-cd.yml`（push `main` 唯一触发点）执行自动发版与发布链路：

```text
origin/main（push）
  → main-ci-cd：判断版本级别、生成 chore(release) 提交并推回 main
  → dispatch lint-gate / frontend-gate / backend-gate
  → 三个门禁全绿
  → dispatch deploy-production（仅 workflow_dispatch）
  → ECS 构建镜像并原地增量部署
```

| 提交类型 | 更新级别 | 示例 |
|---|---|---|
| `fix:`、`chore:`、`docs:`、`test:`、`ci:` | patch +1 | `0.0.9 → 0.0.10` |
| `feat:` | minor +1 | `0.0.9 → 0.1.0` |
| `feat!:`、`fix!:` 或含 `BREAKING CHANGE` | major +1 | `0.0.9 → 1.0.0` |

每次自动发版会把版本同步到后端、前端和根 `package-lock.json`，在 `RELEASE.md` 写入本轮提交、修复、功能与发布时间，并在 GitHub Actions Summary 输出版本、提交清单、门禁耗时、部署耗时与最终结果。

- `deploy-production` 只由 main-ci-cd dispatch 或手动触发，**不再由 push 直接触发**。
- `coverage-gate` / `e2e-gate` 已下线，真实浏览器 E2E 只按需本地运行，不作为发布门禁。
- `chore(release)` 推回会二次触发 main-ci-cd，工作流已加跳过保护，不会重复升版或重复部署。
- 三个门禁未全绿时不得继续发布；不要绕过 CI 手工执行生产部署。

## 6. 发布后同步回本地

CI 发布成功后，把发布结果（含自动生成的 `chore(release)` 提交）同步回本地 `main`，再同步到 `dev`：

```bash
cd /Users/aries/黑金时代-main
git fetch origin main
git log --oneline main..origin/main
git merge --ff-only origin/main

cd /Users/aries/黑金时代
git merge main
```

快进失败或云端有本地没有的业务提交时，立即停止并先建立备份引用，逐项评估后再适配；不得 `reset --hard` 覆盖本地提交，也不得强推远端。同步完成后重新检查 `5199/8125` 与 `5188/8123`。

## 7. 阿里云 ECS 部署与现场检查

生产部署目录 `/opt/heijin/deploy`。前端通过 Nginx 提供 80/443，后端只经 Compose 内网访问，PostgreSQL 端口只绑本机，不开放公网；生产密钥、数据库密码和 `.env` 不进入 Git 或发布包。

发布后在 ECS 现场检查：

```bash
ssh heijin-prod
cd /opt/heijin/deploy
docker compose ps
docker compose exec -T backend curl -fsS http://127.0.0.1:8123/api/v1/health
```

同时确认：

- backend、frontend、db 容器均为 healthy/running。
- **B4 不在 `deploy.sh` 内自动执行**：已有库升级须在 ECS 现场按当期执行单手动跑 `backend/scripts/split_sale_form_scopes.py`，并核对 SALEREC / SALETH / SALEDG 三份字段集非空；`deploy.sh` 只做发布前后只读不变量校验。
- 页面可打开，登录和本次变更的关键路径可用。
- Alembic 版本、表数量、主键约束（`pg_constraint.contype='p'`）和关键业务数据符合发布前基线。
- 发布前备份成功，备份文件和校验文件存在。

**上线＝原地增量，不是覆盖重建**：dump → drill → `schema_diff.py` 只补缺失 → `APP_VERSION=` 换镜像 → 换镜像后再结构比对。

## 8. 数据库备份与回滚

正式备份使用 PostgreSQL 自定义格式，恢复必须使用仓库脚本，不要直接打包运行中的 PostgreSQL 数据目录：

```bash
cd /opt/heijin/deploy
bash scripts/backup_daily.sh
bash scripts/restore_pg.sh --backup /opt/heijin/backups/<backup>.dump --yes
```

发生异常时：

1. 立即停止继续发布，不重复执行迁移或清库。
2. 保存 CI 日志、容器日志、健康检查和数据库版本信息。
3. 按当前版本的回滚说明恢复镜像或数据库。
4. 回滚后重新检查登录、关键读写路径和数据基线。

## 9. 安全边界

- 不在公网开放 `8123`、`8125`、`5432` 或 Docker API。
- `JWT_SECRET_KEY` 必须使用随机强密钥；生产 `CORS_ORIGINS` 不允许使用 `*`。
- 不使用历史 SQLite 部署说明执行 PostgreSQL 正式发布。
