## 第一章 4 个重点可疑点（实测定性）

### 1.1 客户详情「剩余」口径漂移 —— 【确凿 bug · 交裁决】

**事实**：客户详情的「剩余应收」用裸减法，分期域同名字段减坏账 + 夹底 0。

| 场景 | 输入 | 分期域权威 `remaining_receivable` | 客户详情 `remaining_amount` / `installment_remaining_total` |
|---|---|---|---|
| 先收后减免 | 总应收 700、已收 900、减免 500 | **0.00** | **−200.00**（负数可见） |
| 坏账 | 总应收 1200、已收 300、坏账 100 | **800.00** | **900.00**（多算 100 坏账） |

**证据链**：
- 客户详情实现 `backend/app/customer_center/customer_detail.py:152,223`：`remaining = receivable − paid`，两处均不减 `bad_debt_amount`、不夹底。
- 分期域权威 `backend/app/installments/schemas.py:174-185`：`remaining_receivable = 总应收 − 已收 − 坏账`，且 `< 0` 取 0；注释专门说明「先收后减免会出现负的剩余」。
- 前端标签 `frontend/src/customer-center/CustomerDetailDrawer.tsx:103`：`installment_remaining_total` 明确标注为**「剩余应收」**，与分期域 `remaining_receivable` 同名同义；第 137 行合约级 `remaining_amount` 标注为「剩余」。
- 测试现状：分期域有专文 `test_installment_remaining.py` 锁死口径（`test_remaining_never_negative_after_waiver`）；客户详情字段**零口径测试**（`test_parties_*.py` 只测基本字段存在）。
- 实测命令：临时探针 `test_zz_calc_probe.py`（已删），`pytest -q -s`，输出见上表。

**语义二分（需裁决）**：
- 若「剩余应收」应表示**还需收多少**（与分期域一致）→ 这是确凿 bug，应改为 `max(total_receivable − paid − bad_debt, 0)`，两处联动。
- 若客户详情刻意展示**账面差额**（如实暴露多收/坏账、不夹底）→ 属设计如此，但前端标签「剩余应收」有误导之嫌，至少应改标签以区分。

**为何不直接修**：触发路径改变用户可见数字，且存在两种都合理的业务语义 → 按裁决规则只出证据，**不擅自动手**。

### 1.2 总应收双实现 parity —— 【健康】

Python `shared/installment_amounts.py:34` 与 SQL `installments/queries.py:180-191` 公式字面一致：首付 + 每期×期数 + 末期调整 − 减免。

**实测**：构造 `调整+减免+坏账`、`负调整`、`减免超过应收` 三组叠加场景，Python 逐条求和 = SQL `total_receivable` = 1520.00，逐分相等。现有 `test_installment_totals.py` 已做「列表逐条之和 == totals」间接 parity，实测补覆盖了调整组合盲点。**两份实现 parity 成立，不改。**

### 1.3 余额公式多实现 —— 【健康】

`finance/balances.py` 的 `deposit_held = Σ(实缴−已退−已损失)`（SQL 聚合）、`deposits/reads.py::deposit_held_total` 与 `deposits/_shared.py::_outstanding` 三处同公式。

**实测**：`cash_balance == income − expense`、`available == cash_balance`、`balances.deposit_held == deposit_held_total` 全部成立（恒等式探针通过）。注：`available = cash_balance` 是既定口径（押金占用已进 expense，不二次扣可用余额）。**不改。**

### 1.4 押金损失双谓词动态等价 —— 【健康】

SQL `business_cashflow_filter()` 与 Python `is_deposit_loss_flow()`（`shared/order_amounts.py:50,78`）镜像：仅排除 `DEPOSIT + OUT + 非DEPOSIT_HOLD` 的损失重分类流水。

**实测**：构造 24 组 `(attribute, direction, category)`（含 `attribute=None` 三值逻辑边界、4 种 category），SQL 保留 21 条、Python 保留 21 条，集合差异为空。正向写法规避 `NOT(NULL)=NULL` 误删的陷阱有效。**不改。**

## 第三章 待裁决清单

### 【裁决项 1】客户详情「剩余应收」口径

- **一句话**：客户详情的「剩余」用裸减法（不减坏账、不夹底），先收后减免显示负数、坏账场景多算，与分期域同名字段口径不一致。
- **实测证据**：见 1.1（负数 −200、坏账多算 100），前端标签明确写「剩余应收」。
- **选项**：
  - **A（改为与分期域同口径）**：两处改为 `max(总应收−已收−坏账, 0)`，补边界测试。改变可见数字（负数归 0、坏账场景少算）。
  - **B（保持现状，仅改标签）**：口径保留为「账面差额」，前端标签从「剩余应收」改为「账面差额」以免误导。
  - **C（不改）**：维持现状，接受两处口径差异。

> 除本项外，其余全部字段/原语实测健康，无需处置。

### 【处置留痕 2026-11-19】裁决项 1 已按方案 A 修复
