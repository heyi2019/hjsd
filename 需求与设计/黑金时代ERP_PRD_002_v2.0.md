## 1. 业务模式（唯一事实源）

### 1.1 模式定义：委托代理制 + 多资金池

工作室出资、员工买号、售出回本、差价入利润池。
**业务与资金池均可自由新增，二者不写死绑定。**

```
              投资款
                │
                ▼
    ┌──────────────────────┐
    │  投资款荷包（本金）   │──► 员工买号 ──► 库存（在途账号）
    │    又称「小荷包」     │──► 代垫/付同行 ──► 过账
    └──────────┬───────────┘
               │ 售出打回本金
               ▼
    ┌──────────────────────┐
    │  利润荷包（利润）     │◄── 售出差价
    │    源数据称「利润池」 │◄── 平台返点（成单后附加）
    └──────────────────────┘
```

### 1.1.1 业务分类：四类主业务 + 一类附加收入（业务可新增）

**返点不是独立业务，是四个业务成单后的额外收入。**

| 业务 | 代��� | 业务定义 | 资金性质 |
|---|---|---|---|
| **回收** | `HS` | 客户把号卖给我，我择机卖出 | 库存型 |
| **提号** | `TH` | 买家找我买号，我去同行那里提号卖给他 | 过账型 |
| **代挂** | `DG` | 客户让我帮忙卖他的号，我收服务费 | 零本金型 |
| └ **蹭点** | `DG` | **代挂的一种叫法**，非独立业务 | 零本金型 |
| **代分期** | `DFQ` | 代客户买号，到期账号再换绑给他 | 垫资型 |
| **返点** | — | **附加收入**，非独立业务 | 纯利润型 |

**术语等价表**（源数据存在同义混用，须归一）：

| 源数据写法 | 归一为 | 说明 |
|---|---|---|
| 蹭点 | `DG` 代挂 | **主理人口述确认：蹭点就是代挂** |
| 氪金联盟提号 / 氪金提号 / 提号 | `TH` 提号 | 同一业务，流水表有简写 |
| 小荷包 / 经营池 / 投资款荷包 | 投资款荷包 | 同一池，4 种叫法 |
| 利润池 / 利润荷包 | 利润荷包 | 同一池，2 种叫法 |

> **「氪金联盟回收」不在归一范围**：实测 10/1 支出 1,544.40 → 10/2 收入 1,544.40，
> 是独立业务，不是 `TH` 提号。

**返点依附于主业务**：

```
一笔「回收」成单 ──► 平台返点（盼之首保6% / 续保3% / 螃蟹收号5%）
一笔「提号」成单 ──► 平台返点
一笔「代挂」成单 ──► 平台返点
一笔「代分期」成单 ──► 平台返点
```

**关键设计含义**：

| 含义 | 说明 |
|---|---|
| 返点不占 `order_type` 主枚举 | 它是**主业务的附加属性**，不是第五类业务 |
| 返点必须挂 `source_order_id` | 指向产生它的那笔主业务订单 |
| 单笔业务的完整收益 = 主业务利润 + 附加返点 | 报表须合并呈现，否则低估业务收益 |
| 跨期返点需支持 | 平台可能事后结算，返点日期 ≠ 成单日期 |

**源数据现状**：返点被错误地建成独立 `订单类型=返点` 的 19 笔订单，
且**无 `source_order_id` 字段**，仅 6/19 笔能通过金额匹配到主业务，13 笔归属不明。
这是必须修复的结构性缺陷。

**补录策略（已裁决）**：历史 19 笔**后续人工补录** `source_order_id`。

| 阶段 | 策略 |
|---|---|
| M0–M2 | 19 笔全部标 `link_status=UNLINKED`，`source_order_id=NULL`；R5 报表中归入「未归集」行 |
| M3 起 | 新增返点录入**强制必填** `source_order_id` |
| 补录期 | 人工补齐 19 笔，补齐后 R5 自动纳入对应业务 |

> 补录前 R5 报表的「附加返点」列显示 `UNLINKED 1,264.98`，
> **不得摊入任何业务**——宁可显示缺口，不做错误归集。

**返点归属推测**（据备注关键词，仅供参考）：

| 备注关键词 | 疑似来源 | 笔数 |
|---|---|---:|
| 「收号」 | 回收 `HS` | 3 |
| 「首保/续保」 | 跨期，无法判定 | 11 |
| 无备注 | 归属不明 | 5 |

**代挂的例外：4 单混合单**（`DG` 但 `principal ≠ 0`）

| 日期 | 本金 | 利润 | 交易额 | 勾稽差 | 判读 |
|---|---:|---:|---:|---:|---|
| 2026-07-18 | 670.00 | 465.60 | 1,135.60 | 0.00 | 本金+利润=成交额，**纯买号卖号** |
| 2026-09-14 | 564.00 | 106.00 | 670.00 | 0.00 | 同上 |
| 2026-08-27 | 13,700.00 | 1,000.00 | 14,000.00 | −700.00 | 混入回收性质，第三方分成 700 |
| 2026-09-02 | 4,740.00 | 823.95 | 5,299.00 | −264.95 | 同上，分成 264.95 |

> 现有分类把它们记为代挂，但 `capital_type` 应按实际资金流判定，不可一律标 `ZERO`。

### 1.2 资金池（可自由创建，数量与类型均不固定）

**`pools` 是主数据表。系统不假设池的数量与类型，新增池无需改代码。**

当前两个池是**种子数据**，不是硬编码约束：

| 池 | 源数据名称 | `pool_type` | `ownership` | 用途 |
|---|---|---|---|---|
| 投资款荷包 | 「投资款荷包（本金）」「小荷包」「经营池」 | `INVEST` | `OWNED` | 买号、代垫、付同行 |
| 利润荷包 | 「利润荷包（利润）」「利润池」 | `PROFIT` | `OWNED` | 发提成、抵运营消耗 |

#### 池的两个分类维度

| 维度 | 取值 | 作用 |
|---|---|---|
| `pool_type` | `INVEST` / `PROFIT` / `OTHER` | 业务用途分类，可扩展 |
| `ownership` | `OWNED` / `CUSTODY` / `THIRD_PART` | **资金归属，决定是否计入权益** |

`ownership` 是关键：

| 值 | 含义 | 现金头寸 | 权益 |
|---|---|---|---|
| `OWNED` | 自有（工作室的钱） | ✅ 计入 | ✅ 计入 |
| `CUSTODY` | 代管（客户/同行暂存） | ✅ 计入 | ❌ **不计入** |
| `THIRD_PART` | 第三方（平台保证金） | ✅ 计入 | ❌ **不计入** |

> **实测验证**：新增「代客保管池 5,000」+「平台保证金 2,000」后——
> 现金头寸 45,331.53 → 52,331.53（正确纳入），
> 权益 −54,668.47 **纹丝不动**（正确隔离）。
>
> 没有 `ownership` 维度的话，代管资金会被误算成自有，权益虚高。

| 规则 | 说明 |
|---|---|
| **可创建** | 新增池只需在 `pools` 建一行，无需改代码 |
| **可改名/停用** | `status` 字段控制，停用后禁止新增流水 |
| **不可删除** | 有流水的池只能停用，不能物理删除（保住历史归属） |
| **池余额是算出来的** | 由该池的流水汇总得出，不单独存字段 |

> **命名混乱须治理**：源数据里同一个池有 4 种叫法（投资款荷包/小荷包/经营池/本金池）。
> 系统内统一用 `code`（如 `HJ_INVEST` / `HJ_PROFIT`）标识，显示名可改，`code` 不可改。

### 1.3 业务类型（可自由新增，与资金池解耦）

**业务与池是两个独立维度，不写死绑定。**

- **业务**回答「做什么」——回收 / 提号 / 代挂 / 代分期，也可新增
- **池**回答「钱在哪」——投资款荷包 / 利润荷包，也可新增

#### 关系是多对多

```
        order_type_pools
业务 ────────────────────► 池
 TB ──┬── PRINCIPAL ──► 投资款池
      └── PROFIT────► 代客保管池│
           HS ──┬── PRINCIPAL ──► 投资款池
               └── PROFIT ──► 利润池
                    TB2 ──────────► 代客保管池   （TB2 与 TB 共用池）
```

| 关系 | 例子 |
|---|---|
| 一个业务 → 多个池 | 「同行代收」本金走投资款池、利润走代客保管池 |
| 多个业务 → 一个池 | 「同行代收」与「同行挂单」都用代客保管池 |
| 显式覆盖 | 这一单特殊，指定走别的池 |

#### 路由优先级

```
显式指定（order_events.pool_id） > 业务默认路由（order_type_pools） > 报错
```

#### 业务可自由新增

新增业务只需在 `order_type_defs` 建一行，**不改代码、不改表**：

| 场景 | 做法 |
|---|---|
| 新增业务「同行代收」 | `create_order_type(db, "TB", "同行代收", "PASS_THRU")` |
| 配置其资金路由 | `link_order_type_pool(db, "TB", "PROFIT", "HJ_CUSTODY")` |
| 停用某业务 | `is_active=False`，历史订单保留 |

> **实测验证**：新增 `TB`（同行代收）与 `TB2`（同行挂单）两个业务，
> 关联到新建的「代客保管池」，与 `HS/TH/DG/DFQ` 四个原有业务完全并存，
> 恒等式不受影响（① 45,331.53 ④ −54,668.47 均 PASS）。

## 2. 领域模型（三大板块）

### 2.0 订单类型定义（主理人口述，术语唯一事实源）

**五种业务的资金性质完全不同，模型必须区分。** v1.0 把它们一律当「订单」处理，是资金模型失真的根源。

| 订单类型 | 业务定义 | 资金性质 | 是否占库存 | 本金字段语义 |
|---|---|---|---|---|
| **回收** | 客户把号卖给我 | **库存型** | ✅ 占用 | 买号成本 |
| **提号** | 买家找我买号，我去同行那里提号卖给他 | **过账型** | ❌ 零库存 | 付同行的钱 |
| **代挂** | 客户让我帮忙卖他的号 | **零本金型** | ❌ 号不是我的 | 恒为 0 |
| **代分期** | 代客户买号，到期账号再换绑给他 | **垫资型** | ✅ 占用 + 账期 | 代付的买号款 |
| **返点** | 交易完了平台给我的返利 | **纯利润型** | ❌ | 返点基数（非资金流出） |

#### 各类型的资金流转

```
回收：      经营池 ──买号──► 库存 ──卖出──► 经营池      【占用资金，有跌价风险】
提号：      经营池 ──付同行──► 同行 ──交买家──► 经营池    【逐笔即时对冲，零库存】
代挂：      客户号 ──我代卖──► 买家                        【零本金，只收服务费】
代分期：    投资款池 ──代买号──► 账号（待换绑）──到期换绑──► 客户【垫资 + 账期风险】
返点：      平台 ──返利──► 利润池【附加收入，非独立业务】
```

#### 关键分类：资金占用只算「库存型 + 垫资型」

真实数据核算（2026-07 ~ 10-03）：

| 业务性质 | 类型 | 金额 | 是否计入库存占用 |
|---|---|---:|---|
| **库存型** | `HS` 回收·买号 | 71,305.41 | ✅ 计 |
| **过账型** | `TH` 提号·付同行 | 85,985.00 | ❌ **不计**（逐笔对冲） |
| **垫资型** | `DFQ` 代分期·垫资 | 2,907.00 | ✅ 计（+账期风险） |
| 费用 | 代分期介绍费/作图 | 130.88 | ❌ 计运营消耗 |
| **合计** | | **160,328.29** | **库存占用仅 74,212.41** |

> **注意**：提号过账 85,985.00 **不得计入库存占用**。若误计，库存占用会被高估 86,115.88。
> 提号业务逐笔即时对冲（实测：8/11 付同行 16,688 → 同日收回 16,688；8/20 付 6,000 → 同日收回 6,000），
> 钱只是过一道手，不形成库存资产。

#### 修正后的恒等式②

```
② 库存占用 = Σ(BUY.amount WHERE order_type IN ('HS','DFQ'))
            − Σ(SELL.principal WHERE order_type IN ('HS','DFQ'))
            ≈ 74,212.41（含代分期垫资 2,907.00）
```

### 2.1 订单板块

**核心原则：一个真实业务动作 = 一条 `order_events` 记录。** 从模型层面消灭 WPS 的双计问题。

#### 表结构

| 表 | 作用 | 关键字段 |
|---|---|---|
| `orders` | 订单主表，**只存汇总** | id / **order_no(业务单号)** / **order_type(仅 HS/TH/DG/DFQ)** / **capital_type** / account_id / **link_status** / owner_id / trade_date / gross_amount / status |
| ↳ 回款池归属 | — | **不在订单上**，记在 `order_events.pool_id`（池可自由创建，订单层写死会无法扩展） |
| `order_events` | 动作事件流（核心） | id / **event_no** / order_id / event_type / amount / **portion(PRINCIPAL/PROFIT/GROSS)** / occurred_on / **pool_id** / counterparty / **offset_event_id** |
| `accounts` | 在途账号 | id / **account_no** / **game_account(唯一, 可空)** / buy_date / cost_amount / sale_amount / status / **channels(JSON多值)** / buyer / bind_phone / **risk_level** |
| `installments` | 分期合约 | id / **inst_no** / account_id / principal / down_payment / periods / paid / status / next_pay_date / **rebind_date** |
| `rebate_details` | 返点明细 | order_id / channel / **rebate_type(首保/续保/收号)** / rate / base_amount / gross_amount / platform_fee / net_amount |

#### 事件类型（5 种，封闭枚举）

| event_type | 触发时机 | 资金方向 | 产生差价 | 计入库存 | 适用类型 |
|---|---|---|---|---|---|
| `BUY` 买号 | 动用投资款池买号/付同行/代垫 | 池 − amount | 否 | ✅ | `HS` `DFQ` `TH` |
| `SELL` 售出 | 号卖出并回款 | 池 + amount | 是 | 释放 | `HS` `DFQ` `TH` `DG` |
| `REBATE` 返点 | 平台返利入账（**附属事件**，须有 source_order_id） | 池 + amount | 是（全额） | ❌ | 全部四类 |
| `TRANSFER` 划转 | 池内/池间划转 | **不影响余额** | 否 | ❌ | 全部 |
| `CANCEL` 撤销 | 提号取消/买家违约 | 池 + amount | 反向调整 | 释放 | `TH` `DFQ` |

> **新增 `offset_event_id`**：过账型业务（提号）的 `BUY` 与 `SELL` 需互相引用，
> 成对冲销时自动核销，避免时点错配导致库存虚增。
> 真实案例：8/29 付同行 5,520 → 8/30「提号取消」收回 5,520。

> **新增 `CANCEL`**：实测存在「提号取消 5,520」这类业务，原 4 型事件无法表达。

#### 订单类型与事件组合

| order_type | capital_type | 事件组合 | 库存占用 | 利润 |
|---|---|---|---|---|
| 回收 `HS` | `STOCK` 库存型 | BUY + SELL | ✅ 占用并释放 | 售价−成本 |
| 提号 `TH` | `PASS_THRU` 过账型 | BUY + SELL（成对冲销） | ❌ | 买家价 − 同行价 |
| 代挂 `DG` | `ZERO` 零本金型 | SELL | ❌ | 成交额×抽成 |
| 代分期 `DFQ` | `CREDIT` 垫资型 | BUY + SELL + 分期表 | ✅ 占用+账期 | 分期利息 |
| ~~返点~~ | — | **不是独立业务**，见 `rebate_records` 附属表 | ❌ | 附加在主业务上 |

#### 账号状态机

```
在库 ──SELL──► 已售
 │                │
 │                └── 分期未结清 ──► 分期中
 └── 撤单/退货 ──► 已退
```

**入库硬约束**：账号入库（`BUY`）后 7 日内未被任何 `SELL` 事件引用，进「呆滞库存」告警。

### 2.1.1 标识与编号体系

#### 现状：源数据无业务 ID（实测结论）

五张表**均无业务编号**，跨表关联基本不可能。

| 表 | 行数 | 平台行 ID | 业务 ID |
|---|---:|---|---|
| `cashflow` | 196 | ✅ `Bt`/`Bu` | ❌ |
| `orders` | 89 | ❌ 连行 ID 都没有 | ❌ |
| `accounts` | 39 | ✅ `Cb` | ❌ |
| `installments` | 4 | ❌ | ❌ |
| `leads` | 12 | ❌ | ❌ |

> 平台行 ID 是多维表格内部行号，**换文档或重建表即失效**，不可作为关联键。

#### 关联链实测

```
accounts(36) ──[账号密码]──► installments(4)   ✓仅能中1/4
accounts(36) ──[无]────────► orders(89)       ✗ 零交集
orders(89)   ──[无]────────► cashflow(196)    ✗ 仅能靠日期+金额猜
```

**根因**：`orders` 全部字段仅 9 个——`交易金额 / 利润 / 售卖员 / 回收员 / 回款账户 / 日期 / 月份 / 本金 / 订单类型`，
**无账号密码、无手机号、无营地号**，与账号台账零交集。
唯一像业务编号的 `查询数据编号` 字段，89 单中仅 **6 单**有值（8%）。

#### 唯一可用的天然键

| 字段 | 有值 | 唯一 | 判定 |
|---|---:|---:|---|
| `accounts.账号密码` | 36 | **36** | ✅ 唯一，可作账号主键 |
| `accounts.密码` | 36 | 36 | ✅ 唯一 |
| `accounts.绑定手机号` | 32 | **11** | ❌ 大量重复，**不可作键** |
| `orders.查询数据编号` | 6 | 6 | ⚠️覆盖率仅 8% |

#### 设计对策

**① 全部实体自建业务编号（纯顺序号，不含日期）**

| 表 | 编号字段 | 格式 | 示例 |
|---|---|---|---|
| `orders` | `order_no` | `HJ` + 4位序号 | `HJ0001` |
| `order_events` | `event_no` | 订单号 + 事件码 | `HJ0001-BUY` |
| `accounts` | `account_no` | `HJACC` + 4位序号 | `HJACC0001` |
| `installments` | `inst_no` | `HJINS` + 4位序号 | `HJINS0001` |
| `cashflow` | `flow_no` | `HJF` + 4位序号 | `HJF0001` |
| `pools` | `code` | 大写英文 | `HJ_INVEST` |

**编号规则**：
- 纯顺序号，**不含日期**，全局递增不按天重置
- 统一 4 位（上限 9999），**超出即报错，禁止静默进位**
- 创建后**永不修改**，作为全系统业务主键
- 数据库自增 `id` 仅作内部外键，不对外暴露、不参与业务关联

> 排序与检索靠 `trade_date` / `occurred_on` 字段，不靠编号。
> 编号只保证唯一与可读，不承担时间语义。

**② 账号用双重标识**

| 标识 | 字段 | 用途 |
|---|---|---|
| 业务编号 | `account_no` | 对外引用、人工沟通 |
| 账号号 | `game_account`（QQ号等） | 与平台对接、查重唯一键 |

> `game_account` 建唯一索引，但**允许为空**（未取得账号号时先挂单）。
> `绑定手机号` 不作唯一键——实测 32 条只有 11 个不同值。

**③ 历史孤儿数据处理（强制）**

| 情形 | 处理 |
|---|---|
| 89 单无 `account_id` | **不回填**。`account_id` 允许 NULL，标 `link_status=UNLINKED` |
| 关联失败的旧单 | 报表中归入「不可算」区，**不参与**库存周转/呆滞统计 |
| 3 笔分期无对应账号 | 保留孤立记录，标 `link_status=ORPHAN` |

> **原则：宁可标记为不可算，不做不可靠的自动匹配。**
> 现有 `linkage.py` 启发式匹配实测仅中 6/89（准确率 6.7%），
> 错误关联会污染利润与库存数据，比缺关联危害更大。

**④ 迁移期双轨运行**

| 阶段 | 策略 |
|---|---|
| M0–M2 | 新数据强制填 `order_no` / `account_id`；历史数据标 `link_status` |
| M3 起 | 库存周转、呆滞清单等报表**仅统计 `link_status=LINKED` 的数据** |
| 历史部分 | 报表页脚固定标注「2026-07 前的历史订单无账号关联，不计入周转指标」 |

> **影响**：库存周转天数、呆滞库存等指标**从 M0 之后的新数据开始才有值**。
> 现有 89 单历史订单无法回溯，这是数据事实，不做补造。

### 2.2 资金板块

#### 表结构

| 表 | 作用 | 关键字段 |
|---|---|---|
| `pools` | **资金池主数据（可自由创建）** | id / **code(不可改)** / name / **pool_type** / **ownership(OWNED/CUSTODY/THIRD_PART)** / status / note |
| `order_type_defs` | **业务类型主数据（可自由新增）** | id / **code(不可改)** / name / capital_type(默认，可按单覆盖) / is_active / sort_order |
| `order_type_pools` | **业务↔池 多对多路由** | order_type_id / pool_id / portion(PRINCIPAL/PROFIT/GROSS) |
| `cashflow` | 资金流水（唯一入口） | id / **flow_no** / occurred_on / **pool_id(FK必填)** / **nature** / category / direction / amount / order_id / **transfer_id** / remark |
| `categories` | 类别字典 | code / name / is_operating_cost |

> **每笔流水必须指定 `pool_id`**。这是双池模型的第一约束——无池归属的流水无法核算。

#### 现金流性质标签 `nature`（4 值，必填）

| nature | 含义 | 影响池余额 | 影响损益 | 真实数据示例 |
|---|---|---|---|---|
| `EXTERNAL_IN` 外部注入 | 股本 / 借款 | ✅ | ❌ | 投资款 17,500（7/7） |
| `BUSINESS_IN` 经营流入 | 售出打回 / 返点 | ✅ | 仅差价 | 回收本金 700（7/23） |
| `BUSINESS_OUT` 经营流出 | 买号 / 运营 / 薪资 | ✅ | 仅运营消耗 | 房租水电 4,235.31（7/14） |
| `INTERNAL` 池内划转 | **利润池 → 投资款池** | 源池− / 目标池+ | ❌ | 八月利润转入 13,470.42（9/16） |

> **`INTERNAL` 是双池专属机制**：一笔流水影响两个池。
> 字段 `transfer_id` 关联成对的两条流水（一条 `INTERNAL_OUT`，一条 `INTERNAL_IN`），
> 保证两池增减对称、可追溯。
>
> **验收硬条件**：`INTERNAL` 流水不得计入「经营损益」，只影响池余额。
> 源数据把「八月利润转入 13,470.42」记成了运营收入，会虚增利润——这是必须堵掉的洞。

#### 池间划转规则

| 方向 | 场景 | 是否允许 |
|---|---|---|
| 利润池 → 投资款池 | 利润补充买号资金 | ✅ 允许（须有 `transfer_id`） |
| 投资款池 → 利润池 | 预支利润发工资 | ⚠️ 需主理人确认 |
| 同池内划转 | 微信↔支付宝 | ✅ 允许（**不影响池余额**，只换账户） |

> **同池内换账户**：微信/支付宝/银行卡之间转账，池余额不变。
> 需 `accounts` 子表记录物理账户，否则同池多账户无法对账。

#### 运营消耗类别（`is_operating_cost = true`）

| 类别 | 全称 | 真实数据支出合计 |
|---|---|---:|
| `房租/日用` | 房租水电/日常 | 12,125.90 |
| `办公用品` | 办公采购 | 2,119.41 |
| `员工薪资` | 固定薪资发放 | 19,689.08 |
| `运营` | 平台认证/押金/学习费 | 9,990.33 |

## 3. 核算口径与恒等式（验收标准）

**以下恒等式为系统正确性的硬标准，任何一条不成立即为缺陷。**
双池模型下，①②须**分池计算**，③是全池合并口径。

### 3.1 恒等式①：单池余额

```
池余额(pool) = Σ(该池 EXTERNAL_IN) + Σ(该池 BUSINESS_IN)
             − Σ(该池 BUSINESS_OUT) + INTERNAL 净流入

两个池合并（= 全现金头寸）：
   = 100,000.00 + 131,260.12 + 18,324.42 − 160,328.29 − 43,924.72
   = 45,331.53
```

**已实测通过（差 0.00）**。实现后须能分别输出两个池的独立余额。

### 3.2 恒等式②：库存占用

```
② 库存占用 = Σ(BUY.amount WHERE capital_type IN ('STOCK','CREDIT'))
            − Σ(SELL.principal WHERE capital_type IN ('STOCK','CREDIT'))
            = (71,305.41 回收·买号 + 2,907.00 代分期垫资) − 对应回款本金
            ≈ 74,212.41 上限
   ⚠️ 不含提号过账 85,985.00（逐笔对冲，零库存）
```

### 3.3 恒等式③：经营损益（全池合并）

```
③ 经营损益 = Σ四类业务利润 + Σ返点 − Σ运营消耗
            = 33,820.05 + 1,264.98 − 44,055.60
            = −8,970.57
   ⚠️ 须排除 INTERNAL 划转（八月利润转入 13,470.42 不是收入）
```

> **运营消耗修正**：源数据把「同行代分期介绍费 106.00」与「作图费用 24.88」错放在
> 「账号回收」类别，旧口径 43,924.72 **漏计 130.88 运营支出**。
> 修正后经营损益 **−8,970.57**，比旧口径差 130.88（新值更准确）。

### 3.4 恒等式④：权益

```
④ 权益 = **自有池**余额合计 − 股本
        = 45,331.53 − 100,000.00
        = −54,668.47
   ⚠️ 只算 ownership=OWNED 的池；代管资金不计入权益
```

### 3.5 恒等式⑤：双池划转对称性（双池专属）

```
⑤ Σ(INTERNAL_OUT) = Σ(INTERNAL_IN)   按transfer_id 逐对相等
   源数据当前仅 1 笔：9/16 利润池→投资款池 13,470.42
```

> **任何一条 `INTERNAL` 流水不成对，即为数据缺陷。**

### 3.6 恒等式之间的勾稽关系

```
① = 股本 + ③ + 划转影响
   验证：100,000.00 + (−8,839.69) = 91,160.31
   差额 45,828.78 来自库存沉淀与池内划转

② 库存占用 → 资产层
   在库账号 10 个，占用本金 41,547.83（台账口径，与② 差 12,479.66，因台账漏登记部分买号）
```

### 3.7 迁移映射：源数据 → 双池模型

| 源数据「类别」 | 目标 `nature` | 目标 `pool_id` |
|---|---|---|
| 投资款 | `EXTERNAL_IN` | 投资款荷包 |
| 账号回收（收） | `BUSINESS_IN` | 本金→投资款荷包；利润→利润荷包（按订单 `wallet` 拆） |
| 账号回收（支） | `BUSINESS_OUT` | 投资款荷包 |
| 房租/日用、办公用品、员工薪资、运营（支） | `BUSINESS_OUT` | 投资款荷包 |
| 房租/日用、运营（收） | `BUSINESS_IN` | 投资款荷包 |
| 八月利润转入 | `INTERNAL` | **利润荷包 → 投资款荷包**（成对） |
